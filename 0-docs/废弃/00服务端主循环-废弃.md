# 服务端主循环 - 最终敲定方案（可直接照做）

> **重要说明**：关于“模拟时间”的所有详细规则已迁移并统一到 [`模拟时间.md`](模拟时间.md)，本文件不再维护相关内容，请移步查看。

> 本文档为“可直接照做”的实现说明，属于 `docx/01-底层架构/1-最终敲定方案`。
>
> **目标（敲定）**：
> - 总世界数据由服务端权威管理。
> - 服务端在内存中维护**权威世界状态**与**内存快照**，按客户端兴趣范围打包下发。
> - 服务端接收客户端“意图指令（Command）”，在权威模拟时间轴上执行并产出事件/快照。
> - **模拟时间**是权威中心系统：世界推进、结算、网络对齐均绑定 `serverTick`（服务端权威 tick，用于联机对齐与推进）/`gameDatetimeDay`（开局以来累计的游戏日序号，用于日结算/账本归档）。
> - **时间倍率模型（敲定）**：
  - **全局时间倍率 `timeScale`**（决定游戏世界的基础推进速度）：默认 `1.0`，换算关系为“现实1秒推进游戏 `timeScale` 小时”。
    - **支持档位**：`0.1, 0.25, 0.5, 0.75, 1.0, 2.0, 3.0, 4.0`。
    - **修改来源与优先级（高 -> 低）**：
      1. **系统强制减速**：当 `tickCostMs`（每 tick 耗时）持续超出 `tickBudgetMs`（目标预算）时，系统可强制降低 `timeScale`（全局时间倍率）以保证模拟不跳步（时间膨胀），且**禁止通过跳步或追帧补算来追赶进度**。
      2. **技能临时修改**：时间类技能可临时改变全局 `timeScale`（允许覆盖玩家调速，但仍受“系统强制减速”的上限约束）。
      3. **玩家调速**：通过右上角时间 UI 按钮在预设档位间切换。
    - **合成算式（补充敲定）**：
      - **技能倍率定义**：时间类技能不直接“加速世界”，而是通过“施法者自加速”体现为“全局减速 + 施法者局部回补”。
        - 若某实体“将自身加速 `x%`”，则该技能的 **全局技能倍率** 定义为：`skillScale = 1 - x`。
          - 示例：自加速 10% -> `skillScale = 0.9`；自加速 50% -> `skillScale = 0.5`。
      - **全局技能倍率取极值（补充敲定）**：同一时刻存在多个全局时间类技能时，取“减速最强”的那个（即 `skillScale` 最小值）。且必须以“仍在持续中的技能”为准：
        - `skillScaleGlobal = min(skillScale_i where skill_i isActive)`
        - 解释：10% 与 50% 同时发动 -> `skillScaleGlobal = 0.5`；若 `0.5`（50%）先结束但 `0.9`（10%）仍在，则立即回到 `skillScaleGlobal = 0.9`；当全部结束后不再由技能约束。
      - `systemCapScale`（系统强制倍率上限）：由性能监测模块根据 `tickCostMs`（每 tick 耗时）/ `tickBudgetMs`（目标预算）给出，作为上限钳制值。
      - **全局时间倍率（敲定更新：统一合成公式）**：
        - 定义：`playerScale`（玩家调速倍率，来自档位）为基准；`skillScaleGlobal`（全局技能倍率，取减速最强者）在玩家基准上做调节；`systemCapScale`（系统强制倍率上限）在性能压力下可直接压低最终速度。
        - 合成：
          - `timeScaleBase = playerScale * skillScaleGlobal`
          - `timeScale = min(timeScaleBase, systemCapScale)`
        - 说明：
          - 计算压力正常且无技能时：`timeScale = playerScale`。
          - 技能以玩家当前档位为基准进行调节（乘算）。
          - 计算压力过大时：系统可直接忽略玩家/技能的期望速度，通过 `systemCapScale` 压低最终 `timeScale`。
      - **实体局部时间倍率（补充敲定）**：
        - `localTimeScale(entity) = clamp(timeScale + bonusScale(entity), 0.1, 4.0)`。
        - 其中 `bonusScale(entity)` 为该实体自身的“局部回补倍率”，通常等于其自加速技能对应的 `x`（例如 10% -> `0.1`，50% -> `0.5`）。
        - 示例：全局减速到 `0.5`，舰船 A 自加速 10%（`bonus=0.1`） -> `local=0.6`；舰船 B 自加速 50%（`bonus=0.5`） -> `local=1.0`。
      - **说明（重要）**：上述规则刻意把“时间类技能”塑造成“制造时间膨胀（全局变慢）并让施法者相对更快”，可用来实现你描述的案例效果。
    - **约束（敲定更新）**：
      - 玩家手动调速 `playerScale`（玩家调速倍率）必须来自上述预设档位集合。
      - 系统强制倍率上限 `systemCapScale`（系统强制倍率上限）允许以 `0.01` 为最小单位进行精确调节（区间钳制 `[0.1, 4.0]`），且 **向下取整到 0.01**。
      - 主循环在每 tick 计算最终 `timeScale`（权威时间倍率/时间膨胀倍率）时：
        - 先计算 `playerScale`（来自档位）、`skillScaleGlobal`（技能极值）、`systemCapScale`（0.01 精度）。
        - 再合成：
          - `timeScaleBase = playerScale * skillScaleGlobal`（以玩家档位为基准，技能在其上调节）
          - `timeScale = min(timeScaleBase, systemCapScale)`（性能压力下系统可直接压低最终速度）
        - 最终钳制：`timeScale = clamp(timeScale, 0.1, 4.0)`（**不再强制向档位取整**）。
  - **实体局部时间倍率 `localTimeScale`**（每个实体独立的局部时间倍率）：
    - **默认行为**：`localTimeScale`（实体局部时间倍率）默认与全局 `timeScale`（全局时间倍率）保持一致。
    - **技能例外（全局时间技能的施法者特权）**：当一个实体释放“修改全局 `timeScale`”的时间类技能时，该技能携带者自身的 `localTimeScale` 默认保持 `1.0`（即不受自己技能影响）。
    - **可修改性**：允许技能在持续期间显式修改自身 `localTimeScale`（例如把自己加速/减速到某个值），且其 `localTimeScale` 仍可被其它技能或效果修改。
    - **影响范围白名单（补充敲定）**：`localTimeScale` 只允许影响“实体自身的局部逻辑推进速度”，具体包含：
      - 武器/技能冷却（cooldown）
      - 护盾恢复、能量恢复等速率
      - 实体级生产/建造队列进度（若该队列挂在实体本体上）
      - 实体身上的 BUFF/DEBUFF 持续时间与周期触发
    - **禁止影响范围（强制）**：`localTimeScale` 禁止影响以下全局与联机对齐概念：
      - `serverTick`（服务端权威 tick）、`tickInDay`（当日 tick 计数）、`gameDatetimeDay`（日序号）
      - 跨日边界与日结算触发点
      - 事件追帧窗口、快照对齐等网络同步语义
    - **取值约束（补充敲定）**：最终生效的 `localTimeScale` 至少钳制到区间 `[0.1, 4.0]`；若采用档位集合，则与 `timeScale` 使用同一档位集合。
> - **双快照模型（敲定）**：
>   - `RealtimeSnapshot`（实时快照）：反映当前正在推进的世界实时态，用于战斗等高频系统。
>   - `DailySnapshot`（上一日快照）：反映“上一日结算完成后”的稳定账本态；**客户端 UI 只读该快照**。
>   - 每日结算在 `tickInDay`（当日 tick 计数）归零时触发（即跨日时刻）；当“今日结算完成并发布”为新的 `DailySnapshot` 后，才算一个完整结算周期。
> - **多结算周期历史（敲定）**：服务端全量保留整局历史；客户端请求窗口由客户端指定（如最近 30 个结算周期），服务端裁剪推送。
> - **结算失败处理（敲定）**：结算失败记录失败位置与关键信息并打印结构化日志用于排查，不强制进入暂停点（可作为运维开关）。

## 1. 模块职责与边界

- **职责**
  - 维护权威时间轴：`serverTick`（服务端权威 tick，用于联机对齐与推进）、`gameDatetimeDay`（开局以来累计的游戏日序号，用于日结算/账本归档）、`timeScale`（权威时间倍率/时间膨胀倍率）。
  - Tick 驱动：以固定 Tick（敲定：25 tick/s，即每 tick 40ms）推进世界。
  - 消费指令队列：取出已通过网络层校验/幂等处理后的 `Command`（客户端意图指令）。
  - 串行执行规则：调用各系统（经济/战斗/AI/事件等）推进权威状态。
  - 生成并分发：事件（`Event`（权威事件增量））与必要快照（`Snapshot`（权威状态快照））。
  - 性能与时间膨胀：监测 `tickCostMs`（每 tick 耗时），必要时调整推进倍率或触发暂停点。

- **不负责**
  - 不做网络连接管理（TCP/UDP socket、收发）。
  - 不做反序列化/鉴权/幂等缓存（应在网络接入层完成）。
  - 不做持久化存档的落盘 I/O（由存档/快照持久化模块负责）。

## 2. 服务端世界数据存储方式（敲定）

### 2.1 三层数据模型

- **权威世界状态（`WorldState`（权威世界状态对象图））**
  - 形态：服务端内存中的对象图/结构化数据（推荐以“表/索引 + 轻对象”组织）。
  - 写入：仅允许在主循环线程落账。
  - 读取：网络线程/打包线程**不得直接读 `WorldState`（权威世界状态对象图）的可变对象**，只能读“只读视图/快照”。

- **内存快照（In-Memory Snapshot）**
  - 形态：由主循环在“落账点”产出的只读数据。
  - 对外：网络线程仅从快照打包发送，避免跨线程读写同一对象。

- **事件环形缓冲（Event Ring Buffer）（P1-3，补齐上限/退化/排序）**
  - **是什么（中文解释）**：
    - 事件环形缓冲是“最近一段 `serverTick`（服务端权威 tick）的事件增量日志缓存”。
    - 适用场景：客户端因丢包/短暂掉线落后时，携带 `fromTick`（客户端最后确认的 tick）向服务端请求补齐事件区间，实现“追帧对齐”。
    - 之所以叫“环形”：它是固定容量结构，新事件持续写入，超过容量会覆盖最旧事件，因此只保证“最近 N tick”可追帧。
  - **用途边界（中文解释）**：
    - 用于联机追帧（短窗增量同步）。
    - **不用于**需要维持 5 游戏日的交互事件（交互事件走 `Interactive Event Store`）。

  - **窗口策略（短窗，按 tick）**：
    - `eventBufferWindowTicks`（追帧窗口覆盖 tick 数）：推荐默认值 `750`（约 30 秒，按 25 tick/s 计算），可按运维配置调整。
    - `oldestTickInBuffer`（缓冲区中最旧 tick）与 `latestTickInBuffer`（最新 tick）。

  - **容量上限（强制）**：
    - `maxEventsPerTick`（每 tick 最大事件数，默认 `64`，可选 `32/64`）：
      - 中文解释：限制单 tick 的事件风暴，避免内存与网络消息爆炸。
    - `eventBufferBytesCap`（事件缓冲最大内存，默认 `1GiB`）：
      - 中文解释：环形缓冲必须有硬上限，否则极端情况下会把内存打爆。

  - **同 tick 内事件顺序（确定性强制）**：
    - 每个事件必须携带 `eventSeqInTick`（tick 内时间序列号，从 1 递增）：
      - 中文解释：同一 tick 内多个系统产出的事件必须有稳定先后顺序，保证回放/对账一致。
    - 事件写入缓冲前必须按稳定键排序：
      - `serverTick`（权威 tick）升序（自然满足）
      - `eventSeqInTick`（tick 内序列号）升序

  - **分包下发与退化策略（强制）**：
    - 当返回事件区间时，允许将事件拆成多个网络包：
      - `eventChunkIndex`（事件分片序号，从 1 开始）
      - `eventChunkCount`（事件分片总数）
      - 中文解释：事件包过大时拆包可提高成功率，避免单包过大导致拥塞或丢弃。
    - 若事件分包发送失败（可靠层多次重试后仍失败），则退化为快照：
      - `resultType = Snapshot`
      - `reasonCode = TooLargeOrSendFailed`（事件过大或发送失败）
    - 若快照同步也失败，则判定客户端连接不可用：
      - 断开连接（踢出），等待重连。

  - **退化为快照的触发条件（补充敲定 + 扩展）**：
    - 客户端请求追帧 `fromTick`（起始 tick）。若 `fromTick < oldestTickInBuffer`：
      - `resultType = Snapshot`
      - `reasonCode = OutOfWindow`（超窗）
    - 若事件响应体积超过阈值 `maxEventResponseBytes`（事件响应最大字节数，运维配置）：
      - `resultType = Snapshot`
      - `reasonCode = TooLarge`（事件响应过大）

  - **响应口径（补充敲定）**：
    - 返回事件时：`resultType = Events`，并给出 `fromTick`（含）到 `toTick`（含）的事件区间。
    - 退化快照时：`resultType = Snapshot`，并携带 `snapshot.serverTick`（快照对应的权威 tick）作为后续追帧基线。

- **交互事件实例存储（Interactive Event Store）（P1-3，强制敲定）**
  - 用途：存储“需要玩家选择/会触发 Buff 或效果”的事件实例，按 `gameDatetimeDay`（日序号）维持 `5` 个游戏日。
  - 写入：仅允许主循环线程写入（创建/选择/过期处理/回收），确保确定性。
  - 读取：允许网络线程从只读快照/只读视图读取用于下发。
  - **事件维持与回收（敲定）**：
    - `retainDays`（保留天数）固定为 `5`。
    - 事件创建时必须计算：`expireDay`（过期日序号）=`createdDay`（创建日序号）+ `retainDays`。
    - 当 `gameDatetimeDay >= expireDay` 且事件仍未解决（未选择）时：自动执行默认选项并回收。
  - **默认选项（敲定）**：
    - 玩家在过期前未选择，则自动选择 `defaultOptionIndex = 1`（默认选项 1）。
    - 默认选项会触发对应的 `effects`（效果列表，例如 Buff）。
  - **最小字段清单（字段行内注释，强制）**：

```ts
interface InteractiveEventInstance {
  eventInstanceId: string;     // 事件实例唯一 ID
  eventDefId: string;          // 事件定义 ID（指向配置表）
  ownerPlayerId: string;       // 事件归属玩家 ID（用于投递/权限）
  createdDay: number;          // 创建日序号（gameDatetimeDay）
  expireDay: number;           // 过期日序号 = createdDay + 5
  state: 'Pending' | 'Resolved' | 'Expired'; // 状态：待选择/已解决/已过期（已执行默认）
  defaultOptionIndex: number;  // 默认选项序号（固定为 1）
  selectedOptionIndex?: number; // 玩家选择的选项序号（若已选择）
  selectedDay?: number;        // 实际选择发生的日序号
  targetEntityIds: string[];   // 影响目标实体 ID 列表（可为空）
  effectIds: string[];         // 要触发的效果/Buff ID 列表（配置驱动）
}
```

  - **执行时机（强制）**：
    - 事件创建：在主循环 `Commit`（落账）阶段创建并入库。
    - 玩家选择：在主循环消费 `Command`（客户端意图指令）时执行，写入 `selectedOptionIndex` 并触发效果。
    - 默认触发：在每 tick 的 `Commit`（落账）阶段扫描 `expireDay <= gameDatetimeDay` 的待选择事件，按稳定顺序（`eventInstanceId` 升序）执行默认选项并回收。
  - **回收（强制）**：
    - 执行完玩家选择或默认选项后，事件实例从 `Pending` 进入 `Resolved/Expired`，并从存储中移除（或移入归档列表，若需要 UI 历史）。
    - 触发的 Buff/效果由其自身持续时间管理，不因事件实例删除而消失。

## 3. 指令队列与消费口径（Command Queue）（强制，可直接照做）

> 本节用于敲定：服务端如何接收/排队/取消/替换/执行 `Command`（客户端意图指令），并与主循环阶段（第 12 节）对齐。

### 3.1 指令队列结构（按 `playerId`（玩家 ID）分桶）

- **网络接入层 -> 主循环的入口队列**：
  - 网络接入层只负责把已完成“反序列化/鉴权/基础限流/幂等去重”的 `Command`（客户端意图指令）推入线程安全入口队列。
  - 主循环线程在 `PrepareTick`（准备 Tick）阶段 drain 入口队列并冻结本 tick 输入。

- **主循环侧分桶队列（强制）**：
  - `pendingByPlayer[playerId]`（按玩家分桶的待执行队列）：仅由主循环线程维护。
  - `cmdIndex[cmdId]`（指令索引，用于取消定位）：用于在取消时快速定位目标指令。
  - （可选）`groupKey`（可覆盖指令的分组键）：用于对“可覆盖型指令”（例如移动目的地）进行覆盖合并，减少堆积。

### 3.2 权限校验（强制）

- 所有 `Command`（客户端意图指令）在入队与执行前都必须校验 `playerId`（玩家 ID）权限：
  - `playerId`（玩家 ID）必须对 `targetEntityId`（被操控实体 ID）拥有控制权，否则拒绝执行。
  - `CancelCommand`（取消指令）也必须校验：只能取消由同一 `playerId`（玩家 ID）提交且仍处于待执行状态的指令。

### 3.3 取消/替换规则（强制敲定）

- **取消边界（敲定）**：
  - 仅允许取消仍处于 `pendingByPlayer[playerId]`（按玩家分桶的待执行队列）中的指令。
  - 一旦指令进入本 tick（进入 `PrepareTick`（准备 Tick）冻结输入集合），**禁止变动**（禁止取消/修改）。

- **修改方式（敲定）**：
  - 统一采用“`CancelCommand`（取消指令） + 新 `Command`（客户端意图指令）”实现修改。
  - 禁止对同一 `cmdId`（指令唯一 ID）原地修改 payload（指令参数）。

- **取消结果（建议口径）**：
  - 取消成功：返回 `CancelOk`（取消成功）。
  - 取消失败：返回 `CancelRejected`（取消被拒绝）并包含 `reasonCode`（原因码，例如：NotFound/AlreadyFrozen/AlreadyExecuted/Unauthorized）。

### 3.4 冻结输入与排序（确定性强制）

- 在 `PrepareTick`（准备 Tick）阶段：
  - drain 入口队列得到 `incomingCommands`（本 tick 新收到的指令集合）。
  - 按稳定键排序后入桶（避免并发到达顺序导致非确定性）。

- **排序键（强制口径）**：
  - 桶内：按 `clientSeq`（客户端递增序号）升序；完全相同再按 `cmdId`（指令唯一 ID）稳定排序。
  - 跨玩家执行：按 `playerId`（玩家 ID）升序轮询（round-robin）取指令，避免单玩家/单 AI 吃满 tick 预算。

### 3.5 限流与堆积策略（强制项，参数可调）

- **全局上限**：`maxCommandsPerTick`（每 tick 最大处理指令数），用于避免单 tick 计算量爆炸。
- **分源上限**：
  - `maxCommandsPerTickPerPlayer`（每玩家每 tick 最大处理指令数）。
  - `maxCommandsPerTickPerAi`（每 AI 每 tick 最大处理指令数，用于 AI 难度：普通=1，困难=2/3…）。

- **堆积策略（默认）**：
  - 未处理完的指令保留在 `pendingByPlayer[playerId]`（按玩家分桶的待执行队列）中，下 tick 继续处理。

- **可覆盖指令（可选增强）**：
  - 对可覆盖型指令（例如移动目的地）可定义 `groupKey`（可覆盖指令的分组键），同一 `groupKey`（可覆盖指令分组）只保留最后一条，旧指令等价于被取消。

### 3.6 指令执行回执（CommandAck/CommandResult）（P1-4，强制敲定）

> 本节用于敲定：当服务端在主循环内执行 `Command`（客户端意图指令）后，如何把“成功/失败结果”回传给客户端。
>
> **目标**：
> - 指令执行成功：服务端正常推进世界并产生事件/快照即可；同时给客户端一个可对账的成功回执。
> - 指令执行失败：服务端不改变权威状态；必须给客户端发送失败回执，用于 UI 提示（提醒玩家为什么失败）。
>
> **可靠性（强制）**：
> - `CommandAck`（指令回执）必须走可靠投递通道（或可靠层），避免“失败了但客户端不知道”。
> - 回执必须是幂等的：客户端重复收到同一 `cmdId` 的回执应当覆盖/忽略重复，不产生副作用。

#### 3.6.1 回执消息结构（字段行内注释，强制）

```ts
interface CommandAck {
  cmdId: string;          // 指令全局唯一 ID（用于幂等/去重/对账）
  clientSeq: number;      // 客户端递增序号（用于客户端侧乱序处理）
  playerId: string;       // 发起玩家 ID
  serverTick: number;     // 服务端执行该指令时所在的权威 tick（用于对齐与回放对账）
  status: 'Ok' | 'Rejected' | 'Failed'; // 执行结果：成功/被拒绝（校验不通过）/执行失败（运行期失败）
  reasonCode?: string;    // 原因码（失败/拒绝时必填，用于客户端提示与统计）
  message?: string;       // 可读提示（给 UI 展示的中文短句，避免客户端硬编码）
}
```

- `status`（执行结果）说明：
  - `Ok`（成功）：指令已生效，世界已推进。
  - `Rejected`（被拒绝）：未进入执行逻辑（权限/参数/冻结期等原因）。
  - `Failed`（执行失败）：进入执行逻辑但运行期失败（资源不足、冷却中、状态不满足等）。

#### 3.6.2 失败原因码（reasonCode）（建议集合，可扩展）

- `Unauthorized`（无权限）
- `InvalidTarget`（目标非法/不存在）
- `InvalidParam`（参数非法）
- `AlreadyFrozen`（已冻结，无法取消/修改）
- `NotFound`（找不到对应指令/目标）
- `Cooldown`（冷却中）
- `ResourceNotEnough`（资源不足）
- `StateNotAllow`（状态不允许，例如正在跳跃无法移动）
- `InternalError`（服务端内部错误，需记录日志）

#### 3.6.3 发送时机（强制）

- 指令在 `Update`（更新世界状态）阶段被消费并执行：
  - 成功：在该 tick 的 `PostUpdate`（更新后处理）阶段将 `CommandAck{status='Ok'}` 放入网络发送队列。
  - 失败/拒绝：在该 tick 的 `PostUpdate` 阶段将 `CommandAck{status='Rejected'|'Failed'}` 放入网络发送队列。

#### 3.6.4 与事件追帧/快照的关系（强制说明）

- `CommandAck` 用于“玩家输入是否生效”的提示与对账，不替代 `Event`（权威事件增量）与 `Snapshot`（权威状态快照）。
- 客户端状态对齐仍以 `Event Ring Buffer`（追帧事件）与 `Snapshot`（快照）为准。

#### 3.6.5 客户端提醒策略（强制）

- 当收到 `CommandAck.status != 'Ok'` 时：
  - 客户端应根据 `message`（中文短句）进行 UI 提示（例如 toast/弹窗），并可结合 `reasonCode` 做更细化展示。
- 当连续发生 `InternalError` 或快照同步失败导致断开时：
  - 客户端提示“连接中断/已掉线”，并走重连流程。

## 4. 确定性约束清单（强制）

> 目的：保证“相同输入序列 + 相同初始状态”得到相同结果。

- **随机数（RNG）**
  - 禁止在权威逻辑中直接使用 `Math.random()`、`System.currentTimeMillis()` 作为随机源。
  - 必须使用确定性 RNG：`rng(seed, serverTick, entityId, subsystemId, purpose)`（示例口径）。

- **遍历顺序**
  - 禁止依赖 `HashMap/HashSet` 的迭代顺序产生结论。
  - 任何需要“批量处理”的集合，在落账前必须按稳定键排序（如 `entityId`、`orderId`）。

- **并行任务归并**
  - 并行任务只允许产出“候选结果”，最终落账必须在主循环线程完成。
  - 归并时必须按稳定顺序处理（例如对结果按 `id` 排序）。

- **浮点与精度**
  - 涉及账本、命中、结算等强一致结果：优先使用整数/定点/量化口径。
  - 坐标等允许用 `double`，但必须遵循既定单位与换算规则，禁止用 `float` 作为权威存储。

## 4. 双快照模型（RealtimeSnapshot + DailySnapshot）

### 4.1 定义

- **RealtimeSnapshot（实时快照）**
  - 用途：战斗/移动等实时系统的对外同步。
  - 刷新频率：高频（每 tick / 每 N tick / 事件聚合）。

- **DailySnapshot（上一日快照）**
  - 用途：经济/科研/人口等日结算系统 + 客户端 UI 面板展示。
  - 刷新频率：每日结算完成后切换一次。

### 4.2 各系统读写口径（强制）

- **经济系统等“按日结算”的系统**
  - 对外展示/查询：**只能读 `DailySnapshot`（上一日快照）**。
  - 今日结算：以“上一日快照”作为基准数据。

- **战斗系统等“需要实时结算”的系统**
  - 对外同步：读 `RealtimeSnapshot`（实时快照）或事件流。
  - 高频推进：按 tick（或更细步长）处理。
  - 算力不足：优先启用时间膨胀（降低 timeScale）争取计算时间，避免跳步。

## 5. 快照最小字段清单（敲定：派系为主 + 二级索引）

> 本节用于统一最小可落地结构（后续可增字段，但不能破坏语义）。

### 5.1 DailySnapshot（UI/日结算读）

- **Header**
  - `snapshotId`（快照唯一 ID）
  - `schemaVersion`（结构版本）
  - `gameDatetimeDay`（该账本对应的归档日序号）

- **派系主维度数据（按 `factionId`）**
  - `factionDailyStats[factionId]`：
    - `money`（资金余额/摘要）
    - `moneyDelta`（本周期变化）
    - `population`（人口）
    - `inventoryByResource[resourceId]`（库存）
    - `tradeVolumeByResource[resourceId]`（成交量/均价可选）
    - `importantEvents[]`（重要事件摘要：eventId/type/day）

- **二级索引（必须）**
  - `planetOwnerIndex[planetId] -> factionId`
  - `fleetOwnerIndex[fleetId] -> factionId`
  - `shipOwnerIndex[shipId] -> factionId`（可选，若 shipId 在客户端侧出现）
  - **维护机制（补充敲定）**：
    - 二级索引属于 `DailySnapshot` 的派生数据，**不要求在 `WorldState` 中实时维护**。
    - 在“发布新 `DailySnapshot newDaily`”的构建过程中，由主循环线程基于落账后的权威数据一次性构建上述索引，确保与 `newDaily` 内容严格一致。
    - 若后续出现“实时系统需要 ownerIndex”的需求，应在 `RealtimeSnapshot` 侧提供等价索引或直接下发实体 `ownerFactionId`，禁止复用 `DailySnapshot` 的索引语义。

- **多周期历史（全量保留，按需下发）**
  - 服务端存储：全量周期序列（整局）
  - 客户端请求：指定 `historyWindowDays = N`，服务端裁剪为最近 N 天

### 5.2 RealtimeSnapshot（战斗/态势读）

- **Header**
  - `snapshotId`（快照唯一 ID）
  - `serverTick`（服务端权威 tick，用于联机对齐与推进）

- **实时实体最小集（按兴趣范围裁剪）**
  - `fleets[]`（`fleetId`（舰队唯一标识符）、`ownerFactionId`（所属派系 ID）、位置/速度摘要、战斗态势摘要）
  - `combatStates[]`（`combatId`（战斗唯一标识符）及战斗参与者的关键状态）

## 8. 日结算流程（可直接照做，P1-2：补充并行 Draft 状态机）

> 结算时刻：当 `tickInDay`（当日 tick 计数）归零时（即跨日时刻）。
>
> **结算周期（敲定）**：
> - 游戏每日 24 时，0 时为结算点。
> - 一个结算周期为 `24（游戏时） * 25（tick/时） = 600 tick`。
>
> **系统分工（敲定）**：
> - 经济系统：在 600 tick 周期内做“日内累计”（写 `DailyAccumulator`），在结算点完成“日结算”并发布新的 `DailySnapshot`（上一日快照）。
> - 战斗/移动：实时推进，结果写入权威 `WorldState`，并在每 tick 构建/更新 `RealtimeSnapshot`（实时快照）。
>
> **重要澄清（强制）**：
> - `DailySnapshot oldDaily`（上一日快照）为不可变只读对象，禁止原地修改。
> - 结算完成后必须构建并发布 `DailySnapshot newDaily`（新日快照），通过 `dailyRef`（原子引用）切换。

### 8.1 日结算并行 Draft 的含义

- `DailySettlementDraft`（日结算草稿）是后台线程对“日结算结果”的只读计算产物：
  - 允许并行（多核）计算。
  - 禁止写入 `WorldState`（权威世界状态对象图）。
  - 必须是不可变对象（immutable），以保证跨线程传递安全。

### 8.2 日结算状态机（强制）

- `DailySettlementState`（日结算状态）定义：
  - `Idle`（空闲）：无结算任务在进行。
  - `DraftComputing`（草稿计算中）：后台线程正在计算 `DailySettlementDraft`。
  - `DraftReady`（草稿就绪）：后台线程已产出 `DailySettlementDraft`，等待主循环落账。
  - `CommitApplying`（落账中）：主循环正在把结果落账到 `WorldState` 并发布 `newDaily`。
  - `Failed`（失败）：本次结算失败，等待运维策略处理（重试/跳过/暂停）。

### 8.3 结算触发与调度（强制）

- 当检测到跨日（`tickInDay` 归零、`gameDatetimeDay` +1）时：
  - 主循环仅负责**触发**结算任务，不在同一个 tick 内进行大规模计算。
  - 生成 `DailySettlementJobInput`（结算输入快照，主循环构建的只读输入包），至少包含：
    - `oldDaily`（上一日快照，只读）
    - `dailyAccumulatorSnapshot`（日内累计器只读副本）
    - `gameDatetimeDay`（本次要归档的日序号）
  - 将任务提交到结算线程池，状态进入 `DraftComputing`。

### 8.4 并行 Draft 计算（后台线程，强制）

- 后台线程执行：`draft = computeDailySettlementDraft(input)`。
- 输出 `draft` 至少包含：
  - `draftDay`（草稿对应的归档日序号）
  - `economyResults`（经济系统结算结果集合）
  - `dailySnapshotPayload`（构建 `newDaily` 所需的数据载荷或构建参数）
- 禁止事项：
  - 禁止写入 `WorldState`。
  - 禁止读写可变的 `WorldState` 引用。

### 8.5 Commit 落账与发布（主循环线程，强制）

- 主循环在 `Commit`（落账）阶段检查状态：
  - 若 `state == DraftReady` 且 `draft.draftDay == gameDatetimeDay - 1`（结算目标日）：
    - 进入 `CommitApplying`。
    - 将 `draft` 转换为 `DailySettlementDelta delta`（日结算增量），并按确定性顺序应用到 `WorldState`。
    - 构建 `DailySnapshot newDaily`（新日快照），并 `dailyRef.set(newDaily)` 原子切换。
    - 清空/轮换 `DailyAccumulator`（日内累计器），进入下一天的累计。
    - 状态回到 `Idle`。

### 8.6 UI 读取与一致性（强制）

- UI 永远只读 `dailyRef.get()` 返回的 `DailySnapshot`。
- 当跨日已发生但结算草稿仍在计算中：
  - UI 仍然读取旧的 `DailySnapshot oldDaily`。
  - 直到 `newDaily` 发布后，UI 才会在下一次拉取时看到新账本。

### 8.7 失败处理（强制）

- 结算失败时：
  - 不发布 `newDaily`；`dailyRef` 保持旧值。
  - 状态进入 `Failed`。
  - 记录结构化日志：
    - `gameDatetimeDay`（归档日序号）
    - `phase`（失败阶段：Draft/Commit/BuildSnapshot）
    - `errorCode`（错误码）
    - `exception`（异常对象）
    - `inputSummary`（输入摘要）
  - 后续策略（运维开关，默认不阻塞主循环）：
    - `retryNextTick`（下一个 tick 重试 Commit，若 Draft 已就绪）
    - 或 `retryRecomputeDraft`（重新提交 Draft 计算任务）
    - 或 `haltOnFailure`（进入暂停点，等待人工处理）

## 12. 主循环阶段与时间推进（补充敲定）

本节用于明确主循环的执行阶段、`serverTick` 递增规则与游戏时间推进公式，解决“落账点”与时间换算模糊点。

### 12.1 主循环阶段（强制口径）

每个 tick（40ms）按以下阶段串行执行：

1.  **`PrepareTick`（准备 Tick）**
    - `serverTick`（服务端权威 tick）**递增 +1**。
    - 冻结本 tick 的输入：从网络层 `Command`（客户端意图指令）队列中取出本 tick 要处理的指令集合。
    - 计算本 tick 最终的 `timeScale`（全局时间倍率）。
    - 计算本 tick 的游戏时间步长 `dtGameHours`（游戏内小时增量）。

2.  **`Update`（更新世界状态）**
    - **消费指令**：按排序规则执行 `Command` 集合，改变 `WorldState`（权威世界状态对象图）中的实体状态。
    - **系统推进**：调用各子系统（经济/战斗/AI/事件等）的 `update(dtGame)` 方法，传入游戏时间步长。
    - **并行计算**：允许在此阶段将“只读计算”或“候选结果计算”分发到工作线程，但结果不能直接写入 `WorldState`。

3.  **`Commit`（落账）**
    - **串行写入点**：将并行计算的候选结果按确定性规则（如按 ID 排序）归并回 `WorldState`。**这是唯一允许写入权威状态的阶段**。
    - **日结算触发**：检查累计游戏时间是否跨日，若跨日则触发“日结算流程”（见第 8 节）。

4.  **`PostUpdate`（更新后处理）**
    - **生成快照**：基于落账后的 `WorldState` 构建 `RealtimeSnapshot`（实时快照）。
    - **生成事件**：收集本 tick 产生的所有 `Event`（权威事件增量），放入 `Event Ring Buffer`（事件环形缓冲）。
    - **网络分发**：将需要同步的快照与事件交给网络线程打包下发。

### 12.2 游戏时间推进公式（强制口径，已敲定）

> **敲定口径（重要）**：
> - `serverTick`（服务端权威 tick）为唯一权威时间轴：**每秒 25 tick**。
> - **游戏时间与 tick 的换算敲定为**：`25 tick = 游戏 1 小时`。
> - 因此：`1 tick = 游戏 1/25 小时 = 144 秒（游戏内）`，且在 `timeScale = 1.0` 时 **现实 1 秒推进游戏 1 小时**。
> - **现实 40ms/tick** 等价于 `tickBudgetMs`（目标预算）：用于与 `tickCostMs`（每 tick 耗时）对比，并驱动 `timeScale`（时间膨胀）控制；**不是“权威游戏日历”的直接来源**。

- **权威游戏时间步长 `dtGameHours`（游戏内小时增量）**
  - **基准步长**：`baseDtGameHours = 1 / 25`（游戏小时/ tick）。
  - **计算公式**：`dtGameHours = baseDtGameHours * timeScale`。
  - 解释：`timeScale`（全局时间倍率）决定“每个 `serverTick` 实际推进多少游戏时间”。当服务器压力过大时，系统降低 `timeScale` 即实现“时间膨胀（游戏变慢）”。

- **权威日历（敲定：权威仅存日序号 + 当日 tick）**
  - **权威字段**：
    - `gameDatetimeDay`（开局以来累计的游戏日序号，从 1 开始）：2100-01-01 对应 `gameDatetimeDay = 1`。
    - `tickInDay`（当日 tick 计数，用于确定当日时刻）：范围 `0 <= tickInDay < ticksPerDay`。
  - **常量**：
    - `ticksPerSecond`（每秒 tick 数）= 25。
    - `ticksPerHour`（每小时 tick 数）= 25。
    - `hoursPerDay`（每日小时数）= 24。
    - `ticksPerDay`（每日 tick 数）= `ticksPerHour * hoursPerDay = 25 * 24 = 600`。

- **时间推进与跨日处理（强制口径）**
  - **每 tick 更新**：`tickInDay += 1`。
  - **跨日检查**：
    - `if (tickInDay >= ticksPerDay)`:
      - `tickInDay = 0`
      - `gameDatetimeDay += 1`
      - **日结算触发**：在 `Commit`（落账）阶段触发“日结算流程”（见第 8 节）。
  - 说明：在 `timeScale != 1.0` 时，`tickInDay` 的推进仍按 tick 计数（用于“跨日节拍/结算边界”），而世界内部各系统以 `dtGameHours` 获取实际推进量。

- **UI 解析与显示口径（敲定）**
  - UI 不显示秒与分钟，最小单位为“时”。
  - **小时解析**：
    - `gameHour = floor(tickInDay / ticksPerHour)`（范围 0~23）。
  - **年月日解析**：以 `gameDatetimeDay`（从 1 开始）为基准，按“每月 30 天、每年 12 月、开局日期 2100-01-01”解析为年月日。

- **可复算样例（用于验收）**
  - `timeScale = 1.0`：现实 1 秒 = 游戏 1 小时；现实 24 秒 = 游戏 1 天（600 tick）。
  - `timeScale = 0.5`：世界内部推进速率减半（每 tick 只推进 0.5 * 1/25 小时）；但跨日仍在第 600 tick 触发（用于稳定账本边界）。
  - `timeScale = 2.0`：世界内部推进速率翻倍；跨日仍在第 600 tick 触发。

## 13. Tick 调度、超预算与时间膨胀（P0，强制敲定：折中方案）

> 本节用于补齐“tick 调度/超预算行为/时间膨胀”的最终口径，确保实现者在超负载情况下行为一致且可验收。
>
> **折中敲定（强制）**：
> 1. **默认模式（B）**：tick 的 wall-clock 目标频率保持为 25 tick/s（`tickBudgetMs = 40ms` 不变）。当超预算时，优先降低 `timeScale`，从而降低每 tick 的 `dtGameHours`（每 tick 推进的游戏时间），让 CPU 在“单位游戏时间”上获得更多计算预算。
> 2. **熔断模式（A）**：当 `timeScale` 已降到最小档仍持续超预算时，允许**降低 tick 的 wall-clock 目标频率**（即增大 `tickBudgetMs`），作为最后手段保证服务器可用性与稳定性。

### 13.1 Tick 调度目标（Wall-clock 节拍，含熔断）

- **默认 tick 频率目标**：`targetTicksPerSecond = 25`。
- **默认预算**：`tickBudgetMs = 1000 / targetTicksPerSecond = 40ms`。
- **调度规则（默认模式与熔断模式通用）**：
  - 主循环维护 `nextTickDeadlineNs`（下一 tick 截止时间，单调递增）。
  - 若本 tick 提前完成，则 sleep 到 `nextTickDeadlineNs`（避免空转）。
  - 若本 tick 超过截止时间（即 `tickCostMs > tickBudgetMs`），则**不追赶、不补算**，下一 tick 立即开始（不 sleep）。

### 13.2 `tickCostMs` 统计口径（强制）

- `tickCostMs`（每 tick 耗时）统计范围：从进入 `PrepareTick`（准备 Tick）到 `PostUpdate`（更新后处理）结束。
- `tickCostMs` 必须为 wall-clock 耗时（例如 `System.nanoTime` 差值），用于与 `tickBudgetMs` 对比。

### 13.3 默认模式（B）：时间膨胀（降 `timeScale`，tick 目标频率不变）

- **触发条件（基础版）**：
  - 当 `tickCostMs > tickBudgetMs` 时，系统进入“时间膨胀”路径：降低 `systemCapScale`（系统强制倍率上限），从而降低最终 `timeScale`。
- **目标效果（B，澄清）**：
  - `timeScale` 只影响 `dtGameHours = baseDtGameHours * timeScale`。
  - `timeScale = 0.5` 表示：每 tick 推进的游戏时间减半（而不是“现实 2 秒才推进 25 tick”）。

### 13.4 `systemCapScale` 的最小可落地规则（强制，可直接照做）

> 说明：这里先给出“最小可落地”的强制规则，后续可在不破坏语义的前提下增强为更平滑的控制器。

- **候选倍率**：
  - `rawCap = tickBudgetMs / tickCostMs`。
  - 解释：若 `tickCostMs` 是预算的 2 倍，则 `rawCap = 0.5`（推进减半）。
- **钳制与取档**：
  - `rawCapClamped = clamp(rawCap, 0.1, 4.0)`。
  - `systemCapScale = floorToCent(rawCapClamped)`（向下取到 0.01 精度，确保“降速足够”）。
- **生效时机**：
  - 在 `PrepareTick`（准备 Tick）阶段计算本 tick 的最终 `timeScale` 时应用。

### 13.5 恢复规则（防抖，强制）

- 为避免 `timeScale` 抖动，采用“连续窗口”恢复：
  - 连续 `recoverWindowTicks` 个 tick 满足 `tickCostMs <= tickBudgetMs`，才允许 `systemCapScale` 上升 1 档。
  - 连续 `overBudgetWindowTicks` 个 tick 满足 `tickCostMs > tickBudgetMs`，才允许 `systemCapScale` 下降 1 档。
- 默认参数（可运维配置）：
  - `overBudgetWindowTicks = 3`
  - `recoverWindowTicks = 10`

- **系统倍率精度（敲定）**：
  - `systemCapScale`（系统强制倍率上限）允许以 `0.01` 为最小单位进行调节。
  - 该精度仅适用于系统强制减速；玩家手动调速仍以预设档位为准。

### 13.6 熔断模式（A）：降低 tick 目标频率（最后手段）

- **进入条件（强制）**：
  - `timeScale` 已降到最小档位（通常为 `0.1`），且仍然持续超预算：`tickCostMs > tickBudgetMs` 连续 `throttleEnterWindowTicks` 个 tick。
- **行为（强制）**：
  - 进入熔断后，允许降低 tick 的目标频率：
    - `targetTicksPerSecond = max(targetTicksPerSecond - throttleStepTps, minTicksPerSecond)`
    - 同步更新 `tickBudgetMs = 1000 / targetTicksPerSecond`
  - 说明：这会降低网络更新/输入处理频率，是“保命模式”。
- **退出/恢复（强制）**：
  - 连续 `throttleRecoverWindowTicks` 个 tick 满足 `tickCostMs <= tickBudgetMs`，则允许：
    - `targetTicksPerSecond = min(targetTicksPerSecond + 1, 25)`
    - 同步更新 `tickBudgetMs`
- **默认参数（可运维配置）**：
  - `minTicksPerSecond = 10`
  - `throttleStepTps = 5`
  - `throttleEnterWindowTicks = 30`
  - `throttleRecoverWindowTicks = 60`

### 13.7 与事件追帧窗口的关系（强制说明）

- `eventBufferWindowTicks`（追帧窗口覆盖 tick 数）是 **按 tick 计数** 的窗口。
- 在默认模式（B）下，tick 频率不变，`eventBufferWindowTicks=750` 约等于 30 秒现实时间。
- 在熔断模式（A）下，tick 频率降低，同样的 `eventBufferWindowTicks=750` 会覆盖更长的现实时间。若要保持“约 30 秒现实窗口”，需要将运维配置的 `eventBufferWindowTicks` 按当前 `targetTicksPerSecond` 动态换算（是否动态换算可作为运维策略，需实现时二选一）。

### 13.8 验收点（强制）

- **默认模式（B）验收**：
  - 人为注入负载，使 `tickCostMs` 稳定在 ~80ms（约 2 倍预算）：
    - `timeScale` 会下降到 `0.5`（或更低，但不得高于 0.5）。
    - tick 目标频率仍为 25 tick/s（未进入熔断）。
- **熔断模式（A）验收**：
  - 在 `timeScale=0.1` 时仍持续超预算，达到进入窗口后：
    - `targetTicksPerSecond` 会按 `throttleStepTps` 下降，直到不再持续超预算或达到 `minTicksPerSecond`。
  - 负载恢复并稳定在预算内：
    - `targetTicksPerSecond` 按恢复窗口逐步回升到 25。
