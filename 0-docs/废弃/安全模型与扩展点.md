# 安全模型与扩展点（不内置反作弊，仅预留接口）

> 目标：定义联机安全模型的**信任边界**（谁可信、谁不可信）、**权限校验口径**、**审计事件流**与**外置校验/风控/反作弊接入点**。
> 
> 约束：本项目当前**不实现任何内置反作弊检测逻辑**，只做“可插拔接口 + 审计数据输出”，确保未来接入第三方系统时不需要大改核心流程。

---

## 1. 核心结论（先读这一段即可落地）

- 服务端权威（server authoritative，服务端说了算）：所有会影响结果的权威状态只能由服务端修改。
- 客户端不可信（untrusted client，客户端输入只能表达意图）：客户端可做预测，但不可决定结果。
- 安全模型的核心是“信任边界 + 可审计”：
  - 通过明确哪些数据不信任客户端，避免“客户端决定结果”。
  - 通过审计事件流（audit event stream，结构化日志）预留第三方接入点。

---

## 2. 信任边界（Trust Boundary）

### 2.1 不信任客户端的数据清单（强制口径）

以下数据即使客户端上报，也只能作为“建议/请求”，服务端必须自己计算或校验：

- 资产与账本（例如金币/资源/库存/科研点等）：
  - `balance`（余额：资产数值）
  - `inventory`（库存：物品集合与数量）
- 战斗结果（例如命中/伤害/死亡/掉落）：
  - `hitResult`（命中结果）
  - `damage`（伤害值）
  - `unitAlive`（单位存活状态）
- 世界推进时间轴：
  - `serverTick`（服务端权威 tick：推进与对齐单位）
  - `simulationDay`（模拟日：宏观结算单位）
- 状态机关键状态（例如外交状态、战争状态、占领归属）：
  - `diplomaticStatus`（外交状态）
  - `ownership`（归属）

### 2.2 允许客户端提供但必须校验的数据（强制口径）

- `cmdId`（指令全局唯一 ID：幂等追踪）
- `clientSeq`（客户端递增序号：排序/乱序检测）
- `clientTick`（客户端本地 tick：预测对账参考）
- `clientTimeMs`（客户端时间戳：诊断）

> 注：这些字段用于网络语义与诊断，但不能用来决定权威结果。

---

## 3. 权限与鉴权口径（Authorization）

### 3.1 基础身份

- `playerId`（玩家/角色 ID：归属与权限主体）必须由服务端会话（session，会话登录态）绑定，客户端不得自行声明。
- `clientId`（客户端会话/连接 ID）用于行为串联与速率统计。

### 3.2 指令权限校验（强制口径）

服务端在执行任何 `Command`（指令：客户端意图）前必须做：

- 身份一致性：会话绑定的 `playerId` 与指令头中的 `playerId` 一致。
- 资源可用性：是否有足够资源执行（例如余额/库存）。
- 状态可执行性：当前状态机是否允许（例如冷却、战争状态限制）。
- 目标归属：是否对目标对象有操作权限（例如己方城市/舰队）。

## 4. 审计事件流（Audit Event Stream）

> 目标：为未来外置反作弊/风控系统提供“可消费的数据流”。
> 
> 口径：审计事件不是业务事件（business event），它不驱动游戏逻辑，只用于观察与分析。

### 4.1 审计事件结构（建议）

```ts
interface SecurityAuditEvent {
  auditId: string;                 // 审计事件 ID：唯一标识一条审计记录
  createdAtUnixMs: number;         // 发生时间（毫秒）：用于排序与时间窗分析

  serverTick?: number;             // 关联服务端 tick（若发生在 tick 内）
  simulationDay?: number;          // 关联模拟日（若适用）

  playerId?: string;               // 关联玩家 ID
  clientId?: string;               // 关联客户端连接/会话 ID
  sessionId?: string;              // 关联会话 ID（可选）

  cmdId?: string;                  // 关联指令 ID（若由指令触发）
  cmdType?: string;                // 关联指令类型
  clientSeq?: number;              // 关联客户端序号

  category: 'CommandReceived' | 'CommandRejected' | 'CommandExecuted' | 'RateLimit' | 'Anomaly' | 'SecurityError'; // 分类
  severity: 'Info' | 'Warn' | 'Error'; // 严重级别

  reasonCode?: string;             // 原因码：拒绝原因/异常原因
  metrics?: Record<string, number>;// 指标：例如频率、间隔、偏差

  extra?: any;                     // 扩展字段：保留给未来第三方系统
}
```

### 4.2 必须输出的审计点位（Hook Points）

- Hook A：指令接收后（收到 `cmdId` 时）
- Hook B：指令校验失败/拒绝（记录 `reasonCode`）
- Hook C：指令执行完成（可记录执行耗时与摘要）
- Hook D：速率限制触发（rate limit，限流）
- Hook E：检测到不一致（例如 `authoritativeHash` 不一致）

## 5. 外置校验/风控/反作弊接入点（仅接口，不实现检测）

### 5.1 接口目标

- 允许外部模块在关键阶段“给出建议动作”：
  - `Allow`（允许继续）
  - `Reject(reasonCode)`（建议拒绝）
  - `Defer(reasonCode, retryAfterMs)`（建议延期）
  - `Flag(auditEvent)`（仅标记：输出审计事件，不拦截）

### 5.2 推荐接入阶段

- 指令接收阶段：用于外部统计与风险评分
- 指令执行前阶段：用于外部规则校验（例如参数范围/频率）
- 指令执行后阶段：用于外部审计与事后分析

> 注：本项目不实现检测逻辑，但必须保证这些阶段存在明确调用点（hook）。

## 7. 验收标准

- 明确列出“不信任客户端”的数据清单，并在服务端执行路径中体现。
- 审计事件结构固定，且能在关键点位输出。
- 外置接口存在且可插拔：不改核心流程也能接入第三方模块。
- 不包含任何内置反作弊检测逻辑（仅接口与审计数据）。
