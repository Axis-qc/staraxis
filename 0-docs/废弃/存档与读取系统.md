# 存档与读取系统（敲定方案）

> 目标：定义存档的**权威结构**、**写入与读取流程**、**版本校验规则**、**自动/手动存档策略**与**失败处理口径**。
>
> 本文档为 `docx/03-核心机制/敲定方案/` 下的敲定方案，作为实现的权威依据。

---

## 1. 版本号写入与读取检测（强制，保持不变）

### 1.1 `gameVersion`（存档生成时的游戏版本）

- `gameVersion`（存档版本号）：推荐采用语义化版本（SemVer），格式为 `MAJOR.MINOR.PATCH`（例如 `1.2.3`）。
- 存档必须写入 `gameVersion`，读取时必须校验。

### 1.2 读取判定规则（强制）

- 若 `save.gameVersion == currentGameVersion`（版本一致）：允许加载。
- 若 `save.gameVersion < currentGameVersion`（存档更旧）：允许加载，但必须提示“版本不一致”。
- 若 `save.gameVersion > currentGameVersion`（存档更新）：拒绝加载，提示玩家版本不兼容。

> 注：本项目不维护自动迁移链（不维护逐版本迁移脚本）。

## 2. 存档格式选择（推荐方案）

> 你问“存档格式要用什么，有什么好建议”。这里给出可落地的选择结论与理由。

### 2.1 推荐：二进制（MessagePack/CBOR） + 可选 JSON 调试导出

- **推荐主格式**：`MessagePack`（或 `CBOR`）。
  - **优点**：
    - 体积比 JSON 小，读写更快。
    - 结构仍是“键值/对象”，比自定义裸二进制更好维护。
    - 兼容性比纯 Protobuf 强依赖 `.proto` 更灵活（本项目又不做迁移链）。
  - **缺点**：
    - 不如 JSON 直观，需要工具查看。

- **建议保留调试导出**（可选开关）：
  - 支持把同一份 `SaveFile` 导出为 JSON（仅用于调试/回归定位，不作为正式存档）。

### 2.2 可选：Protobuf（适合协议统一，但对存档迁移要求更高）

- 若未来你计划把**网络协议与存档 schema 统一**（同一套 `.proto`），可以使用 Protobuf。
- 注意：Protobuf 更适合“严格 schema 管理 + 明确字段演进策略”，而你当前口径是不维护迁移链，因此会增加维护成本。

### 2.3 不推荐：纯 JSON 作为正式存档

- 主要问题：
  - 体积大、解析慢。
  - 浮点/大整数/精度处理容易踩坑。
  - 长局存档会很大。

## 3. 存档文件结构（敲定）

### 3.1 顶层结构（字段带中文注释，强制）

```ts
interface SaveFile {
  meta: SaveMeta;             // 元信息：版本、时间、展示摘要
  world: WorldStateSave;      // 世界权威状态（用于恢复模拟推进）
  dailySnapshot: DailySnapshotSave; // 上一日快照（供 UI 直接读取）

  // 可选：索引/缓存（不影响规则，可丢弃重建）
  indices?: SaveIndices;
}

interface SaveMeta {
  gameVersion: string;        // 存档版本号（必须写入，用于读取判定）
  createdAtUnixMs: number;    // 创建时间（用于 UI 展示）
  updatedAtUnixMs: number;    // 最近保存时间（用于 UI 展示）
  saveName: string;           // 存档名（用于 UI 展示）

  // 展示摘要（不影响规则）
  summary?: {
    gameDatetimeDay: number;  // 当前日序号（用于展示进度）
    tickInDay: number;        // 当前日内 tick（用于展示）
    serverTick: number;       // 当前权威 tick（用于展示/联机恢复基线）
  };

  // 存档类型（用于区分自动/手动/退出前保存等）
  saveType: 'Auto' | 'Manual' | 'Shutdown'; // 存档类型
}

interface WorldStateSave {
  serverTick: number;         // 权威 tick（恢复对齐基线）
  gameDatetimeDay: number;    // 日序号（恢复日历）
  tickInDay: number;          // 日内 tick（恢复日历）

  // 其余权威数据（实体/派系/经济/战斗状态等）
  // 具体字段由 WorldState 的权威结构决定
}
```

### 3.2 与联机追帧的关系（敲定）

- 存档不要求保存 `Event Ring Buffer`（追帧短窗事件），读档后可清空并以 `serverTick` 为新基线。

## 4. 写入流程（保存）（强制）

### 4.1 保存触发点（敲定）

- **手动保存**：玩家主动触发，保存数量不受限制（一直存在）。
- **自动保存**：按“游戏日间隔”触发，见第 5 节。
- **停机保存**：服务端停机前触发一次保存。

### 4.2 保存的一致性与线程模型（敲定）

- 存档内容必须来自主循环线程的稳定点：
  - 推荐在 `Commit`（落账）阶段之后，复制/冻结需要持久化的数据快照（避免跨线程读写 WorldState）。
- 落盘 I/O 由独立存储线程执行，避免阻塞主循环。

### 4.3 原子写入（强制）

- 必须采用“临时文件 + 原子替换”流程：
  1. 写入 `save.tmp`
  2. flush/fsync
  3. rename 为正式文件名（原子替换）
- 写入失败：不得破坏旧存档。

## 5. 自动存档策略（敲定）

### 5.1 自动保存档位（敲定）

- 自动保存间隔以 `gameDatetimeDay`（日序号）为准，提供四个档位：
  - `7`（每 7 游戏日）
  - `30`（每 30 游戏日）
  - `90`（每 90 游戏日）
  - `180`（每 180 游戏日）

### 5.2 触发行为（敲定）

- 当到达保存间隔时：
  - **自动暂停**主循环推进（暂停推进的含义：停止世界模拟写入；网络可继续收发，但不执行新指令）。
  - 执行一次自动保存。
  - 保存完成后**自动恢复**。

### 5.3 自动存档保留数量（敲定）

- 自动存档最多保留 `3` 个。
- 超出后自动删除最旧的自动存档（只删自动存档，不影响手动存档）。

---

## 6. 读取流程（读档）（强制）

1. 读取文件并反序列化为 `SaveFile`。
2. 校验必要字段存在（`meta.gameVersion`、`world.serverTick`、`world.gameDatetimeDay` 等）。
3. 执行版本判定（见第 1 节）。
4. 恢复 `WorldState` 与权威时间轴：`serverTick`、`gameDatetimeDay`、`tickInDay`。
5. 恢复 `DailySnapshot`（用于 UI 查询）。
6. 清空追帧事件缓冲并以 `serverTick` 设定新基线。
7. 构建初始 `RealtimeSnapshot` 并下发给客户端。

---

## 7. 失败处理（敲定）

- **读档失败**：提示“存档损坏/不可读”，拒绝加载。
- **版本过新**：提示“请升级版本后再加载”，拒绝加载。
- **自动保存失败**：
  - 记录结构化日志（包含存档类型、目标路径、异常栈）。
  - 解除暂停并恢复游戏（避免永久卡死）。
  - 向客户端提示“自动保存失败，请稍后重试或手动保存”。
