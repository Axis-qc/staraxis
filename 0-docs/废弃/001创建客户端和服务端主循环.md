# 001 创建客户端和服务端主循环（实现指导 / 最小可落地）

> 目标：**只做三件事**，不做任何多余功能。
>
> 1) 创建服务端主循环（Server Main Loop）
> 2) 创建客户端主循环（Client Main Loop）
> 3) 创建通讯系统（Client ⇄ Server 通讯骨架）
>
> 约束（强制）：遵循 `docx/00-通用规范与治理/核心规范.md`：
> - `serverTick`（服务端权威 tick）驱动一切权威逻辑，禁止由 FPS 驱动权威推进。
> - 服务端权威与确定性优先：相同初始状态 + 相同输入序列 => 相同输出。
> - 多线程允许，但任何权威写入必须在明确的串行化落账点执行（本任务先不实现并行计算）。
>
> 参考口径（权威来源）：
> - `docx/01-底层架构/1-最终敲定方案/00服务端主循环-实现.md`
> - `docx/01-底层架构/1-最终敲定方案/模拟时间.md`（V2：Tick 与时间推进分离）

---

## 0. 本任务明确不做什么（范围边界）

为保证“最小可跑”，本任务 **不实现**：

- 日结算（Daily Settlement）、`DailySnapshot`（上一日快照）
- 事件环形缓冲（`Event Ring Buffer`）与追帧
- 复杂指令队列（按玩家分桶、取消/覆盖等）
- 可靠层、重传、分包、压缩
- ECS、战斗/经济/AI 等任何业务模块

本任务的交付物只需要证明：
- 服务端能稳定以 25 tick/s 运行并输出 `serverTick`。
- 客户端能连接并收发最小消息：握手、`serverTick` 同步、心跳。

---

## 1. 必要字段与常量（本任务最小集）

### 1.1 服务端时间字段（来自《模拟时间.md》V2）

- `serverTick`（服务端权威 tick，用于联机对齐与确定性排序）
- `ticksPerSecond`（每秒 tick 数，固定为 `25`）
- `tickBudgetMs`（目标 tick 预算毫秒，`1000 / 25 = 40ms`）
- `timeScale`（全局时间倍率，本任务可固定 `1.0`）
- `dtGameHours`（本 tick 推进的游戏小时数，本任务只计算不使用）：
  - `baseDtGameHours`（基准小时步长）=`1/25`
  - `dtGameHours = baseDtGameHours * timeScale`

> 说明：V2 口径是 Tick 与时间推进分离。即使本任务不做结算，也应按口径保留 `dtGameHours` 计算，避免后续返工。

### 1.2 通讯最小消息字段

- `clientId`（客户端连接唯一标识，可先用随机 UUID）
- `clientSeq`（客户端递增序号，用于客户端侧自查乱序；本任务可只递增不做乱序处理）
- `serverTick`（服务端权威 tick，下发给客户端做对齐与显示）

## 2. 服务端主循环（Server Main Loop）最小实现任务

### 2.1 线程模型（最小版）

- `MainLoopThread`（主循环线程）：只负责 Tick 调度与打印日志。
- `NetThread`（网络线程）：只负责 socket 收发与消息编解码。

> 本任务不引入更多线程与并行计算。

### 2.2 Tick 阶段（最小版，仅保留结构）

服务端每 tick 按以下阶段执行（阶段名用于后续扩展，本任务阶段内只做必要工作）：

1. `PrepareTick`（准备 Tick）
   - `serverTick += 1`
   - 计算 `timeScale`（本任务固定 `1.0`）
   - 计算 `dtGameHours`（`1/25 * timeScale`）

2. `Update`（更新）
   - 本任务不做业务逻辑（留空）

3. `Commit`（落账）
   - 本任务不做权威写入（留空）

4. `PostUpdate`（更新后处理）
   - 将当前 `serverTick` 写入网络发送队列（下发给客户端）

### 2.3 Tick 调度（25 tick/s）

- 使用单调时钟（如 `System.nanoTime()`）维护 `nextTickDeadlineNs`（下一 tick 截止时间）。
- 若本 tick 提前完成则 sleep 到截止时间；若超时则不追赶、不补算，下一 tick 立即开始。

### 2.4 服务端最小验收

- [ ] 启动后持续输出：`serverTick`（服务端权威 tick）
- [ ] 在空负载下，输出频率约 `25 tick/s`
- [ ] `NetThread` 不阻塞 `MainLoopThread`（网络 I/O 不得在主循环线程执行）

## 3. 客户端主循环（Client Main Loop）最小实现任务

### 3.1 线程模型（最小版）

- `ClientMainThread`（客户端主线程）：负责 UI / 输入采集（本任务只打印日志）。
- `ClientNetThread`（客户端网络线程）：负责连接、收发、编解码。

### 3.2 客户端主循环行为（最小版）

- 以渲染帧或固定间隔运行均可，但 **不得** 用客户端循环驱动权威时间。
- 客户端只做：
  - 连接服务器
  - 接收服务端下发的 `serverTick`
  - 打印“最新 `serverTick`”
  - 定时发送 `ClientHeartbeat`（客户端心跳）

### 3.3 客户端最小验收

- [ ] 能成功连接服务端
- [ ] 控制台能持续打印最新 `serverTick`
- [ ] 断线后能提示（本任务不要求自动重连）

---

## 4. 通讯系统（最小骨架）

### 4.1 连接与握手

- 客户端连接后发送 `ClientHello`（客户端握手请求），包含：
  - `clientId`（客户端连接唯一标识）
  - `clientVersion`（客户端版本字符串，本任务可写死）

- 服务端返回 `ServerHello`（服务端握手响应），包含：
  - `serverTick`（当前服务端权威 tick）
  - `serverVersion`（服务端版本字符串）

### 4.2 Tick 同步（最小版）

- 服务端每 tick 发送 `ServerTick`（tick 同步消息），包含：
  - `serverTick`（服务端权威 tick）

- 客户端收到后更新本地 `lastServerTick`（客户端最后收到的权威 tick）并打印。

### 4.3 心跳

- 客户端定时发送 `ClientHeartbeat`，包含：
  - `clientSeq`（客户端递增序号）
  - `clientTimeMs`（客户端本地时间毫秒，仅用于链路观测；不得参与权威逻辑）

- 服务端可选返回 `ServerHeartbeatAck`，包含：
  - `serverTick`（服务端权威 tick）
  - `clientSeq`（回显客户端序号）

### 4.4 编解码与消息边界

- 本任务允许使用任意简化编码（例如 JSON 行协议 / length-prefix 二进制），但必须做到：
  - 消息可区分类型（例如 `type`（消息类型）字段）
  - 每条消息有明确边界（避免粘包/半包）
