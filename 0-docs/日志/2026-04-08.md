# AGENTS 工作日志

## 2026-04-08：前端视觉计算迁移方案 - 降低后端移动计算压力

### 📋 项目概述
用户希望将舰船移动的视觉计算完全转移到前端，以降低后端计算压力。后端只需知道单位位置、当前指令和目的地，根据实体移动速度推测路径。如果中途变更指令，根据上次指令发出后的移动时间计算出当前位置，然后开始新的指令计算喵。

**核心思想**：前端进行完整的60Hz视觉计算，后端只存储移动指令和进行简化验证，大幅降低计算压力喵。

### 🔍 问题分析
当前架构中，`ShipMovementSystem.java` 在每个 tick（20Hz）对每艘舰船执行完整的物理计算，包括：
- 舰首朝向更新
- 移动方向与舰首夹角计算
- 速度惩罚（正向/侧向/反向）
- 加速度和减速计算
- 位置更新

对于1000艘舰船，这会产生每秒约6万次三角函数调用的高计算负载喵。

### 🎯 目标
- **前端**：完整复制移动算法，进行流畅的视觉模拟
- **后端**：简化计算，只进行指令存储和路径推测
- **协调机制**：前端预测与后端权威状态对齐
- **误差容忍**：< 1.0GU（用户选择）

### 🚀 实施方案

#### 阶段1：前端移动计算引擎（1周）
1. **复制移动算法**：创建 `ShipMovementSystemFrontend.ts`，完整移植 `ShipMovementSystem.java` 的逻辑喵。
2. **集成渲染系统**：修改 `shipRenderer.ts`，添加预测状态，每帧调用前端移动系统喵。
3. **时间同步**：创建时间管理系统，跟踪后端 `simulationTick` 和 `totalGameSeconds`喵。

#### 阶段2：后端简化计算（2天）
1. **重构 `ShipMovementSystem.java`**：移除每tick的完整物理计算，改为基于指令的推测算法喵。
2. **指令存储系统**：创建 `MovementCommand` 类，存储指令参数和起始状态喵。
3. **验证机制**：定期验证实体位置是否在合理范围内，防作弊检查喵。

#### 阶段3：协调机制（4天）
1. **偏差检测**：前端比较预测位置与快照中的权威位置喵。
2. **纠正机制**：实现平滑纠正算法，避免视觉跳跃喵。
3. **通信协议增强**：在快照中添加 `movementCommand` 字段喵。

#### 阶段4：测试与优化（3天）
1. **算法一致性测试**：确保前后端相同输入产生相同输出喵。
2. **性能测试**：模拟1000艘舰船场景，测量CPU使用率变化喵。
3. **网络测试**：模拟不同网络延迟，验证纠正机制鲁棒性喵。

### 🔧 技术挑战与解决方案

#### 挑战1：算法一致性
- **问题**：Java和TypeScript的浮点数计算可能产生微小差异喵。
- **解决方案**：使用相同的算法实现逐行移植，设置容忍阈值（0.001GU），将物理参数提取到共享配置喵。

#### 挑战2：时间同步
- **问题**：前端需要精确知道每个tick的游戏时间流逝喵。
- **解决方案**：后端广播 `totalGameSeconds` 和 `deltaGameSeconds`，前端使用 `performance.now()` 进行微秒级插值喵。

#### 挑战3：网络延迟
- **问题**：命令发送到执行有延迟，前端预测可能偏差喵。
- **解决方案**：前端使用客户端时间立即开始预测，后端记录命令接收时间计算补偿喵。

### ⚠️ 风险评估与缓解

#### 风险1：预测偏差累积
- **描述**：微小计算差异随时间累积导致大偏差喵。
- **缓解**：定期权威计算（每5tick）重置偏差喵。

#### 风险2：网络不稳定
- **描述**：高延迟或丢包导致纠正频繁喵。
- **缓解**：自适应纠正策略，网络差时放宽阈值喵。

#### 风险3：浏览器性能
- **描述**：低端设备无法处理1000个单位计算喵。
- **缓解**：动态调整计算频率，添加性能监控喵。
