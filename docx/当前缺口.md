### P0-1：时间推进/跨日规则与 `timeScale`（全局时间倍率）口径矛盾（已修订文档口径）

- **问题**
  - 文档同时定义：
    - `dtGame`（游戏时间步长）= `baseDtGame * timeScale`，且宣称“现实 1 秒推进游戏 `timeScale` 小时”。
    - 但跨日触发使用 `tickInDay += 1` 与固定 `ticksPerDay = 25 * 3600 * 24`（2160000）判断。
  - 这会导致：
    - 跨日/日结算与 `timeScale` 无关（永远现实 24 小时才跨日）。
    - UI 的 `gameHour`（游戏小时）解析也退化为现实时间口径。
- **违反/关联规范**
  - 《核心规范.md》6：模拟驱动（推进必须由 `serverTick` / `simulationDay` 驱动，且时间口径必须一致）
  - 《核心规范.md》10：具体实现文档必须“可执行”（当前存在互相冲突的可执行规则）
- **影响**
  - 日结算触发时刻、经济系统账本节奏、回放/对账都会与预期不一致。
  - 任何实现者按不同段落实现会得到不同游戏时间语义，导致不可验收。
- **建议补齐（需要在文档中敲定一种）**
  - **方案 A（推荐）**：跨日由“累计游戏时间”驱动
    - 维护 `gameTimeAcc`（累计游戏时长，建议定点/整数单位，例如“游戏秒/游戏毫秒/游戏分钟”）。
    - 每 tick：`gameTimeAcc += dtGame`；当 `gameTimeAcc >= 24h` 时跨日（允许一次跨多日：循环扣减 24h）。
    - `tickInDay`（当日 tick 计数）仅作为“UI/调试计数器”或直接改为 `gameTimeInDay`（当日累计游戏时间）。
  - **方案 B**：跨日固定 tick 计数驱动（则必须修改“现实 1 秒推进游戏 X 小时”的定义，明确 `timeScale` 只影响局部系统推进，不影响日历/结算）。
- **验收标准**
  - 在 `timeScale=1.0` 下，现实时间与游戏时间换算与文档宣称一致（给出一组可复算样例）。
  - 调整 `timeScale` 后，跨日与日结算触发点随之成比例变化（或明确不变化）。

### P0-2：Tick 调度/超预算策略缺失（导致无法实现“禁止追帧补算/不跳步”）（已敲定折中口径，待实现）

- **问题**
  - 文档要求：25 tick/s（40ms），并写明“禁止通过跳步或追帧补算来追赶进度”。
  - 但未定义当 `tickCostMs`（每 tick 耗时）> `tickBudgetMs` 时：
    - 主循环如何调度下一 tick（sleep/不 sleep/如何计算 deadline）。
    - 是否允许 tick 频率降低（现实时间节拍变慢），以及如何与 `timeScale`（时间膨胀）协同。
- **违反/关联规范**
  - 《核心规范.md》7：多核与性能（要求“度量驱动”，需要明确超预算的控制策略与指标闭环）
  - 《核心规范.md》10：可执行性（当前缺少可直接实现的调度规则）
- **影响**
  - 实现者会在“保持 25 tick/s”与“禁止跳步/追赶”之间做出不一致选择，导致行为不确定。
  - 超预算时可能出现事件/快照/队列内存爆炸。
- **建议补齐**
  - 明确“主循环调度器”规则：
    - 采用 `nextTickDeadlineNs`（下一 tick 截止时间）模型。
    - 若本 tick 超时：不追赶、不补算；允许现实 tick 变慢（即主循环尽快开始下一 tick，不 sleep）。
  - 明确“时间膨胀控制器”与生效时机：
    - `systemCapScale`（系统强制倍率上限）基于过去 N tick 的 `tickCostMs/tickBudgetMs` 计算。
    - 设定滞回：连续超预算 K 次降档，连续低于阈值 M 次升档。
- **验收标准**
  - 人为注入 2 倍负载后：
    - tick 不跳步、`serverTick` 仍逐 tick 递增。
    - `timeScale` 按规则下降并稳定，不出现剧烈抖动。

### P1-1：`systemCapScale`（系统强制倍率上限）与“档位钳制/取整”规则不完整（历史记录：该文件会被覆盖，最终口径已写入主循环文档）

- **敲定口径**
  - 玩家手动调速 `playerScale`（玩家调速倍率）只允许来自预设档位集合（`0.1, 0.25, 0.5, 0.75, 1.0, 2.0, 3.0, 4.0`）。
  - 系统强制倍率上限 `systemCapScale`（系统强制倍率上限）允许以 `0.01` 为最小单位精确调节（区间钳制 `[0.1, 4.0]`）。
  - 取整策略（敲定）：`systemCapScale` **向下取整到 0.01**（保守降速，确保“降速足够”）。
  - 合成顺序（敲定）：
    - `timeScaleRaw = min(playerScale, skillScaleGlobal, systemCapScale)`
    - `timeScale = clamp(timeScaleRaw, 0.1, 4.0)`（最终 `timeScale` **不再强制向玩家档位取整**）。

- **推导公式（最小可落地）**
  - `rawCap = tickBudgetMs / tickCostMs`
  - `rawCapClamped = clamp(rawCap, 0.1, 4.0)`
  - `systemCapScale = floorToCent(rawCapClamped)`（向下取到 0.01）

- **可复算样例（用于验收）**
  - 前提：`tickBudgetMs = 40ms`，`playerScale = 1.0`，`skillScaleGlobal = 1.0`。
  - `tickCostMs = 50ms`：
    - `rawCap = 40/50 = 0.80`
    - `systemCapScale = 0.80`
    - `timeScale = min(1.0, 1.0, 0.80) = 0.80`
  - `tickCostMs = 40ms`：
    - `rawCap = 40/40 = 1.00`
    - `systemCapScale = 1.00`
    - `timeScale = 1.00`
  - `tickCostMs = 60ms`：
    - `rawCap = 40/60 = 0.666...`
    - `systemCapScale = 0.66`（向下取整到 0.01）
    - `timeScale = 0.66`

- **关联规范**
  - 《核心规范.md》7：度量驱动（倍率调整必须可量化、可复算、可验收）

### P1-2：日结算并行 Draft 的任务状态机缺失（跨日/失败/重试/队列）

- **问题**
  - 文档定义了两段式输出（`DailySettlementDraft` 后台线程 + `DailySettlementDelta` 主线程落账），但缺少：
    - 一次 tick 跨多日时的处理策略（是否循环结算/是否拆分到多 tick）。
    - draft 任务的生命周期状态（Idle/Computing/ReadyToCommit/Failed）。
    - 失败后 `DailyAccumulator`（日内累计器）是否清零、是否重试、如何避免重复结算/数据丢失。
- **关联规范**
  - 《核心规范.md》2：确定性模拟（结算重试/幂等必须明确，否则可能重复落账）
  - 《核心规范.md》10：可执行性
- **建议补齐**
  - 增加“日结算调度与状态机”小节：
    - `settlementTargetDay`（待结算日序号）、`draftForDay`（草稿对应日）、`draftStatus`（草稿状态）。
    - 明确失败重试策略与最大重试次数/运维开关。
- **验收标准**
  - 人为让结算在 Draft 阶段抛错：
    - `dailyRef` 不切换。
    - 下一个跨日到来时行为确定（重试/跳过/暂停）且有结构化日志。

### P1-3：事件环形缓冲缺少“体积上限/退化策略/确定性排序”

- **问题**

- **关联规范**
  - 《核心规范.md》2：确定性模拟（顺序必须稳定）
  - 《核心规范.md》7：性能（背压与上限必须明确）
- **验收标准**
  - 构造极端事件风暴时：
    - 缓冲区不会无上限增长。
    - 客户端能得到明确的 `resultType`（Events/Snapshot）与 `reasonCode`。
