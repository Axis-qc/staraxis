# 联机语义落地 - 具体实现文档（TCP 控制通道 + UDP 数据通道）

> 本文档为“可直接照做”的实现说明，属于 `docx/01-底层架构/具体实现`。
>
> **目标**：为 `同步模型与指令口径.md` 提供可直接落地的 Java 实现方案：
> 
> - **TCP** 用于：登录/握手、会话控制、心跳、投票/暂停/踢出、重连协商等 **控制流**。
> - **UDP** 用于：指令/事件/快照等 **高频数据传输**。
> - 定义可实现的 **发包/解包策略**（分包、序号、ACK/重传、乱序窗口、带宽与优先级）。
> - 定义 **掉线/超时处理**：踢出、暂停游戏、等待重连或由在场玩家选择继续推进。
> - **世界快照模型**：服务端保存全量世界快照；客户端请求“基本数据 + 兴趣范围数据”，并在推进过程中切换/增量订阅。
>

## 0. 设计原则（落地约束）

- **权威写状态只在服务端主循环线程内发生**：网络线程只做解析、校验、排队，不得直接改 `WorldState`。
- **协议分层**：
  - 传输层：TCP / UDP
  - 可靠层（仅 UDP 需要）：序号、ACK、重传、乱序重排
  - 语义层：Command/Ack/Event/Snapshot 与 reconcile
- **最小闭环优先**：先保证指令可达（至少语义可靠），再逐步优化弱一致通道（如轨迹/表现）。

## 1. 通道划分（TCP 控制通道 / UDP 数据通道）

### 1.1 TCP 控制通道（可靠、有序）

用于低频但必须可靠的消息：

- 会话建立/鉴权/握手（含 UDP 端口绑定）
- 心跳与连接健康
- 玩家掉线通知
- 暂停/继续推进的投票与决策
- 重连协商（请求快照/追帧）
- 管理命令（踢出/封禁/限流告警）

### 1.2 UDP 数据通道（低延迟，需自研可靠层）

用于高频消息：

- Commands（客户端 → 服务端）：**建议走可靠 UDP**（语义层必须可靠/幂等）
- Events（服务端 → 客户端）：**建议走可靠 UDP**（避免丢事件导致状态漂移）
- Snapshots（服务端 → 客户端）：可靠 UDP（大包需要分片）
- 弱一致表现（可选）：不可靠 UDP（例如轨迹/镜头提示），丢了无所谓

## 2. 会话建立与 UDP 绑定（TCP 握手流程）

> 目标：在 NAT 场景下让服务端知道“该玩家的 UDP 外网地址/端口”，并与 TCP 会话绑定。

### 2.1 客户端流程（建议）

1. 客户端建立 TCP 连接并鉴权（token/账号等）
2. 客户端本地创建 UDP socket（随机端口）
3. 客户端通过 TCP 发送 `ConnectRequest`：包含 `playerId`、`clientId`、`udpLocalPort`（仅用于调试）
4. 服务端回 `ConnectAck`：包含服务端 UDP 端口、会话参数（心跳间隔、超时阈值、窗口大小等）
5. 客户端向服务端 UDP 端口发送 `UdpHello`（带 `sessionId`/`nonce`）
6. 服务端收到 `UdpHello` 后记录 `udpRemoteAddress:port` 绑定到该 `playerId` 会话，并回 `UdpHelloAck`

### 2.2 服务端会话结构（建议）

```java
public final class PlayerSession {
    public final String playerId;
    public final String clientId;

    // TCP
    public volatile long lastTcpHeartbeatAtMs;

    // UDP
    public volatile InetSocketAddress udpRemote;
    public volatile long lastUdpPacketAtMs;

    // 顺序与幂等（语义层）
    public volatile long lastAcceptedClientSeq;

    // 连接状态
    public volatile SessionState state; // CONNECTED / DISCONNECTED / RECONNECTING

    public PlayerSession(String playerId, String clientId) {
        this.playerId = playerId;
        this.clientId = clientId;
    }
}

public enum SessionState {
    CONNECTED,
    DISCONNECTED,
    RECONNECTING
}
```

## 3. UDP 发包/解包策略（分片、序号、ACK、重传、乱序窗口）

### 3.1 包头（统一 Header）

> 说明：UDP 是数据报，有消息边界；但需要自定义 header 来做可靠传输。

```java
public final class UdpHeader {
    public int protocolVersion;
    public long sessionId;

    public long packetSeq;   // 本端发送序号（单调递增）
    public long ackSeq;      // 已收到对端的最大连续 seq
    public long ackBits;     // ack 位图：表示 ackSeq 往前 64 个包是否收到（用于批量确认）

    public int flags;        // RELIABLE / FRAGMENT / CONTROL 等
    public int msgType;      // COMMAND / EVENT / SNAPSHOT / ACK_ONLY ...

    public int payloadLength;
    public int crc32;        // 可选：快速校验
}
```

### 3.2 分片（Fragmentation）

> UDP 单包建议控制在 MTU 内（典型 1200 字节左右更稳，避免 IP 层分片）。

- 若 `payloadLength > MTU_PAYLOAD_LIMIT`：
  - 将 payload 切分为 N 片
  - 每片带 `fragmentId`、`fragmentIndex`、`fragmentCount`
  - 接收端缓存分片，齐了再组装成完整消息
  - 分片缓存必须有 TTL，避免内存泄漏

### 3.3 可靠层（ACK/重传）

- 发送端：
  - 对 `RELIABLE` 包分配 `packetSeq`
  - 放入 `pendingReliablePackets`（包含 `sentAtMs`、`retryCount`）
  - 若在 `resendTimeoutMs` 内未被 ack，则重传（指数退避/上限次数）

- 接收端：
  - 维护 `lastReceivedSeq` + 位图窗口
  - 收到包就更新 ack 位图
  - 定期回 ACK（可 piggyback 在业务包头里，也可发 `ACK_ONLY` 包）

### 3.4 乱序窗口

- 对可靠消息：允许窗口内乱序到达并缓存（例如 64～256 个包）
- 超出窗口：丢弃并记为 `OutOfWindow`（必要时触发重连/快照）

## 4. Commands（客户端 → 服务端）的接收管线（实现口径）

> **关键点**：UDP 可靠层保证“尽量到达”，语义层仍必须 **幂等**（`cmdId`）与 **按序**（`clientSeq`）。

### 4.1 依赖（建议）

- `CommandQueue`：主循环消费队列（线程安全）
- `processedCmdIdCache`：幂等缓存（Caffeine）
- `PlayerSessionManager`：会话与 last seq
- `Serializer`：Protobuf（或 KryoNet MVP）

### 4.2 处理流程（网络线程）

```java
public final class CommandIngestService {
    private final CommandQueue commandQueue;
    private final Cache<String, CommandAck> processedCmdIdCache;
    private final PlayerSessionManager sessionManager;
    private final UdpSender udpSender;

    public void onUdpCommandPacket(InetSocketAddress remote, byte[] bytes) {
        // 1) 解包：UdpHeader + payload
        // 2) 找 session：remote -> session（或 payload 内 sessionId）
        // 3) 反序列化 Command
        // 4) 基础校验（playerId/字段范围）
        // 5) 幂等：cmdId 命中则直接回发上次 ack
        // 6) 顺序：clientSeq <= lastAcceptedClientSeq 则丢弃/重发 ack
        // 7) 入队：commandQueue.enqueue(cmd)
        // 8) 生成 Ack(ACCEPTED/REJECTED/DEFERRED) 并通过 UDP 回发
    }
}
```

## 5. 服务端 → 客户端：事件/快照发送策略

### 5.1 Events（增量）

- 建议 **可靠 UDP**
- 事件必须带 `serverTick`、`eventId`，并可选 `causedByCmdId`
- 客户端可基于 `serverTick` 排序应用

### 5.2 Snapshots（快照）

- 用于：首次进入、重连、严重分歧、追帧窗口过期
- 必须支持分片 + 可靠传输
- 可设计 `SnapshotManifest`（清单小包）+ `SnapshotChunk[]`（分片大包）

## 6. 超时/掉线：踢出、暂停、等待重连或继续推进

本节落地你在 `游戏循环与模拟推进.md` 第 6 节的口径。

### 6.1 判定掉线（建议参数）

- TCP 心跳间隔：`heartbeatIntervalMs = 1000`
- 判定掉线阈值：连续 `missedHeartbeats >= 3` 或 `noUdpPacketMs >= 3000`

### 6.2 掉线处理（服务端）

1. 标记玩家 `DISCONNECTED`
2. 广播控制消息（TCP）：`PlayerDisconnected(playerId)`
3. 进入“联机暂停点”（暂停主循环推进或冻结推进）
4. 进入等待窗口（例如 30 秒）

### 6.3 等待窗口内的两种结果

- **玩家重连成功**：
  - 走 TCP 重连协商（`ReconnectRequest(lastKnownServerTick, lastAckedClientSeq)`）
  - 服务端决定：追帧（发缺失 Events）或发 Snapshot
  - 广播（TCP）：`GameResumed`

- **其他玩家选择继续推进**：
  - 走 TCP 投票/房主决策：`ContinueVote`
  - 服务端解除暂停继续推进
  - 缺席玩家处理策略：托管/冻结/AI 接管（需另文档定稿）

### 6.4 踢出规则

- 等待窗口结束仍未重连：
  - 服务端发送（TCP）：`PlayerKicked(playerId, reason=Timeout)`
  - 从会话与联机房间移除

## 7. 依赖与核心需求（Java 生态建议）

> 你选择的方向是 **TCP 建连 + UDP 传输**。这里给一套可落地依赖组合（不强绑定，方便替换）。

- TCP：
  - 推荐：Netty（成熟、可观测）
- UDP：
  - 推荐：Netty DatagramChannel（统一线程模型与 pipeline）
- 序列化：
  - 推荐：Protobuf（协议演进更安全）
- 缓存：
  - 推荐：Caffeine（幂等 cmdId、去重窗口、分片缓存 TTL）
- 日志：
  - SLF4J + Logback

## 8. 验收清单（最小闭环）

- [ ] TCP 连接建立成功后，UDP `UdpHello` 能绑定到同一 `PlayerSession`
- [ ] UDP 可靠层：丢包 10% 情况下 Commands 仍能最终到达并 Ack
- [ ] 幂等：重复发送同一 `cmdId` 不会重复执行
- [ ] 乱序：`clientSeq` 乱序时不会导致执行顺序错乱
- [ ] 断线重连：在追帧窗口内能追帧，超窗能发快照恢复
- [ ] 掉线：触发暂停点，重连/继续推进/超时踢出都按口径执行

## 9. 世界快照模型（服务端全量保存 / 客户端按需请求）

> 你选择的口径是 **B**：服务端保存全量世界快照；客户端请求“基本数据 + 兴趣范围数据”，并随着推进持续请求更新。

### 9.1 三类快照

- **全量快照 `WorldSnapshot`（服务端持久化）**
  - 用途：存档/断线恢复/运维回滚/严重分歧强制对齐
  - 内容：全世界权威状态（强一致字段为主，必要索引）
- **分区快照 `ShardSnapshot`（服务端可选持久化/内存缓存）**
  - 用途：按星区/分片加载，降低快照生成成本
  - 内容：该分片内权威状态 + 跨分片必要引用的摘要
- **兴趣范围快照 `InterestSnapshot`（服务端按需生成，仅下发）**
  - 用途：客户端进入/切换视角时获取“可用最小状态集”
  - 内容：客户端当前兴趣范围内的实体与必要依赖（如目标行星、舰队、订单面板等）

### 9.2 快照一致性锚点（必须字段）

- `snapshotId`：快照唯一 ID（可用 UUIDv7/雪花/哈希）
- `serverTick`：该快照对应的权威 tick
- `simulationDay`：该快照对应的模拟日
- `schemaVersion`：快照结构版本（用于存档迁移/兼容）
- `worldId`：世界/存档 ID

### 9.3 快照内容边界（建议）

- **必须包含**：
  - 权威实体状态（强一致字段）
  - 玩家/派系与权限相关状态
  - 与客户端 UI/交互直接相关的聚合摘要（可选，但要明确可重建与否）
- **不建议包含**（可重建缓存）：
  - 路径缓存、渲染缓存、派生可再算的临时数据

## 10. 服务端：快照生成、存储、加载

### 10.1 生成时机（建议）

- 周期性全量快照：例如每 `N` 个 `simulationDay` 或每 `M` 分钟
- 关键时刻快照：
  - 版本升级前后
  - 运维手动触发
  - 严重分歧（hash 不一致）
  - 追帧窗口过期且客户端需要强制对齐

### 10.2 存储结构（Manifest + Chunk）

- `SnapshotManifest`（小包/可落盘索引）：
  - `snapshotId/serverTick/simulationDay/schemaVersion/worldId`
  - `chunkCount/chunkSize`
  - `hash`（全量 hash）
  - `compression`（none/lz4/zstd）
- `SnapshotChunk[i]`（分片大包）：
  - `snapshotId`
  - `chunkIndex`
  - `payloadBytes`
  - `crc32`

### 10.3 建议序列化与压缩

- 序列化：Protobuf（严格 schema）
- 压缩：优先 LZ4（解压快）或 Zstd（压缩率高）

### 10.4 InterestSnapshot 的生成（服务端按需）

- 输入：`InterestSpec`（兴趣范围定义，见第 11 节）
- 输出：只包含兴趣范围实体 + 必要依赖（跨域引用用摘要或补齐实体）

## 11. 客户端：快照请求与推进更新请求

### 11.1 InterestSpec（兴趣范围定义）

客户端请求“基本数据 + 兴趣范围数据”时，必须带兴趣范围：

- 视角中心：`focus`（星区/恒星系/行星/舰队等）
- 半径：`R`（星区环数/距离阈值）
- 订阅类型：需要哪些面板数据（经济/外交/战斗摘要等）

### 11.2 首次进入（请求基本数据）

- TCP：`EnterWorldRequest(playerId, worldId, interestSpec)`
- 服务端响应：
  - 优先下发 `InterestSnapshot`（UDP 可靠 + 分片）
  - 随后开始持续推送 Events

### 11.3 推进过程中更新请求

- 当玩家切换视角/打开新面板：
  - TCP 或 UDP（可靠）发送：`UpdateInterestRequest(newInterestSpec)`
- 服务端处理：
  - 回 `InterestSnapshot`（补齐新增范围内实体）
  - 对离开兴趣范围的实体，服务端不再推送其事件（或只推摘要）

### 11.4 重连/追帧/快照三选一

客户端重连时发送：

- `ReconnectRequest`：
  - `lastKnownServerTick`
  - `lastAckedClientSeq`
  - `lastAppliedEventId`（或 `lastAppliedServerTick`）
  - `interestSpec`

服务端决策：

- 能追帧：补发缺失 Events
- 追帧失败/超窗：发 `InterestSnapshot` 或全量 `WorldSnapshot` 的子集

## 12. 客户端“修改指令”核心逻辑（发送、重发、Ack、预测边界）

> 核心目标：客户端只能表达意图，最终以服务端落账为准。

### 12.1 必备字段

- `cmdId`：全局唯一（UUIDv7 推荐）
- `clientSeq`：单连接递增
- `expectedServerTick`（可选）：期望执行 tick（用于降低抖动）

### 12.2 发送与重发策略（建议）

- 指令通过 **UDP 可靠通道** 发送（底层可靠层负责 packetSeq/ack/重传）
- 语义层仍需：
  - `pendingCommands` 队列（按 clientSeq）
  - 超时未收到 `CommandAck`：重发同一 `cmdId`

### 12.3 收到 Ack 的处理

- `Accepted`：
  - 标记该 cmd 已确认
  - 等待对应 Events（可通过 `causedByCmdId` 关联）更新权威展示
- `Rejected`：
  - 移除 pending
  - 回滚预测（如果有）
  - UI 提示 `reasonCode`

### 12.4 预测边界（强制口径）

- 允许预测：UI 状态、路径预览、镜头反馈
- 不允许预测（或只能灰态）：资产扣减、战斗命中/伤害等强一致结果

- [ ] 服务端能生成并落盘 `WorldSnapshot`（带 schemaVersion 与 hash）

- [ ] 客户端切换兴趣范围能触发 `UpdateInterestRequest` 并补齐数据
- [ ] 重连时服务端能在“追帧/快照”之间正确选择
- [ ] 指令发送：丢包/乱序下仍能最终收到 Ack 且不重复执行

## 14. 快照字段清单（最小可用版）

> 目标：把快照从“概念”推进到“可以开始写 Protobuf schema”。此处是**最小可用**字段集：只保证客户端能跑起来与对账；更丰富内容按系统逐步加。

### 14.1 WorldSnapshot（全量，服务端落盘）

- **Header**
  - `snapshotId`
  - `worldId`
  - `schemaVersion`
  - `serverTick`
  - `simulationDay`
  - `createdAtMs`
  - `hash`（全量 hash，可选）

- **Core State（最小可用）**
  - `players[]`：玩家/连接归属（playerId、factionId、权限域摘要）
  - `factions[]`：派系状态（外交状态摘要、主要资源摘要）
  - `globalTime`：时间推进相关（serverTick、simulationDay、timeScale 等）

- **World Structure（最小可用）**
  - `sectors[]`：星区（sectorId、坐标、类型、seed 引用）
  - `systems[]`：恒星系（systemId、sectorId、seed/类型）
  - `planets[]`：行星（planetId、systemId、类型、关键数值摘要）

- **Dynamic Entities（最小可用）**
  - `fleets[]`：舰队（fleetId、ownerFactionId、GlobalPosition、速度/航线摘要）
  - `ships[]`（可选，若舰队内细节不下发则可不含）

- **Economy（最小可用）**
  - `accounts[]`：资产/库存账本（强一致字段）
  - `orders[]`（可选：若订单市场需要在客户端可见）

- **Indices（为了客户端装载效率）**
  - `indexPlanetBySystem`（planetId 列表）
  - `indexFleetByFaction`（fleetId 列表）

> 注：WorldSnapshot 字段集必须与 `03-核心机制/存档与版本迁移.md` 的 schemaVersion/迁移策略对齐。

### 14.2 InterestSnapshot（兴趣范围，下发给客户端）

- **Header**
  - `snapshotId`
  - `worldId`
  - `schemaVersion`
  - `serverTick`
  - `simulationDay`
  - `interestSpecHash`（用于客户端确认当前兴趣范围）

- **Basic（必带）**
  - `selfPlayer`（playerId/factionId）
  - `globalTime`（serverTick/simulationDay/timeScale）

- **Entities（按兴趣范围裁剪）**
  - `sectors[]/systems[]/planets[]`（只包含兴趣范围内或 UI 需要的）
  - `fleets[]`（兴趣范围内 + 玩家相关）
  - `uiPanels`（可选：面板摘要数据，明确是否可重建）

## 15. 追帧窗口与事件缓冲（Catch-up / Event Buffer）

### 15.1 事件环形缓冲（服务端）

- 服务端维护 `EventRingBuffer`：按 `serverTick` 递增追加。
- 每条 Event 必须带：`eventId`、`serverTick`、`simulationDay`、（可选）`causedByCmdId`。

建议结构：

```java
public final class EventRingBuffer {
    private final BaseEvent[] ring;
    private final int capacity;

    private long firstTick; // ring[0] 对应的 serverTick
    private long lastTick;  // 当前最后一个 serverTick

    public synchronized void append(long serverTick, BaseEvent event) {
        // 写入 ring[(serverTick % capacity)]，并更新 firstTick/lastTick
    }

    public synchronized List<BaseEvent> getRange(long fromTickExclusive, long toTickInclusive) {
        // 若 fromTick < firstTick 则说明超窗
        return List.of();
    }

    public synchronized boolean isInWindow(long fromTickExclusive) {
        return fromTickExclusive >= firstTick;
    }
}
```

### 15.2 窗口大小建议

- 以“允许重连追帧的最长时间”来定：例如 30 秒
- 若 tick=20Hz：30 秒≈600 tick
- 若每 tick 平均事件量大，容量可按“事件条数”而不是 tick 数设计（但必须可按 tick 回放）

### 15.3 超窗判定与切换策略

- 客户端发送 `ReconnectRequest(lastAppliedServerTick)`
- 服务端：
  - 若 `EventRingBuffer.isInWindow(lastAppliedServerTick)`：返回缺失 events
  - 否则：返回 `InterestSnapshot`

### 15.4 断点续传（快照分片）

- 客户端在接收 `SnapshotManifest` 后，若缺失 chunk：
  - 发送 `SnapshotChunkRequest(snapshotId, missingChunkIndexes[])`
- 服务端补发缺失 chunks

## 16. 客户端修改指令闭环（更细的落地清单）

### 16.1 客户端本地队列

- `pendingCommands`：未收到 Ack 的指令（按 clientSeq 排序）
- `lastAckedClientSeq`：最近确认序号

### 16.2 超时重发

- 若 `ackTimeoutMs`（如 300ms~1000ms）未收到 Ack：重发同 cmdId
- 重发次数上限：例如 5 次；超过触发重连/请求快照

### 16.3 与事件对齐

- 服务端事件建议带 `causedByCmdId`
- 客户端收到事件后：
  - 若属于某 cmdId，则可标记该 cmd 的“结果已到账”

### 16.4 预测/回滚最小口径

- 预测：只改 UI 与渲染态（不改权威账本）
- 收到 Rejected：撤销 UI 状态并提示
