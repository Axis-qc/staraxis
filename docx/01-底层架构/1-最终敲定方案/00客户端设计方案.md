# 客户端设计方案（最终敲定草案，可直接落地）

> 本文档目标：给出一套**可直接实现**的 StarAxis 客户端架构方案。
>
> 设计约束（强制）：
> - **服务端权威**：客户端不决定任何权威结果，只做输入采集、视觉表现、预测与平滑。
> - **客户端预测口径**：当前采用《客户端预测与平滑处理.md》定义的 **“仅视觉预测 + 权威硬对齐（Correction Warp）”**。
> - **UI 独立系统（强制）**：UI 必须是独立系统，界面在加载期完成创建（预构建），运行时只做数据绑定/状态切换，禁止“运行时临时拼 UI”。
>
> 参考：
> - `docx/01-底层架构/客户端/客户端预测与平滑处理.md`
> - `docx/00-通用规范与治理/核心规范.md`

---

## 0. 客户端在整体架构中的位置

客户端仅做三件事：

1. **输入采集**：把玩家操作编码为 `Command`（客户端意图指令）并可靠发送。
2. **状态表现**：把服务端下发的 `Event`（权威事件增量）/`Snapshot`（权威状态快照）转换为本地可渲染状态。
3. **视觉预测与平滑**：为减少卡顿，对位置等视觉量做外推；收到权威数据后做对账与纠正。

> 客户端不参与：
> - 权威战斗结算、经济结算、随机判定、资产变更等所有结果。

---

## 1. 客户端分层（强制）

客户端代码必须按以下层次组织（禁止跨层访问内部状态）：

- **Net Layer（网络层）**
  - 负责连接管理、收发包、可靠通道、消息反序列化。
  - 输出：已解析的 `ServerMessage`（服务端消息）。

- **Sync Layer（同步层）**
  - 负责：
    - 维护 `serverTick`（服务端权威 tick）进度
    - 事件追帧与快照切换
    - 本地“权威视图缓存”（只读）
  - 输出：`AuthorityFrame`（权威帧：某个 tick 的权威增量/快照）。

- **Sim View（模拟视图层，非权威）**
  - 负责把 `AuthorityFrame` 应用到客户端侧的**只读展示模型**：`SimulatedState`（展示用模拟态）。
  - 注意：这里的“模拟态”只是为了 UI/渲染方便，不是权威模拟。

- **Render Layer（渲染层）**
  - 维护 `RenderState`（表现态），基于 `SimulatedState` 做视觉预测/平滑后渲染。

- **UI System（UI 独立系统）**
  - 独立于渲染世界对象的 HUD/面板系统。
  - 通过订阅数据源（`DailySnapshot`、选择态、玩家态等）更新 UI。

---

## 2. 双状态模型：SimulatedState 与 RenderState（强制）

### 2.1 SimulatedState（展示用模拟态）

- 来源：仅由服务端权威 `Event`/`Snapshot` 驱动更新。
- 用途：
  - 作为 UI/渲染的“数据源”。
  - 提供实体的最新权威位置、速度、血量摘要、阵营等。
- 禁止事项：
  - 禁止在 SimulatedState 内做任何会影响结果的逻辑推演（例如本地战斗结算）。

### 2.2 RenderState（表现态）

- 来源：
  - 权威输入：`SimulatedState` 的最新权威数据。
  - 本地预测：用于渲染的“预测位置/朝向”等。
- 用途：
  - 只服务于画面流畅，不对外提供任何权威语义。

## 3. 客户端预测与平滑（V1：仅视觉预测 + 硬对齐）

> 本节口径完全继承《客户端预测与平滑处理.md》，并明确它在客户端架构中的落点。

### 3.1 适用范围（强制）

- 当前只对**位置类**视觉数据做预测：`posGU`（GU 单位坐标）。
- 预测输入来自：
  - `SnapshotMsg.velGUPerTick`（服务端估计速度，可选）
  - 或本地已知的上一帧/上一 tick 速度

### 3.2 核心规则（强制）

- 收到权威 `SnapshotMsg` 后：
  - `predictedPos = authorityPos`（立即对齐，无插值）
- 渲染帧更新时：
  - 可以根据 `velGUPerTick` 外推 `predictedPos`
- 偏移超过阈值：
  - 触发 `Correction Warp`（纠正平移），再次硬对齐到权威位置

### 3.3 最小数据结构（引用口径）

```ts
interface SnapshotMsg {
  tick: number;            // 权威 tick
  id: string;              // 实体唯一 ID
  posGU: Vector3d;         // GU 单位权威坐标
  velGUPerTick: Vector3f;  // 可选：服务端估计速度，供预测使用
}

interface PredictState {
  lastAuthorityTick: number;
  lastAuthorityPos: Vector3d;
  predictedPos: Vector3d;   // 当前帧用于渲染的坐标
}
```

## 4. 与服务端同步的输入/输出口径（可直接落地）

### 4.1 客户端发送 Command（客户端意图指令）

- 客户端在本地为每个玩家维护 `clientSeq`（客户端递增序号，用于乱序/丢包检测）。
- 每条 `Command` 必须携带：
  - `cmdId`（指令唯一 ID，用于幂等/去重/对账）
  - `clientSeq`（客户端递增序号）
  - `playerId`（玩家 ID）
  - `payload`（指令参数）

> 客户端策略建议：
> - 本地立即把该指令标记为 `Pending`（待确认），用于 UI 状态提示（例如按钮进入冷却灰态）。

### 4.2 接收 CommandAck（指令回执）

- 客户端收到 `CommandAck`（指令回执）后：
  - 若 `status='Ok'`：将对应 `cmdId` 从 Pending 移除。
  - 若 `status!='Ok'`：从 Pending 移除并显示 `message`（可读中文短句），同时记录 `reasonCode`。

> 注意：
> - `CommandAck` 只用于“输入是否生效”的对账与 UI 提示，不替代事件/快照同步。

## 5. 事件/快照的客户端处理流程（推荐落地）

### 5.1 AuthorityFrame（权威帧）

客户端同步层输出统一结构，供 SimulatedState 使用：

```ts
interface AuthorityFrame {
  serverTick: number;     // 权威 tick
  resultType: 'Events' | 'Snapshot'; // 本帧来源
  events?: Event[];       // 若为 Events
  snapshot?: Snapshot;    // 若为 Snapshot
}
```

### 5.2 应用规则（强制）

- `resultType = Snapshot`：
  - 直接用快照重建或覆盖 SimulatedState（按兴趣范围）。
- `resultType = Events`：
  - 按 `serverTick` + `eventSeqInTick` 的稳定顺序应用事件。

> 客户端不得假定事件一定连续：
> - 若发现缺 tick/超窗，则等待服务端退化快照或主动请求快照。

## 6. UI 独立系统（强制：预构建 + 运行时绑定）

### 6.1 目标

- UI 作为独立系统，不依赖世界渲染对象的生命周期。
- UI 的**组件树**在加载期创建完成，运行时只做：
  - 数据绑定更新（文本、进度条、列表数据）
  - 可见性切换（show/hide）
  - 状态切换（tab/page/state）

### 6.2 禁止项（强制）

- 禁止在运行时“临时拼 UI 布局”（例如每次打开面板重新 new 整棵界面树）。
- 禁止把 UI 构建逻辑散落在业务系统 update 中。

### 6.3 推荐实现方式（可直接落地）

- `UiRoot`（UI 根节点）在游戏启动时初始化一次。
- 各 UI 面板（例如经济面板、舰队面板、科技面板）在启动/进入游戏时创建并注册。
- 使用 `UiViewModel`（UI 视图模型）作为 UI 的唯一数据入口：
  - 订阅 `DailySnapshot`（上一日快照，UI 只读）
  - 订阅本地 `SelectionState`（选择态：当前选中舰队/星球）
  - 订阅网络状态（延迟、掉线、重连）

> UI 刷新节奏：
> - UI 不需要跟随每渲染帧刷新。
> - 建议以“数据变更驱动”刷新（observer）或以低频节拍刷新（例如 5~10Hz）。

## 7. 客户端主循环（建议）

客户端至少有两种节拍：

- **Render Frame（渲染帧）**：尽可能高频（受 GPU/平台影响）。
- **Net Pump（网络泵）**：固定或尽可能频繁地处理网络收发。

推荐流程：

1. Net Layer：收包 -> 解码 -> 推给 Sync Layer。
2. Sync Layer：整理为 `AuthorityFrame`。
3. SimulatedState：应用 `AuthorityFrame`。
4. RenderState：基于 SimulatedState 做预测与平滑。
5. Render：渲染世界 + 渲染 UI。

---

## 8. 最小验收清单

- UI 只读 `DailySnapshot`（上一日快照）作为经济/面板展示数据源，不读取“结算中间态”。
- 网络抖动/丢包场景下，单位能保持可接受的视觉连续性，且收到权威后能硬对齐不漂移。
- 指令失败时，客户端能收到 `CommandAck` 并展示明确原因。
- 客户端不存在任何会决定权威结果的本地结算逻辑。
