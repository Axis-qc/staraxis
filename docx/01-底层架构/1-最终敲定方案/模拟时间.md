# 模拟时间 - 最终敲定方案 (V2)

> 本文档为 StarAxis 项目关于“游戏模拟时间”的唯一权威来源，取代《服务端主循环-实现.md》及其他文档中所有关于时间推进、倍率、结算触发的相关描述。若有冲突，以此为准。
> 
> **核心口径 (V2 更新)**：
> - **Tick 与时间推进分离**：服务器 tick 维持 `25 tick/s` 的固定节拍，仅作为逻辑更新的脉冲，与游戏内时间的流逝速率解耦。
> - **结算周期由模拟时间驱动**：日结算/跨日判定由“游戏内累计时间”驱动。每当游戏世界推进了完整的 `24` 个模拟小时，就触发一次日结算。`timeScale`（时间速度）直接影响结算发生的真实世界时长。

---

## 1. 核心概念与关键字段

### 1.1 基本定义

- **`serverTick` (服务端权威 Tick)**：是服务器逻辑更新的“脉冲”或“节拍器”，以固定的 `25 tick/s` 频率运行。它是所有联机对齐、事件排序和确定性回放的唯一时间轴基准。
- **游戏时间 (Game Time)**：是游戏世界内部流逝的时间，单位为“游戏小时”。它的推进速度由 `timeScale` (全局时间倍率) 决定，与 `serverTick` 的固定节拍分离。

### 1.2 字段与常量清单

| 字段 / 常量 | 含义与规范 (注释强制) |
|---|---|
| `serverTick` | **服务端权威 Tick**；固定 `25 tick/s`；主循环 `PrepareTick` 阶段自增+1。 |
| `ticksPerSecond` | **每秒 Tick 数**；常量，固定为 `25`。 |
| `ticksPerHour` | **每游戏小时对应的标准 Tick 数**；常量，固定为 `25` (仅用于 `timeScale=1.0` 时的基准换算)。 |
| `tickBudgetMs` | **目标 wall-clock Tick 预算 (毫秒)**；`1000 / ticksPerSecond = 40ms`。 |
| `tickCostMs` | **实际 wall-clock Tick 耗时 (毫秒)**；监控指标，用于判断是否超预算并触发时间膨胀。 |
| `gameDatetimeDay` | **游戏日序号 (从 1 开始)**；当累计游戏小时数满 24h 后，在 `Commit` 阶段 `+1`。 |
| `tickInDay` | **当日 Tick 计数**；当日结算触发后归零。**V2 中仅供参考，不用于跨日判断**。 |
| `accGameHoursInDay` | **当日累计游戏小时数**；范围 `[0, 24)`，是驱动日结算的核心变量。 |
| `baseDtGameHours` | **基准游戏小时步长 (每 Tick)**；`1 / ticksPerHour = 1/25` 游戏小时。 |
| `timeScale` | **全局时间倍率 (时间速度)**；合成自玩家档位、技能倍率、系统上限的最终值。 |
| `dtGameHours` | **本 Tick 实际游戏小时步长**；计算公式：`baseDtGameHours × timeScale`。 |
| `localTimeScale` | **实体局部时间倍率**；影响实体自身冷却/Buff等，公式：`clamp(timeScale + bonusScale, 0.1, 4.0)`。 |

## 2. 时间倍率模型 (Time Scale Model)

### 2.1 全局时间倍率 `timeScale` 合成

`timeScale` 的最终值由三层来源按优先级合成，确保了玩家控制、游戏性调节和系统稳定性之间的平衡。

**合成公式：**

```typescript
// 1. 基础倍率 = 玩家调速 * 全局技能修正
const timeScaleBase = playerScale * skillScaleGlobal;

// 2. 最终倍率 = min(基础倍率, 系统性能上限)
const timeScale = min(timeScaleBase, systemCapScale);
```

**来源与优先级 (高 → 低):**

1.  **`systemCapScale` (系统强制倍率上限)**
    -   **来源**：由性能监控模块根据 `tickCostMs` 与 `tickBudgetMs` 的对比实时计算。
    -   **作用**：当服务器性能压力过大导致处理超时，系统可强制降低此值，直接压低最终的 `timeScale`，实现“时间膨胀”，保证模拟不跳步。
    -   **精度**：允许以 `0.01` 为最小单位进行精确调节。

2.  **`skillScaleGlobal` (全局技能倍率)**
    -   **来源**：由当前所有生效的“全局时间类技能”决定。
    -   **作用**：实现“时间膨胀”类技能效果。例如，“全局减速50%”的技能其 `skillScale` 为 `0.5`。
    -   **合成规则**：同一时刻存在多个全局时间技能时，取“减速最强”的那个 (即 `skillScale` 的**最小值**)。

3.  **`playerScale` (玩家调速倍率)**
    -   **来源**：玩家通过 UI 在预设档位间切换。
    -   **作用**：为 `timeScale` 提供基础值。
    -   **预设档位 (强制)**：`{0.1, 0.25, 0.5, 0.75, 1.0, 2.0, 3.0, 4.0}`。

### 2.2 实体局部时间倍率 `localTimeScale`

`localTimeScale` 允许单个实体拥有与全局不一致的时间流速，主要用于实现“自身加速/减速”类技能效果。

**计算公式：**

```typescript
// localTimeScale = clamp(全局时间倍率 + 自身额外加成, 最小倍率, 最大倍率)
const localTimeScale = clamp(timeScale + bonusScale, 0.1, 4.0);
```

-   `bonusScale` (实体自身的回补倍率) 通常等于其“自加速”技能提供的加成值。

**影响范围白名单 (强制)：**

`localTimeScale` **只允许**影响“实体自身的局部逻辑推进速度”，具体包含：
-   武器/技能冷却 (cooldown)
-   护盾/能量等恢复速率
-   实体级生产/建造队列进度
-   实体身上的 BUFF/DEBUFF 持续时间与周期性触发

**禁止影响范围 (强制)：**

`localTimeScale` **禁止**影响任何全局或联机对齐概念，包括：
-   `serverTick`、`gameDatetimeDay`、`accGameHoursInDay`
-   跨日边界与日结算触发
-   网络同步相关的任何语义

## 3. 游戏时间推进与日结算

这是 V2 版本的核心变更。日结算不再由固定的 Tick 计数触发，而是由游戏内时间的真实流逝驱动。

### 3.1 时间推进公式

在主循环的 `PrepareTick` 阶段，按以下公式计算本 Tick 的游戏时间增量：

```typescript
// serverTick 是逻辑脉冲，固定递增
serverTick += 1;

// 1. 计算本 Tick 实际推进的游戏小时数
const dtGameHours = baseDtGameHours * timeScale; // baseDtGameHours = 1/25

// 2. 累加到当日累计器
accGameHoursInDay += dtGameHours;
```

随后，各子系统在 `Update(dtGameHours)` 接口中，统一使用此 **`dtGameHours` (小时增量)** 来推进其内部逻辑。

### 3.2 日结算触发机制

在主循环的 `Commit` 阶段最开始，检查当日累计游戏小时数是否达到 `24` 小时：

```typescript
// 检查是否累计满一个游戏日
if (accGameHoursInDay >= 24.0) {
    // 1. 从累计器中减去一个整天，保留当天溢出的时间用于下一天
    accGameHoursInDay -= 24.0; 

    // 2. 游戏日期推进一天
    gameDatetimeDay += 1;

    // 3. 当日 Tick 计数器归零 (仅供参考)
    tickInDay = 0; 

    // 4. 触发日结算流程
    triggerDailySettlement();
} else {
    // 若未跨日，则当日 Tick 计数器正常推进
    tickInDay += 1;
}
```

### 3.3 `timeScale` 对结算周期的影响

`timeScale` 现在是影响真实世界中“游戏一天”时长的唯一因素。

-   **`timeScale = 1.0`**：每 tick 推进 `1/25` 游戏小时。需要 `24 / (1/25) = 600` tick (即 **24 秒** 现实时间) 结算一天。
-   **`timeScale = 0.5`**：推进速度减半。需要 `600 / 0.5 = 1200` tick (即 **48 秒** 现实时间) 结算一天。
-   **`timeScale = 2.0`**：推进速度翻倍。需要 `600 / 2.0 = 300` tick (即 **12 秒** 现实时间) 结算一天。

## 4. Tick 调度与超预算处理

为保证服务器在超负载下的稳定性和模拟的确定性，采用“时间膨胀优先，频率熔断保底”的策略。

### 4.1 Tick 调度目标

- **默认 tick 频率目标**：`targetTicksPerSecond = 25`。
- **默认预算**：`tickBudgetMs = 1000 / targetTicksPerSecond = 40ms`。
- **调度规则**：主循环维护 `nextTickDeadlineNs`（下一 tick 截止时间）。若本 tick 提前完成，则 sleep 到截止时间；若超时，则不追赶、不补算，下一 tick 立即开始。

### 4.2 默认模式：时间膨胀 (Time Dilation)

-   **触发条件**：`tickCostMs > tickBudgetMs` (实际耗时 > 目标预算 40ms)。
-   **行为**：系统通过降低 `systemCapScale` 来压低最终的 `timeScale`。这会减少每 tick 推进的 `dtGameHours`，从而降低单位游戏时间的计算量，给服务器更多处理时间。
-   **`systemCapScale` 计算规则 (强制)**：
    -   `rawCap = tickBudgetMs / tickCostMs`
    -   `rawCapClamped = clamp(rawCap, 0.1, 4.0)`
    -   `systemCapScale = floorToCent(rawCapClamped)` (向下取到 0.01 精度)
-   **恢复规则 (防抖)**：为避免 `timeScale` 抖动，采用“连续窗口”机制。只有当 `tickCostMs` 连续多个 tick 稳定在预算内/外时，才允许 `systemCapScale` 升/降。

### 4.3 熔断模式：降低目标 Tick 频率 (Circuit Breaker)

-   **触发条件**：当 `timeScale` 已降至最小档位 (如 `0.1`)，但仍然连续多个 tick 超预算。
-   **行为**：作为最后手段，允许降低 tick 的目标物理频率 (例如从 `25 tick/s` 降至 `20 tick/s`)，同步增大 `tickBudgetMs`。这会降低网络更新和输入处理的频率，是“保命模式”。
-   **恢复**：当负载恢复正常后，目标 tick 频率会逐步回升至 `25 tick/s`。

## 5. UI 时间显示口径

为确保客户端显示一致，UI 必须遵循以下口径解析和显示游戏时间：

-   **小时**：直接取自当日累计游戏小时数的整数部分。
    `gameHour = floor(accGameHoursInDay)`
-   **年月日**：以 `gameDatetimeDay` (日序号) 为基准进行推算。开局日期为 2100-01-01，采用“每年12月，每月30日”的固定历法。

---

## 6. 强制规则与禁止项

1.  **结算驱动源唯一**：`timeScale` 是影响日结算频率的唯一因素。所有与时间推进和结算周期相关的逻辑，必须以 `accGameHoursInDay` 作为唯一判断依据。
2.  **推进单位统一**：所有系统的 `Update` 接口必须统一使用 `dtGameHours` (游戏小时增量) 作为推进单位。
3.  **写入串行化**：任何对 `serverTick`, `gameDatetimeDay`, `accGameHoursInDay` 等权威时间字段的修改，都必须在主循环的串行化落账点 (`Commit` 阶段) 进行。并行任务绝对禁止直接修改这些值。
