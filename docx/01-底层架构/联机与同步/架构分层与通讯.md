# 架构分层与通讯（核心逻辑 / C-S 分离）

> 目标：为 StarAxis 的长期开发（含未来多人/服务器模式）确立“服务端模拟、客户端渲染与交互”的硬性边界，并定义客户端与服务端之间的通讯口径。

## 1. 总原则（必须遵守）

1. **服务端负责模拟演算**：所有游戏规则、状态推进、数值计算、随机结果判定，必须由服务端负责。
2. **客户端负责渲染与输入**：客户端只负责展示与采集输入，不得在客户端做会影响结果的规则计算。
3. **UI 层独立**：UI 只展示“服务端给出的状态/派生展示信息”，不实现规则。
4. **模拟时间驱动**：任何推进以 `模拟时间` 为唯一基准，禁止用帧率推进核心逻辑。

## 2. 分层模型（概念）

### 2.1 服务端（Server / Simulation）

- 维护权威世界状态（World State）
- 推进模拟时间（Simulation Time）
- 执行：世界生成、经济日结算、舰队移动、战斗结算、外交状态变化等

### 2.2 客户端（Client / Presentation）

- 渲染：星图/恒星系/地表等视图
- 输入：点击、拖拽、快捷键、指令选择
- 本地可做：镜头运动、UI 动画、纯视觉特效

### 2.3 通讯层（Transport / Protocol）

- 负责在 C-S 间传输“输入指令”和“权威状态/事件”
- 必须能记录与回放（用于调试与复现）

## 3. 通讯模式（口径）

> **注**：本节定义宏观通讯模式。具体的指令（Commands）、事件（Events）和快照（Snapshots）的数据结构，请参见 **《通信协议与数据结构.md》**。

### 3.1 指令式输入（Command）

客户端发送 **指令** 给服务端：

- 指令包含：`指令类型` + `参数` + `目标对象标识` + `客户端时间戳/序号`
- 指令不得包含：直接修改世界状态的“结果值”（避免作弊/不一致）

**示例（概念）**：
```typescript
// MoveFleetCommand 负载示例
{
  fleetId: "fleet_alpha_01",
  destinationWorldPos: { x: 12345.6, y: 67890.1 }
}
```

### 3.2 事件/快照输出（Event / Snapshot）

服务端向客户端输出：

- **快照（Snapshot）**：某一模拟时间点的状态摘要（用于初次加载/断线重连/纠错）
- **事件（Event）**：状态变化事件流（用于实时更新 UI）

## 4. 同步节奏（口径）

- 服务端以固定或可配置的“模拟步长”推进（例如每 X 模拟秒/或按需要推进）
- 客户端渲染帧率可变，但显示的状态只能来自：
  - 最近一次快照
  - 后续事件流的应用结果

> 注：具体网络帧率/压缩/可靠性协议属于实现细节，本文件只定义“必须存在快照 + 事件”两类输出。

## 5. 身份与对象标识（口径）

- 世界中所有可交互对象必须有稳定唯一标识（例如 `sectorId`, `starSystemId`, `fleetId`）
- 客户端交互只通过标识引用对象，不直接持有/修改权威状态

## 6. 失败与回退（口径）

- 指令无效（资源不足、目标不存在、权限不允许等）时：
  - 服务端返回“拒绝事件”（如 `CommandRejectedEvent`）与原因（可本地化为提示）
- 客户端不得“假定成功”并永久修改状态；若需预测，仅允许视觉层临时表现，最终以服务端结果为准
