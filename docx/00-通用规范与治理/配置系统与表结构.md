# 配置系统与表结构（数值与内容生产口径）

> 目标：定义配置/参数表体系的权威口径，使经济/战斗/科技/事件等系统的内容生产与数值迭代可维护、可校验、可热更，并保证联机一致性。
> 
> 本文只定义“配置是什么、怎么组织、怎么校验、怎么版本化、怎么热更”。具体每张表的业务字段由各系统文档定义。

---

## 1. 核心结论（先读这一段即可落地）

- 配置以“表”为中心组织（表：一组结构一致的记录），所有记录必须有稳定主键 `id`（主键：唯一标识一条记录的字段）。
- 配置文件格式统一为 **`JSON`（唯一规范格式）**。
- 配置文件统一放在 `assets/`（资源目录）下，允许子目录，且按模块拆分（模块：一个系统域，例如科技/经济/战斗/世界生成/事件）。
- 客户端/服务端必须使用同一份配置版本 `configVersion`（配置版本：用于联机一致性校验），不一致时必须拒绝进入联机房间或强制更新。
- 配置变更必须经过校验（校验：类型、范围、引用关系、唯一性、循环依赖等），不允许带着错误上线。
- 热更必须有边界：
  - 允许热更“纯数值/纯内容”字段。
  - 不允许热更“影响存档结构/协议结构/世界生成确定性”的字段（除非配套升级机制）。

---

## 2. 配置来源与格式（口径）

### 2.1 推荐来源

- 表格（CSV/TSV/Excel 导出）作为策划编辑源。
- 构建时导出为 **`JSON`（唯一规范格式）**：
  - 不使用二进制作为配置发布格式（避免调试困难与跨语言兼容成本）。
  - 如需加速加载，可在运行时做内存缓存/索引构建，但源文件与发布文件仍保持 JSON。

### 2.2 配置组织方式（强制口径：按模块拆分 JSON，保存在 assets）

- 配置文件按“模块/系统域”拆分，且统一放在 `assets/`（资源目录）下，允许子目录。
- 目录规则：`assets/<module>/*.json`。
- 约束：
  - **不允许把所有表混合在一个大 JSON 中**（避免耦合、降低协作效率、影响热更粒度）。
  - 每个模块目录下可以包含多份 JSON（多文件：便于协作与热更粒度），但禁止跨模块混放。
  - 文件命名必须使用 `kebab-case`（例如 `planet-type.json`、`tech-tree.json`）。

#### 2.2.1 模块目录清单（建议口径，后续可增补）

- `assets/worldgen/*.json`（世界生成配置：星区类型、恒星系模板、行星生成参数等）
- `assets/world/*.json`（世界基础数据：坐标尺度、世界常量、通用阈值等）
- `assets/planet/*.json`（行星：行星类型、行星基础数据、地表参数等）
- `assets/city/*.json`（城市：城市基础数据、城市专精、建筑槽规则等）
- `assets/population/*.json`（人口：人口增长、迁移、职业/阶层等）
- `assets/law/*.json`（法律/政策：法律条目、效果、适用条件等）

- `assets/technology/*.json`（科技：科技树、科技分类、科研规则、科研点数产出等）

- `assets/economy/*.json`（经济：资源、配方、产业链、市场参数、运输参数等）

- `assets/ship/*.json`（舰船：船体、舰船设计、舰队规则、船坞规则等）
- `assets/ship-module/*.json`（舰船模块：引擎、护盾、装甲、反应堆、辅助模块等）
- `assets/weapon/*.json`（武器：武器类型、弹药/能量参数、射程、命中修正等）
- `assets/combat/*.json`（战斗：命中/伤害/抗性公式参数、补给规则、战斗状态机参数等）

- `assets/event/*.json`（事件：事件定义、权重、条件、奖励/惩罚等）
- `assets/anomaly/*.json`（异常：异常定义、触发条件、解决方案等）

> 注：如果某模块过大，建议继续按子模块拆目录，例如 `assets/economy/resource/*.json`、`assets/economy/recipe/*.json`。

#### 2.2.2 单个模块 JSON 文件结构（示例）

```json
{
  "meta": {
    "configVersion": "1.2.3+build.456",
    "module": "technology",
    "generatedAtUnixMs": 1730000000000
  },
  "tables": {
    "technology": [
      {
        "id": "tech_mining_1",
        "name": "基础采矿",
        "cost": 100,
        "prerequisiteTechIds": []
      }
    ]
  }
}
```

- `meta.configVersion`（配置版本：用于客户端/服务端一致性校验）：
  - 必须可比较、可展示。
  - 必须对全局唯一：同一次发布中，所有模块 JSON 的 `meta.configVersion` 必须一致。
- `meta.module`（模块名：用于诊断与加载路由）：
  - 例如 `technology`、`economy`、`combat`、`worldgen`。

## 3. 配置版本策略（多文件拆分下的联机一致性口径）

### 3.1 `configVersion` 的定义

- `configVersion`（配置版本）是一个**全局版本号**：代表“本次发布的整套配置”。
- 规则：
  - 所有模块 JSON 都必须写同一个 `meta.configVersion`。
  - 客户端与服务端都必须以同一个 `configVersion` 作为联机一致性校验依据。

### 3.2 校验要求（强制）

- 启动加载时：
  - 服务端扫描 `assets/` 下所有模块 JSON，要求 `meta.configVersion` 全部一致；否则视为发布包损坏/混装，必须拒绝启动。
  - 客户端加载同理，`meta.configVersion` 必须一致；否则拒绝进入联机。
- 联机握手时：
  - 客户端上报 `configVersion`（配置版本：全局版本号）。
  - 服务端校验 `client.configVersion == server.configVersion`（必须完全一致），否则拒绝加入。

### 3.3 为什么不做“逐模块版本号”

- 逐模块版本号会导致“部分模块一致、部分模块不一致”的灰区，联机必然产生不可控分歧。
- 本项目口径：联机只认一个全局 `configVersion`。

## 4. 表结构规范（口径）

### 4.1 主键与命名

- 每张表必须有 `id`（主键）：
  - 类型建议 `string`（字符串主键便于跨表引用）。
  - 全表唯一，不允许重复。

### 4.2 记录字段约束

- 任何字段都必须有明确类型（类型：string/number/bool/enum/数组/对象）。
- 数值字段必须定义单位与范围（单位：例如 `credits`、`days`、`m/s`；范围：min/max）。
- 枚举字段必须定义取值集合（取值集合：允许的字符串列表）。

### 4.3 引用关系（外键）

- 表间引用必须使用 `xxxId`（外键：引用另一张表主键的字段）。
- 必须校验引用存在性（存在性：引用的 id 必须在目标表出现）。

示例：
- `shipDesign.weaponId`（武器引用）必须存在于 `weapon` 表。

---

## 5. 校验规则（强制口径）

### 5.1 基础校验

- `id` 唯一性校验。
- 必填字段存在性校验。
- 类型校验（例如 number 不能写成 string）。
- 数值范围校验（例如 `0 <= hitPoints <= 1_000_000`）。
- 枚举取值校验。

### 5.2 引用校验（外键）

- 所有 `xxxId` 必须指向存在的 `id`。
- 对于数组引用（例如 `requiredTechIds[]`），数组中每项都要存在。

### 5.3 循环依赖校验

- 对存在依赖图的表（例如科技树）：
  - 必须检测并禁止循环依赖（循环：A 依赖 B，B 依赖 A）。

### 5.4 可重复性校验（确定性相关）

- 影响世界生成与模拟确定性的配置：
  - 必须保证同 `seed`（世界种子）下输出一致。
  - 不允许在运行中热更影响生成结果的字段（热更边界见第 7 节）。

---

## 6. 加载时机与缓存（口径）

### 6.1 服务端

- 启动时加载配置（从 `assets/` 读取所有模块 JSON）。
- 加载失败（校验失败/缺表/缺字段/版本不一致）：必须拒绝启动或进入维护模式。

### 6.2 客户端

- 启动时加载（或进入主菜单前加载）。
- 联机进入房间前必须完成配置版本校验（见第 8 节）。

### 6.3 缓存策略

- 表数据应当只读（只读：运行时不允许直接改表数据）。
- 业务运行时如需可变数据，应放在状态层（状态：存档/运行时对象），不要写回配置。

---

## 7. 热更与回滚（口径）

### 7.1 允许热更的字段（建议口径）

- 纯数值平衡字段（例如伤害系数、生产效率、价格权重）。
- 纯内容字段（例如文本、图标引用、展示排序）。

### 7.2 禁止热更的字段（强制口径）

- 影响协议结构的字段（协议结构：网络消息字段定义）。
- 影响存档结构/解释方式的字段（存档结构：存档文件 schema）。
- 影响世界生成确定性的字段（生成确定性：同 seed 输出一致）。

### 7.3 热更流程（建议口径）

1. 生成新配置发布包（所有模块 JSON 更新为同一个新 `meta.configVersion`）。
2. 服务端校验通过后进入热更窗口（热更窗口：可切换配置的安全时机，例如暂停点/日结算点）。
3. 下发/提示客户端更新配置版本。
4. 客户端完成更新并校验 `configVersion`（全局配置版本）一致后允许继续联机。

### 7.4 回滚流程（建议口径）

- 回滚本质是切回旧 `configVersion`（全局配置版本）。
- 回滚也必须经过同样的校验与一致性检查。

---

## 8. 联机一致性约束（强制口径）

### 8.1 进入房间校验

- 客户端加入联机房间时必须上报：
  - `gameVersion`（游戏版本，SemVer）
  - `configVersion`（配置版本：全局版本号）
- 服务端必须校验：
  - `gameVersion` 与房间运行版本一致（或符合项目允许的版本策略）。
  - **`configVersion` 必须完全一致**。

### 8.2 不一致处理

- 若 `configVersion` 不一致：
  - 必须拒绝加入（拒绝：返回错误码与提示）。
  - 提示玩家更新客户端或等待服务端同步。

---

## 9. 验收标准（最小闭环）

- 新人能新增一张表/一条记录，通过校验并被客户端/服务端加载。
- 任意配置错误会被校验拦截，不会带错上线。
- 联机场景下，`configVersion`（全局配置版本）不一致必定被拦截。
- 热更流程可控：允许热更的字段可上线；禁止热更的字段不会在运行中被替换。
