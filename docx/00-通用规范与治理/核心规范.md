# StarAxis 项目核心开发规范 (V2)

> **本文档是 StarAxis 项目的最高技术规范，是所有开发活动的“宪法”。**
> 
> - **权威性**：本文档的原则覆盖所有代码、文档与技术决策。若其他规范或实现与本文档冲突，以本文档为准。
> - **适用范围**：所有项目贡献者，包括程序、策划、美术（涉及技术对接部分）与 QA。
> - **变更流程**：对本规范的任何修订，都必须经过技术评审并由架构负责人确认，以确保项目技术方向的一致性。

---

## 一、 架构与设计原则

### 1. 单机权威与本地世界状态 (Offline Authoritative)

- **核心**：本项目采用单机模式，游戏世界状态的唯一权威为本地进程内的 `WorldState`（或同等命名的世界状态容器）。
- **边界**：任何会改变游戏结果的逻辑、计算与随机判定，必须在核心模拟模块中执行，并以对 `WorldState` 的写入作为最终落账点。
- **禁止**：
  - UI/表现层直接修改权威世界数据。
  - 模块绕过统一入口直接“偷写”其他模块维护的实体数据。
- **说明**：联机与服务端系统当前不在范围内，相关文档与实现应以单机模式为准。

### 2. 确定性模拟 (Deterministic Simulation)

- **核心**：游戏的核心模拟逻辑必须是确定性的。在给定相同输入序列和初始状态下，模拟结果必须完全一致。
- **应用**：这是实现回放（Replay）与存档/读档一致性的基础。
- **禁止**：在核心逻辑中引入不确定性来源，如未固化种子的随机数、浮点数精度敏感计算、依赖系统时间或哈希顺序等。
- **参考**：[回放与确定性](../../03-核心机制/回放与确定性.md)

### 3. 数据驱动 (Data-Driven)

- **核心**：游戏的行为和内容应由外部数据（如 JSON, Scriptable Objects）定义，而不是硬编码在代码中。
- **边界**：禁止在代码中使用魔法数字（Magic Numbers）或硬编码字符串。所有可配置项（如数值、ID、路径）都应通过配置系统加载。
- **参考**：[配置系统与表结构](配置系统与表结构.md)

### 4. 实体-ID 索引模型 (Entity-by-ID)

- **核心**：所有游戏数据必须以 ID 作为唯一索引与引用方式。任何系统模块不得持有跨帧/跨模块的“裸对象引用”作为权威引用。
- **适用实体示例**（不限于）：
  - 国家 `countryId`
  - 星区 `sectorId`
  - 恒星系 `starSystemId`
  - 星球 `planetId`
  - 舰队 `fleetId`（多个舰船的集合体）
  - 舰船 `shipId`（单个舰船）
  - 领袖 `leaderId`
  - 人口 `populationId`

- **ID 生成方式（原则）**：
  - ID 的生成方式以“实体类型”为边界进行组织（例如按类型分配 ID 空间或由类型 + 序列构成）。
  - ID 生成与索引模型的具体设计单独沉淀到《ID 索引模型》文档中，以便迭代。

- **对象引用生命周期**：
  - 允许在 **单个模拟 tick** 内持有实体对象引用（例如局部变量/临时计算对象）。
  - **跨 tick** 必须仅持有 ID（或同等的可失效引用结构），禁止跨 tick 持有权威实体对象引用。

- **系统写入规则**：
  - 经济/战斗/外交/AI 等系统模块必须通过 `id` 获取实体数据，并仅修改其负责字段，最终写回 `WorldState`。
  - 任意“修改实体”的操作必须是可追踪的：输入（哪些 id）→ 变更（哪些字段）→ 落账（写入点）。

- **禁止**：
  - 以对象实例地址/哈希作为跨系统引用。
  - 通过 UI 层直接改写实体集合。

### 5. 内存常驻与实体文件存档 (In-Memory + Save Files)

- **核心**：游戏运行时，世界数据应常驻内存；并且必须支持保存为实体文件（存档）与从实体文件加载恢复。

- **存档要求（原则）**：
  - **完整性**：存档必须包含恢复游戏所需的最小完整世界状态（含所有被引用的实体）。
  - **引用完整性**：任何 ID 引用在存档中必须可解析（禁止悬挂引用）。
  - **一致性**：读档后应能继续确定性推进，且存档/读档不应引入额外随机性。
  - **版本迁移**：存档格式必须具备版本号；当数据结构演进时需提供迁移策略。

- **设计拆分**：
  - 存档系统的具体设计（文件格式、原子性、校验、压缩、错误处理、版本迁移细则等）单独沉淀到《存档系统》文档中，以便迭代。

- **禁止**：
  - 运行时依赖外部服务（如服务端）才能恢复存档。
  - 仅保存“差量且无法恢复”的状态（除非同时能保证可完整重建）。

### 6. 模块化与解耦 (Modularization & Decoupling)

- **核心**：功能必须按职责高度内聚、低耦合的模块进行划分。模块间通过清晰的接口（API）或事件（Events）通信。
- **禁止**：模块间循环依赖、跨层调用或直接访问其他模块的内部状态。

## 二、 编码与实现规范

### 7. 命名与语言

- **语言**：所有文档、注释、技术交流**必须**使用简体中文。代码标识符（变量、函数、类名等）**必须**使用英文。
- **术语**：所有中英文术语**必须**与《术语对照表》保持一致。

#### 7.1 总原则

- **标识符必须为英文**（禁止拼音）。
- **语义清晰优先**：宁可长一些，也不要随意缩写。
- **保持一致性**：同一概念在全项目中只能有一个英文名。

#### 7.2 大小写与命名风格

| 适用场景           | 风格            | 示例                     |
|--------------------|-----------------|--------------------------|
| 变量 / 函数        | `camelCase`     | `userProfile`, `calcSum` |
| 类 / 接口 / 组件   | `PascalCase`    | `UserService`, `AuthAPI` |
| 常量               | `UPPER_SNAKE_CASE` | `MAX_PAGE_SIZE`, `PI` |
| 文件 / 文件夹      | `kebab-case`    | `user-service`, `api-v2` |

*若目录或文档需要中文命名，可酌情使用，但代码目录仍建议采用 `kebab-case`。*

#### 7.3 禁止项

- **拼音**：如 `xingQuId`、`shouyi`。
- **过度缩写**：如 `cfgMgr`, `ecoSys`（除非全项目统一约定）。
- **同义不同名**：同一含义出现多个英文表达，例如同时使用 `user`、`player` 指代同一概念。

#### 7.4 文档字段注释规范

> 目标：让任意单篇文档即可自洽，读者无需跳转即可理解字段 / 结构 / 缩写含义。防止新开发者需要跳转或猜测术语含义

##### 7.4.1 适用范围

- 适用于所有开发文档（总览、系统设计、协议、示例、缺口清单等）。
- “字段 / 代码名”包括但不限于：
  - 模拟字段：`simulationTick`, `simulationDay`
  - 存档字段：`saveVersion`, `saveId`
  - 实体字段：`entityId`, `countryId`, `planetId`
  - 结构名：`RequestHeader`, `AuditEvent`
  - 枚举 / 状态码：`Rejected`, `Timeout`
  - 关键集合 / 变量：`pendingTasks`, `processedIds`

##### 7.4.2 正文写法（行内字段必须注释）

- 在正文出现字段 / 结构名时，必须采用以下格式之一：
  - **推荐**：`fieldName`（一句话解释它是什么或做什么用）
  - 或：`fieldName`（是什么）+（作用 / 维护者）

示例：

- `simulationTick`（模拟 tick，用于推进世界状态与确定性演算）
- `saveVersion`（存档版本号，用于兼容性与迁移）

##### 7.4.3 代码块写法（每个字段行内注释）

```ts
interface SaveHeader {
  saveId: string;          // 存档唯一 ID
  saveVersion: number;     // 存档版本号
  simulationTick: number;  // 当前模拟 tick
}
```

##### 7.4.4 枚举 / 状态码写法

- 枚举值必须附带中文解释：
  - `Timeout`（请求超时）
  - `Rejected`（已拒绝）

##### 7.4.5 例外情况（应极少出现）

- 众所周知的通用缩写可不解释（如 CPU、GPU、JSON）。
- 大段“完整字段表”可将解释移入表格，但需保证同页可见。

### 8. 游戏模拟驱动 (Simulation-Driven)

- **核心**：所有游戏逻辑的推进**必须**由模拟时间（`simulationTick` / `simulationDay`）驱动，**严禁**依赖渲染帧率（FPS）。

### 9. 多核与性能（强制）

- **强制并行化**：游戏的数据计算应当能够分布到多个线程/任务上，**禁止**长期演进后出现“所有计算全部累积到单一线程”导致的性能瓶颈。
- **权威一致性前提下并行**：并行化不得破坏确定性与权威写入边界：
  - 权威状态（`WorldState`）的写入仍应有明确的串行化/落账点。
  - 可并行部分应拆分为 Job（例如寻路、可见性计算、AI 意图生成、经济候选计算、事件筛选等），以任务队列方式提交。
- **低锁竞争**：高并发路径优先采用无锁/低锁数据结构与算法，避免全局锁。
- **度量驱动**：新增/修改并行代码必须配套性能度量（基准/监控），证明其收益或可接受的成本。

## 三、 扩展

### 10. 扩展性与 Mod 支持

- **核心**：架构设计必须预留扩展点（如事件总线、策略模式、数据注册表），为未来的功能扩展和 Mod 支持提供基础。
- **迭代**：项目采用覆盖式迭代开发，无需强制向后兼容，但重大变更必须有清晰的迁移路径说明。

---

## 四、 文档与流程

### 11. 文档即代码 (Docs as Code)

- **权威入口**：`docx/总目录.md` 是查找所有权威技术文档的唯一入口。
- **一致性**：代码实现若与文档口径不一致，必须优先更新文档并进行评审，或将代码修正至与文档一致。
- **可执行性**：所有“具体实现”文档，必须提供可直接参照开发的伪代码、接口定义、依赖清单和验收标准。
