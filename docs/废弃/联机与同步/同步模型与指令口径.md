# 同步模型与指令口径

> 目标：在“联机 + 客户端预测 + 服务端权威”的前提下，给出可落地、可排障、可扩展的权威口径：
> - 同步模型选择与边界（谁说了算）
> - 指令（Command，客户端发给服务端的“意图消息”）生命周期（从客户端到服务端再回到客户端）
> - 必须字段与排序/幂等/去重规则（让网络抖动/丢包下仍能正确执行）
> - 断线重连、快照、追帧与回滚/对账（reconcile，客户端把预测状态纠正为权威状态）规则
> - 强一致/弱一致的数据分层（哪些必须完全以服务端为准，哪些允许延迟/插值）
> - 预留外置反作弊接入点（不实现反作弊，仅定义接口点与事件结构，方便未来接入第三方）

---

## 1. 总体原则（权威口径）

- **服务端权威（Server Authoritative，服务端说了算）**：
  - 世界权威状态（权威状态：决定游戏结果、可存档、可回放的状态）只在服务端推进与落账（落账：把变化写入权威状态）。
  - 客户端只能通过发送指令（Command，意图）表达意图，不能直接决定权威结果。
- **客户端预测（Client Prediction，客户端先“假设执行”以提升手感）**：
  - 客户端允许对“即时交互体验”做预测与平滑（平滑：插值/外推/补间），但预测结果必须可被服务端回包纠正。
- **可重放（Replayable，可用输入/事件重建过程）与可审计（Auditable，可追踪每一步发生了什么）**：
  - 关键链路（指令、权威结算、关键快照）必须可被记录并用于回放定位（定位：找到分歧发生的 tick/事件）。
- **确定性边界（Determinism Boundary，哪些必须一致）**：
  - “模拟推进/结算逻辑”必须在服务端确定（确定：相同输入得到相同输出）。
  - 客户端的渲染/动画/UI 不要求确定（允许不同帧率/不同插值策略）。

## 2. 同步模型：分层 + 两条通道

### 2.1 两条通道

- **指令通道（Client -> Server，客户端发指令）**：
  - 可靠、有序（逻辑上：语义层保证最终按规则处理，不要求底层一定 TCP）
  - 核心诉求：幂等（重复发不重复执行）、去重（识别重复包）、乱序处理（包可能后到）、权限校验（玩家是否有权这么做）
- **状态通道（Server -> Client，服务端回状态）**：
  - 事件（Events，增量变化通知）+ 快照（Snapshots，某一时刻的整体/局部状态）混合
  - 核心诉求：能增量同步（平时用事件省带宽），必要时强制对齐（快照），并支持重连

> 备注：底层传输可用 UDP/QUIC/WS 等，本文档只规定“语义层”的可靠、有序与重放要求，不绑定具体网络库。

### 2.2 强一致 vs 弱一致（口径）

- **强一致（必须以服务端为准：客户端只能展示，不得决定最终值）**
  - 资产/库存/资源余额（数值：钱/物资/产能等）
  - 建造队列落账、科研进度落账（进度：是否完成/完成时间）
  - 战斗命中、伤害结算、单位存活（战果：死亡/掉血/命中结果）
  - 领土归属/外交状态（关系：战争/和平等）
- **弱一致（允许客户端插值/预测/延迟：短期不一致可接受）**
  - 位置与轨迹表现（表现：画面上位置/路径，可预测 + 平滑）
  - UI 展示字段（展示：面板数据，可缓存、可延迟刷新）
  - 非关键粒子特效、动画状态（纯表现，不影响结果）

### 2.3 Tick/Day 的时间口径

- 服务端维护权威时间轴：
  - **`serverTick`**（服务端权威 tick：联机对齐与预测对账的最小推进单位，如 20Hz/30Hz/60Hz）：用于驱动联机对齐、预测回滚与消息排序。
  - **`simulationDay`**（模拟日：宏观结算/归档/显示的逻辑时间单位）：用于经济日结算、事件推进、UI 展示与历史记录。
- 协议层必须能够同时携带：
  - `serverTick`（服务端权威 tick：用于对齐/回滚/去重/排序）
  - `simulationDay`（模拟日：用于业务事件归档/显示/统计）

## 3. 指令（Command）生命周期（端到端）

### 3.1 生命周期（必备流程）

1. **客户端产生指令**（带 `cmdId`（指令全局唯一 ID，用于幂等追踪）、`clientSeq`（客户端递增序号，用于排序/检测丢包）、`clientTick`（客户端本地 tick，用于预测对账）等）
2. **客户端本地预测执行**（可选：为了手感先执行；必须可回滚/可重算）
3. **客户端发送指令**到服务端（可重发：超时未收到确认则再发同一个 `cmdId`）
4. **服务端接收与预处理**
   - 基础校验（格式/字段范围：避免非法数据）
   - 乱序缓存（按 `clientSeq`（客户端递增序号，用于排序/检测丢包）或 `clientTick`（客户端本地时间轴 tick，用于预测对账））
   - 去重（按 `cmdId`（指令全局唯一 ID，用于幂等避免重复执行））
5. **服务端权限校验与执行**（权威执行：只有这一步会改变权威状态）
   - 通过则执行并生成事件/回包
   - 不通过则拒绝并返回拒绝原因
6. **服务端回包**
   - `CommandAck`（指令确认消息：告诉客户端“收到了/执行了/拒绝了”）
   - 相关 `Events`（事件增量：把权威变化同步给客户端）
   - 必要时 `Snapshot`（快照：强制对齐当前权威状态，通常用于重连/严重分歧）
7. **客户端对账（reconcile，对齐权威）**
   - 将本地预测状态与权威结果对齐
   - 需要时回滚到 `ackedAtServerTick`（指令实际生效 tick）并重放未确认指令（重放：按顺序再跑一遍本地预测）

### 3.2 必须支持的结果类型

- **Accepted（已接受）**：指令被接受并执行（可能延迟生效：在未来某个 tick 才落账）
- **Rejected（已拒绝）**：指令被拒绝（明确原因：客户端可提示/回滚预测）
- **Superseded（已覆盖）**：指令被后续更高优先级事件覆盖（例如被系统强制取消）
- **Deferred（已延期）**：指令已接收但排队等待执行窗口（如“下一 tick 执行”或“队列资源满足后执行”）

## 4. 指令字段口径（必须字段清单）

本文档与 `通信协议与数据结构.md`（通信协议：Command/Event/Snapshot 的基础结构定义）保持一致，但补齐联机所需字段与语义。

### 4.1 CommandHeader（推荐结构）

```ts
// 概念性数据结构（语义口径）
interface CommandHeader {
  cmdId: string;               // 指令全局唯一 ID：用于幂等/去重/追踪（推荐 UUIDv7 或等价方案）
  cmdType: string;             // 指令类型：例如 "MoveFleet"，服务端用它路由到具体处理器

  clientId: string;            // 客户端连接/设备/会话标识：用于区分连接、做速率统计与审计
  playerId: string;            // 玩家/角色标识：用于权限判定与归属（谁在发这个指令）

  clientSeq: number;           // 客户端单连接递增序号：用于排序、检测丢包、乱序缓存窗口
  clientTick: number;          // 客户端本地 tick：用于预测对账/回滚（服务端不得用它推进权威时间）
  clientTimeMs: number;        // 客户端时间戳（毫秒）：仅用于诊断/统计（不可作为权威依据）

  expectedServerTick?: number; // 期望服务端执行 tick：用于降低抖动/排队（服务端可忽略/裁剪）

  authContext?: any;           // 认证上下文：例如 token 摘要/权限域/登录态，具体由登录系统定义
}

interface BaseCommand {
  header: CommandHeader;       // 指令头：用于通用追踪/排序/鉴权
  payload: any;                // 指令体：与 cmdType 对应的具体业务字段
}
```

### 4.2 字段语义（强制口径）

- `cmdId`（指令全局唯一 ID：用于幂等/去重/追踪）
  - **必须全局唯一**。
  - 服务端以 `cmdId` 做幂等：同一个 `cmdId` 重复到达只能执行一次。
- `cmdType`（指令类型：决定由哪个处理器处理）
  - 服务端必须基于 `cmdType` 做路由与权限判断（例如某些指令只允许特定角色/状态）。
- `clientId`（客户端会话/连接标识：用于追踪连接侧行为）
  - 用于日志关联（同一连接的行为串联起来）与速率统计。
- `playerId`（玩家/角色标识：用于归属与权限）
  - 服务端必须基于会话验证 `playerId` 与登录态一致（防止伪造）。
- `clientSeq`（客户端递增序号：用于排序/检测丢包/乱序窗口）
  - 单连接内递增。
  - 用于检测乱序/丢失，并决定缓存窗口。
- `clientTick`（客户端本地 tick：用于预测对账）
  - 用于客户端预测与回滚对账。
  - 服务端不得信任它作为“权威时间”。
- `clientTimeMs`（客户端时间戳：用于诊断）
  - 仅用于问题定位（例如：测 RTT、统计延迟），不得影响业务逻辑。
- `expectedServerTick`（期望执行 tick：用于更平滑的体验）
  - 服务端可根据当前负载/窗口调整实际执行 tick。
- `authContext`（认证上下文：登录态/权限域）
  - 用于服务端快速做权限域校验与审计记录。

## 5. 服务端接收：幂等、去重、乱序、重发

### 5.1 幂等与去重规则

- 服务端维护：
  - `processedCmdIds`（近期已处理的 cmdId 集合：用于幂等去重，需带 TTL 防止无限增长）
  - `lastAcceptedClientSeqByPlayer`（每玩家/连接最后已接受的 clientSeq：用于检测回退/跨越）
- 处理规则：
  - 若 `cmdId` 已处理：直接返回对应 `CommandAck`（指令确认：不重复执行）。
  - 若 `clientSeq` 明显回退或跨越过大：进入风控/审计（审计：记录异常行为；本项目不直接判作弊）。

### 5.2 乱序处理窗口

- 允许一个有限的乱序窗口（例如 N 条或 T 毫秒：在窗口内允许缓存等待缺失包）。
- 超出窗口：
  - 可选择拒绝（`Rejected: OutOfWindow`（拒绝原因：超出乱序窗口））
  - 或要求客户端重连/请求快照（快照对齐：用 Snapshot 覆盖式同步）

### 5.3 重发策略（语义）

- 客户端若在超时内未收到 `CommandAck`（指令确认），可重发同一 `cmdId`（同 ID 重发）。
- 服务端必须保证：重发不会导致重复执行（幂等）。

## 6. 服务端回包：Ack、Events、Snapshot

### 6.1 CommandAck（建议结构）

```ts
interface CommandAck {
  cmdId: string;                // 被确认的指令 ID：用于客户端把 ack 对应回 pendingCommands
  clientSeq: number;            // 被确认的客户端序号：用于客户端批量确认 <= 此序号的指令

  status: 'Accepted' | 'Rejected' | 'Deferred' | 'Superseded'; // 指令状态：接受/拒绝/延期/覆盖
  reasonCode?: string;          // 原因码：Rejected/Superseded/Deferred 时给出（用于客户端提示与日志）

  serverTick: number;           // 生成 ack 的服务端 tick：用于客户端更新 lastKnownServerTick
  ackedAtServerTick?: number;   // 指令实际生效 tick：用于客户端回滚/重放（若与 serverTick 不同）

  authoritativeHash?: string;   // 权威摘要 hash：用于快速检测分歧（可选，通常用于调试/回放）
}
```

### 6.2 事件（Events）口径补充

- 事件必须携带：
  - `eventId`（事件唯一 ID：用于去重与追踪）
  - `eventType`（事件类型：客户端用它路由更新逻辑/表现）
  - `serverTick`（事件发生的服务端 tick：用于排序/对齐）
  - `simulationDay`（事件归属的模拟日：用于归档/显示）
  - （可选）`causedByCmdId`（关联指令 ID：用于追踪“哪个指令导致的变化”）

### 6.3 快照（Snapshot）发送时机（强制口径）

- 首次进入世界（初始同步：客户端无任何状态）
- 断线重连（状态可能缺失：需要强制对齐）
- 客户端检测到严重分歧（例如 `authoritativeHash`（权威摘要 hash）不一致、关键状态缺失）
- 服务端判定客户端落后过多（追帧不可行：事件缓冲已过期）

## 7. 客户端对账（Reconcile）与预测边界

### 7.1 客户端需要维护的最小集合

- `pendingCommands[]`（待确认指令队列：已发送但未收到 ack，按 `clientSeq` 排序）
- `predictedState`（本地预测状态：仅用于交互/表现，随时可能被权威纠正）
- `lastAckedClientSeq`（最后已确认的 clientSeq：用于丢弃已确认指令）
- `lastKnownServerTick`（最近收到的服务端 serverTick：用于估计服务端进度/对齐）

### 7.2 Reconcile 标准流程

- 收到 `CommandAck(status=Accepted)`（确认：已接受/已执行）时：
  - 将 `pendingCommands` 中 `clientSeq <= ack.clientSeq`（序号不大于确认序号）的指令标记为已确认
  - 如服务端回了关键事件/快照：以服务端为准覆盖本地（权威覆盖：强一致字段直接替换）
  - 回滚到 `ackedAtServerTick`（生效 tick），重放剩余 pendingCommands（重放：按序再次执行预测逻辑）
- 收到 `Rejected`（拒绝：不允许执行）时：
  - 移除该指令，并撤销对应预测副作用（撤销：回滚 UI/表现）
  - 显示失败原因（或静默处理：由交互设计决定）

### 7.3 预测允许范围（建议口径）

- 允许预测（可立即反馈，不影响最终结果）：
  - 本地选择、UI 状态、路径预览
  - 运动/镜头/交互反馈
- 不允许预测（或只能“灰态”展示：等待权威确认）：
  - 资产扣减最终值
  - 战斗命中/掉血最终值

## 8. 断线重连与追帧

### 8.1 重连流程（口径）

1. 客户端重连并携带：`lastKnownServerTick`（客户端已知的最新服务端 tick）、`lastAckedClientSeq`（客户端已确认到的序号，可选）
2. 服务端判断：
   - 可追帧：发送缺失的 Events（事件增量）+ 必要 Ack（补齐确认）
   - 不可追帧：发送 Snapshot（快照对齐：覆盖式同步）
3. 客户端：
   - 应用 Snapshot（用权威状态覆盖本地）
   - 清理过期 pendingCommands（丢弃已不再可用的旧指令）
   - 重新发送仍需要的意图（由业务决定：例如重新下达移动/建造）

### 8.2 追帧窗口

- 服务端应保留最近一段时间的事件环形缓冲（环形缓冲：固定容量的最近事件队列，按 tick 或按时间索引）。
- 超出窗口：只能走 Snapshot（因为缺失事件无法补齐）。

## 9. 错误处理与拒绝原因码（建议枚举）

- `InvalidPayload`（载荷非法：缺字段/类型不对/越界）
- `Unauthorized`（未认证：会话无效/登录失效）
- `Forbidden`（无权限：角色/状态不允许执行）
- `OutOfWindow`（超出窗口：乱序/追帧窗口外）
- `Conflict`（冲突：与当前权威状态不一致导致无法执行）
- `InsufficientResource`（资源不足：钱/物资/人口等不满足）
- `NotFound`（对象不存在：目标 id 无效）
- `Cooldown`（冷却中：需要等待时间/回合）
- `ServerBusy`（服务端繁忙：可重试或降级处理）

> 口径：拒绝原因码用于客户端处理与诊断日志，不应暴露敏感细节。

## 10. 外置反作弊接入点（不实现，仅定义扩展点）

> 本项目当前不做内置反作弊，但必须保证未来可接入外部反作弊/风控模块，且不需要大改核心流程。

### 10.1 接入点清单（Hook Points）

- **Hook A：指令接收后、基础校验前**
  - 用途：记录原始指令、做速率统计（例如：每秒指令数）
- **Hook B：基础校验后、权限校验前**
  - 用途：基于“玩家上下文/会话/历史行为”做外部判定（例如：异常频率标记）
- **Hook C：权限校验后、执行前**
  - 用途：做参数范围/业务约束的外部校验（可返回 Reject/Defer：外部建议拒绝/延期）
- **Hook D：执行后、事件广播前**
  - 用途：输出审计事件（状态变化摘要：用于外部系统分析）
- **Hook E：拒绝/异常时**
  - 用途：上报可疑/错误样本（例如：非法 payload、频繁失败）

### 10.2 审计事件结构（建议）

```ts
interface SecurityAuditEvent {
  auditId: string;             // 审计事件 ID：用于追踪一条审计记录
  serverTick: number;          // 审计发生的服务端 tick：用于时间排序
  simulationDay: number;       // 审计归属模拟日：用于归档/统计

  playerId: string;            // 玩家 ID：谁触发的行为
  clientId: string;            // 客户端会话/连接 ID：从哪个连接来的

  cmdId?: string;              // 关联指令 ID（若有）：用于把审计与具体指令关联
  cmdType?: string;            // 关联指令类型（若有）：用于分类统计
  clientSeq?: number;          // 关联客户端序号（若有）：用于定位乱序/丢包问题

  category: 'CommandReceived' | 'CommandRejected' | 'CommandExecuted' | 'RateLimit' | 'Anomaly'; // 分类：收到/拒绝/执行/限流/异常
  severity: 'Info' | 'Warn' | 'Error'; // 严重级别：信息/警告/错误

  reasonCode?: string;         // 原因码：例如拒绝原因/异常原因
  metrics?: Record<string, number>; // 指标：例如频率、间隔、偏差
  snapshotHash?: string;       // 权威摘要 hash：用于快速判断是否发生分歧（可选）

  extra?: any;                 // 扩展字段：保留给未来第三方系统
}
```

### 10.3 外部校验器接口（概念）

- 输入：`CommandHeader`（指令头：含身份/序号/时间信息） + `payload`（业务载荷） + `playerContext`（玩家上下文：服务端侧状态/权限） + 近期行为统计（速率/失败率等）
- 输出：
  - `Allow`（允许：不干预执行）
  - `Reject(reasonCode)`（拒绝：给出原因码）
  - `Defer(reasonCode, retryAfterMs)`（延期：建议多久后重试）
  - `Flag(auditEvent)`（仅标记不上线拦截：输出审计事件供外部分析）

## 12. 最小闭环检查表（用于验收）

- 客户端能发送指令，服务端能 Ack（Accepted/Rejected：能明确告诉客户端结果）。
- 服务端对 `cmdId` 幂等：同一指令重发不重复执行。
- 客户端维护 `pendingCommands` 并能在 Ack 后对账（预测纠正）。
- 服务端能在断线重连时：追帧（补事件）或回 Snapshot（强制对齐）。
- 存在明确的外置反作弊接入点：至少包含 hook 点位与审计事件结构（未来可接第三方）。
