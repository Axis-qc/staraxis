# 服务端主循环（可直接落地模型，极简版）

> 本文档目标：给出一套**可直接实现**的服务端主循环模型。
>
> 设计取向（强制）：
> - 主循环**尽量精简**：只维护权威时间、冻结输入、阶段调度、串行落账（Commit）、产物发布（事件/快照/回执）。
> - 具体业务逻辑（经济/战斗/AI/事件等）**全部下沉到模块**，主循环只调用模块接口。
> - 所有改变权威结果的写入都必须遵守**服务端权威**与**确定性模拟**原则，符合《核心规范.md》。
>
> 参考与口径来源：
> - `00服务端主循环-实现.md`（主循环阶段/指令/事件缓冲/日结算并行 Draft 方案）
> - `模拟时间.md`（V2：Tick 与游戏时间推进分离；跨日由累计游戏小时驱动）
> - `核心规范.md`（服务端权威、确定性、并行边界与度量驱动）

## 0. 核心原则（必须先读）

- **服务端权威（强制）**：所有会改变游戏结果的逻辑只能在服务端权威链路中生效。客户端只提交 `Command`（客户端意图指令）。
- **确定性（强制）**：相同初始状态 + 相同输入序列 => 相同输出。禁止把“线程完成先后”“HashMap 遍历顺序”“系统时间”作为结果依据。
- **并行边界（强制）**：
  - 并行任务只能做“候选计算”（Candidate），不得直接写入 `WorldState`（权威世界状态对象图）。
  - 所有写入必须集中在主循环 `Commit`（落账）阶段，以稳定顺序归并。
- **时间模型（强制，以 V2 为准）**：
  - `serverTick`（服务端权威 tick）固定 `25 tick/s`，仅作为联机对齐与确定性排序的时间轴。
  - 游戏时间流逝由 `dtGameHours`（本 tick 推进的游戏小时数）决定：`dtGameHours = baseDtGameHours * timeScale`，其中 `baseDtGameHours = 1/25`。
  - 跨日/日结算由 `accGameHoursInDay`（当日累计游戏小时数）驱动：累计满 `24h` 触发一次日结算。

## 1. 主循环最小职责（极简边界）

主循环只做以下事情：

1. **维护权威时间轴**
   - `serverTick`（权威 tick）自增
   - `timeScale`（全局时间倍率）合成
   - `dtGameHours`（本 tick 游戏时间步长）计算
   - `accGameHoursInDay`（当日累计小时）累加并驱动跨日

2. **冻结并排序本 tick 输入**
   - 从网络接入层线程安全入口队列 `drain` 出 `Command`（客户端意图指令）
   - 进行确定性排序/限流/分桶
   - 冻结为本 tick 的 `TickInput`（本 tick 输入快照），冻结后禁止取消/修改

3. **阶段调度（调用模块）**
   - 依次调用各模块的阶段回调（见第 3 节接口）
   - 主循环不实现任何业务逻辑，只传递 `TickContext`、`TickInput`、并收集模块输出

4. **串行落账（Commit）**
   - 将模块产生的候选结果按稳定键排序后应用到 `WorldState`
   - 触发/应用日结算（并行 Draft + 主循环 Commit）
   - 处理交互事件默认选项/过期回收等“必须权威且确定性”的事务

5. **发布产物（PostUpdate）**
   - 构建 `RealtimeSnapshot`（实时快照）
   - 写入 `Event Ring Buffer`（事件环形缓冲）
   - 写入网络发送队列（事件/快照/CommandAck）

## 2. 权威数据与跨线程读写模型（必须遵守）

### 2.1 三层数据模型（敲定）

- `WorldState`（权威世界状态对象图）
  - 写入：**仅主循环线程**，且仅在 `Commit` 阶段写入（强制）。
  - 读取：网络线程/打包线程不得直接读可变对象。

- In-Memory Snapshot（内存快照，只读）
  - 由主循环在落账后生成。
  - 网络线程只读快照并按兴趣范围裁剪打包。

- `Event Ring Buffer`（事件环形缓冲）
  - 缓存最近 N tick 的事件增量，用于追帧。

### 2.2 并行任务输出只能是“候选结果”（强制）

并行任务不得直接修改 `WorldState`。可输出以下两类之一：

- `CandidateDelta`（候选增量，强制可排序）
  - 含 `applyKey`（应用排序键）与 `apply(worldState)`（落账函数或等价描述）。

- `Intent`（意图列表）+ `Resolver`（解析器）
  - 模块产生意图，Commit 阶段由统一解析器按顺序解析为增量。

## 3. 主循环与模块的最小接口（可直接照做）

> 目标：模块可完全下沉业务逻辑，但必须在主循环给定的确定性框架内运行。

### 3.1 TickContext（每 tick 不可变上下文）

```ts
interface TickContext {
  serverTick: number;          // 服务端权威 tick（用于联机对齐与确定性排序）
  timeScale: number;           // 全局时间倍率（最终合成值）
  dtGameHours: number;         // 本 tick 推进的游戏小时数
  gameDatetimeDay: number;     // 游戏日序号（从 1 开始）
  accGameHoursInDay: number;   // 当日累计游戏小时数（范围 [0,24)）
}
```

### 3.2 TickInput（本 tick 冻结输入）

```ts
interface TickInput {
  commands: Command[];         // 本 tick 冻结后的指令集合（已排序/限流）
}
```

### 3.3 模块接口（阶段回调）

```ts
interface IGameModule {
  name: string;

  // 可选：用于模块在本 tick 开始前做只读准备（不得写 WorldState）
  onPrepareTick?(ctx: TickContext, input: TickInput): void;

  // Update：模块执行本 tick 的核心逻辑
  // 允许提交并行任务；允许产生候选结果；禁止写 WorldState
  onUpdate(ctx: TickContext, input: TickInput, out: TickOutput): void;

  // Commit：模块在主循环线程落账点执行最终写入（强制）
  // 主循环可以选择：统一收集 out.candidates 统一排序后落账；或让模块在 onCommit 内自行落账。
  // 推荐做法：模块只提供 candidates，由主循环统一排序后 apply。
  onCommit?(ctx: TickContext, out: TickOutput, world: WorldState): void;

  // PostUpdate：模块生成事件/同步数据（禁止写 WorldState）
  onPostUpdate?(ctx: TickContext, out: TickOutput): void;
}

interface TickOutput {
  candidates: CandidateDelta[]; // 候选增量（必须可稳定排序）
  events: Event[];              // 本 tick 产生的权威事件增量（先收集，后统一排序写入环形缓冲）
  acks: CommandAck[];           // 指令回执（可靠发送）
}
```

### 3.4 CandidateDelta（候选增量）排序键（强制）

> 用于解决“多线程先算完的先落账导致结果反转”的问题：**先算完不代表先生效**。

```ts
interface CandidateDelta {
  applyKey: {
    serverTick: number;     // 必须
    phaseOrder: number;     // 可选：用于模块间固定先后，例如战斗(10)在经济(20)之前
    moduleName: string;     // 必须：稳定键
    seq: number;            // 必须：模块内部递增序号
  };
  apply(world: WorldState): void; // 只在主循环 Commit 阶段调用
}
```

- `applyKey`（应用排序键）必须保证：同一 tick 内全局可稳定排序。
- 如果增量由某条 `Command` 导致，建议把 `cmdId`（指令唯一 ID）/`clientSeq`（客户端递增序号）纳入稳定键，避免歧义。

## 4. 指令（Command）在主循环中的处理口径（可直接照做）

### 4.1 网络接入层与主循环的边界（强制）

- 网络接入层负责：反序列化/鉴权/基础限流/幂等去重。
- 网络接入层只把通过校验的 `Command` 推入线程安全入口队列。
- 主循环在 `PrepareTick` 阶段 `drain` 并冻结输入。

### 4.2 冻结、取消、替换（强制）

- 允许取消的范围：仅限仍在 `pending` 队列且尚未被冻结。
- 一旦进入本 tick 冻结输入集合：禁止取消/修改。
- 修改统一走 `CancelCommand` + 新 `Command`，禁止原地改 payload。

### 4.3 排序与公平性（强制）

- 桶内排序：按 `clientSeq`（客户端递增序号）升序；相同再按 `cmdId`（指令唯一 ID）稳定排序。
- 跨玩家执行：按 `playerId`（玩家 ID）升序轮询（round-robin）取指令，避免单玩家吃满 tick 预算。

### 4.4 CommandAck（指令回执）

- 回执必须可靠投递。
- 发送时机：主循环 `PostUpdate` 阶段统一写入网络发送队列。

## 5. 模拟时间（V2）在主循环中的落地（强制）

### 5.1 每 tick 时间推进（PrepareTick）

- `serverTick`（服务端权威 tick）在 `PrepareTick` 阶段 `+1`。
- 合成 `timeScale`（全局时间倍率）：
  - `timeScaleBase = playerScale * skillScaleGlobal`
  - `timeScale = min(timeScaleBase, systemCapScale)`
  - `timeScale = clamp(timeScale, 0.1, 4.0)`
- 计算 `dtGameHours = baseDtGameHours * timeScale`，其中 `baseDtGameHours = 1/25`。
- 累加：`accGameHoursInDay += dtGameHours`。

### 5.2 跨日判定与日结算触发（Commit）

> V2 强制：跨日由累计游戏小时驱动，不再以固定 tick 数驱动。

在 `Commit` 阶段最开始：

- 若 `accGameHoursInDay >= 24.0`：
  - `accGameHoursInDay -= 24.0`（保留溢出小时用于下一天）
  - `gameDatetimeDay += 1`
  - `tickInDay = 0`（仅供参考/统计，不作为跨日判断依据）
  - 触发日结算 `triggerDailySettlement()`（仅触发，不做大计算）
- 否则：
  - `tickInDay += 1`（仅供 UI/统计参考）

## 6. 日结算（并行 Draft + 主循环 Commit 落账）（可直接照做）

### 6.1 状态机（强制）

- `Idle`（空闲）
- `DraftComputing`（草稿计算中）
- `DraftReady`（草稿就绪）
- `CommitApplying`（落账中）
- `Failed`（失败）

### 6.2 触发（主循环 Commit）

跨日触发时：

- 主循环构建 `DailySettlementJobInput`（结算输入快照，必须只读）：
  - `oldDaily`（上一日快照，只读）
  - `dailyAccumulatorSnapshot`（日内累计器只读副本）
  - `settlementDay`（本次要归档的日序号）
- 提交到结算线程池，进入 `DraftComputing`。

### 6.3 Draft 计算（后台线程）

- 后台线程执行 `computeDailySettlementDraft(input)` 得到 `DailySettlementDraft`（不可变）。
- 禁止写入 `WorldState`。

### 6.4 Commit 应用与发布（主循环 Commit）

- 主循环在 `Commit` 阶段检查：若 `state==DraftReady` 且 day 匹配，则：
  - 将 `draft -> delta` 并按确定性顺序应用到 `WorldState`
  - 构建 `DailySnapshot newDaily` 并 `dailyRef.set(newDaily)` 原子切换
  - 轮换/清空 `DailyAccumulator`（日内累计器）
  - 状态回到 `Idle`

## 7. 事件环形缓冲（追帧）与快照退化（可直接照做）

### 7.1 事件顺序（强制）

- 每个事件必须携带 `eventSeqInTick`（tick 内序列号，从 1 递增）。
- 写入环形缓冲前按稳定键排序：
  - `serverTick`（权威 tick）升序
  - `eventSeqInTick`（tick 内序列号）升序

### 7.2 追帧请求与退化

- 若 `fromTick < oldestTickInBuffer`：退化为 `Snapshot`（超窗）。
- 若事件响应体积超过 `maxEventResponseBytes`：退化为 `Snapshot`（过大）。
- 若分包发送失败：退化为 `Snapshot`（过大或发送失败）。

---

## 8. Tick 调度、超预算与时间膨胀（可直接照做）

- 默认：`targetTicksPerSecond = 25`，`tickBudgetMs = 40ms`。
- 统计口径：`tickCostMs` 统计范围为 `PrepareTick -> PostUpdate`。

### 8.1 时间膨胀（优先）

- 当 `tickCostMs > tickBudgetMs`，降低 `systemCapScale` 以压低 `timeScale`。
- `systemCapScale` 计算（最小可落地规则）：
  - `rawCap = tickBudgetMs / tickCostMs`
  - `systemCapScale = floorToCent(clamp(rawCap, 0.1, 4.0))`
- 恢复/防抖：采用连续窗口升降（参数可运维配置）。

### 8.2 熔断（最后手段）

- 当 `timeScale` 已到最小仍持续超预算，允许降低 tick 目标频率，增大 `tickBudgetMs` 以保命。

## 9. 主循环伪代码（实现者可直接照做）

> 注意：此伪代码强调“主循环极简 + 调度模块 + 统一落账”。

```ts
while (running) {
  const tickStart = nowNs();

  // ========== PrepareTick ==========
  serverTick += 1;

  const incoming = commandIngressQueue.drain();
  const tickInput = commandQueue.freezeAndBuildTickInput(incoming); // 排序/限流/round-robin

  const systemCapScale = perfController.updateAndGetSystemCapScale(/*lastTickCostMs*/);
  const timeScale = timeScaleComposer.compose(/*playerScale, skillScaleGlobal, systemCapScale*/);
  const dtGameHours = (1 / 25) * timeScale;

  accGameHoursInDay += dtGameHours;

  const ctx: TickContext = {
    serverTick,
    timeScale,
    dtGameHours,
    gameDatetimeDay,
    accGameHoursInDay,
  };

  const out: TickOutput = { candidates: [], events: [], acks: [] };

  // ========== Update（调用模块） ==========
  for (const m of modules) m.onPrepareTick?.(ctx, tickInput);
  for (const m of modules) m.onUpdate(ctx, tickInput, out);

  // ========== Commit（唯一写入点） ==========
  // 1) 跨日触发（V2：累计小时驱动）
  if (accGameHoursInDay >= 24.0) {
    accGameHoursInDay -= 24.0;
    gameDatetimeDay += 1;
    tickInDay = 0;
    dailySettlement.triggerIfIdle(/*oldDaily, accumulatorSnapshot, day*/);
  } else {
    tickInDay += 1;
  }

  // 2) 日结算 DraftReady 则应用并发布 newDaily
  dailySettlement.tryCommitIfReady(worldState, /*dailyRef*/);

  // 3) 统一按稳定键排序后落账
  out.candidates.sort(byApplyKey);
  for (const c of out.candidates) c.apply(worldState);

  // （可选）模块自定义 commit 钩子（不推荐写复杂逻辑）
  for (const m of modules) m.onCommit?.(ctx, out, worldState);

  // 4) 交互事件过期默认处理（若实现了 InteractiveEventStore）
  interactiveEventStore.commitExpireAndDefault(worldState, gameDatetimeDay);

  // ========== PostUpdate ==========
  // 1) 生成 RealtimeSnapshot
  realtimeSnapshot = snapshotBuilder.buildRealtime(worldState, serverTick);

  // 2) 事件写入环形缓冲（排序）
  out.events.sort(byTickAndSeq);
  eventRingBuffer.append(serverTick, out.events);

  // 3) 发送队列（事件/快照/CommandAck）
  netOutbox.enqueue(buildNetPayloads(realtimeSnapshot, out.events, out.acks));

  // ========== Tick 调度 ==========
  const tickCostMs = (nowNs() - tickStart) / 1e6;
  perfController.recordTickCostMs(tickCostMs);
  scheduler.sleepOrRunNext(/*tickBudgetMs*/);
}
```

## 10. 验收点（最小验收清单）

- 主循环线程是唯一写 `WorldState` 的线程，且写入发生在 `Commit`。
- 并行任务只产出候选结果，最终落账顺序由 `applyKey` 决定，而不是由“计算完成先后”决定。
- `serverTick` 固定 25 tick/s；`timeScale` 只影响 `dtGameHours`；跨日由 `accGameHoursInDay` 驱动。
- `DailySnapshot` 原子切换；UI 只读 `dailyRef.get()`。
- `Event Ring Buffer` 支持追帧，超窗/过大/失败可退化为快照。
- `CommandAck` 可靠发送，失败原因码可用于 UI 提示。
