# 数据流与状态管理

> 目标：明确游戏世界数据“从哪里来、如何改、怎么存、给谁看”的完整生命周期，作为服务端与客户端实现的核心依据。

## 1. 权威状态（Authoritative State）

- **唯一真实源**：游戏世界的唯一真实、权威的状态数据，**必须且只能**存在于**服务端内存**中。
- **内容**：包括所有星区、恒星系、行星、舰队、资源库存、外交关系等模拟对象。
- **客户端**：客户端持有的任何游戏世界数据都只是服务端的“非权威拷贝”或“派生视图”，用于渲染和交互，**绝不能**作为规则计算的依据。

## 2. 状态修改（Modification）

- **唯一修改者**：权威状态**只能**由服务端的**模拟循环（Simulation Loop）**修改。
- **修改触发条件**：
  1. **响应指令（Command）**：客户端提交的指令（如`MoveFleetCommand`）被服务端验证通过后，在模拟循环中执行并修改状态。
  2. **预定事件（Scheduled Event）**：模拟时间到达某个预定点时触发（如`DailySettlement`）。

## 3. 状态持久化（保存/读取）

### 3.1 保存游戏（Save Game）

- **行为**：将服务端内存中的**权威世界状态**在某个精确的模拟时间点，完整地**序列化**为一个存档文件。
- **本质**：存档文件是世界状态的**完整快照**。
- **格式（建议）**：采用二进制序列化（如 Kryo）以提高性能和减小体积，或在开发阶段使用 JSON/YAML 以便于调试。

### 3.2 读取游戏（Load Game）

- **行为**：服务端**反序列化**一个存档文件，将内容完全重建到其内存中，作为新的权威世界状态。
- **约束**：读取后，服务端的模拟时间、对象状态必须与存档文件记录的完全一致。

## 4. 状态呈现（Presentation to Client）

客户端通过以下两种方式从服务端获取数据，并构建用于渲染的**本地视图状态（Local View State）**：

### 4.1 快照（Snapshot）

- **用途**：
  1. **初次加载/连接**：客户端连接时，服务端发送一次当前世界的完整快照。
  2. **断线重连/纠错**：当客户端状态与服务端差异过大时，通过快照强制同步。
- **内容**：是权威状态的“摘要”或“部分视图”，只包含客户端当前需要渲染和交互的部分。

### 4.2 事件流（Event Stream）

- **用途**：在快照之后，实时地将服务端的“状态变化”通知给客户端。
- **内容**：一系列描述“发生了什么”的事件，例如：
  - `FleetMovedEvent(fleetId, newPosition)`
  - `ResourceUpdatedEvent(planetId, resourceType, newAmount)`
  - `BattleStartedEvent(fleetA_Id, fleetB_Id, location)`

### 4.3 客户端工作流

1. 接收初始**快照**，构建基础视图状态。
2. 持续接收**事件流**，增量更新本地视图状态。
3. 渲染引擎根据本地视图状态进行渲染。

> 这种模式确保了客户端和服务端状态的最终一致性，同时允许客户端在事件间隙进行平滑的视觉插值（Interpolation），提升表现力。
