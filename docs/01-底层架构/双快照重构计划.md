# Dual Snapshot Redesign Plan

> 双快照重构计划：按更新频率重新划分 `RealTimeWorldState` 与 `DailySettlementState`，消除重叠，补全缺口。
>
> 更新时间：2026-07-06

---

## 1. 现状问题

### 1.1 两份快照在恒星/行星数据上重复

```
publishRealTimeSnapshot()       publishBaselineSnapshot()
  ├─ EntitySnapshot STAR        ├─ EntitySnapshot STAR       ← 重复
  ├─ EntitySnapshot PLANET      ├─ EntitySnapshot PLANET     ← 重复
  ├─ EntitySnapshot SYSTEM_     ├─ EntitySnapshot SYSTEM_    ← 重复
  │    BARYCENTER               │    BARYCENTER
  └─ 只读视图：                  └─ 只读视图：
       getEntitySnapshotsView()      publicEntityBaselinesBySectorKey
```

同一份 `StarBody`/`PlanetBody` 数据，每个 tick 在两个地方各构造一遍 `EntitySnapshot`。

### 1.2 双缓冲没覆盖的数据迫使 webnet 读 WorldState

webnet 在 9 个文件中直接读 `WorldState`，其中 2/3 是因为双缓冲里**没有**这些数据：

| 读 `WorldState` 的用途 | 应放在哪个快照 |
|---|---|
| `nationManager.getNationIdByPlayer(pid)` | 低频 |
| `visibilitySystem.computeIntelVisibleSystems3D(nationId)` | 低频（预计算） |
| `intelSystem.getEffectiveDetectorLevel3D(nationId, pos)` | 低频（预计算） |
| `astro.getSystemsView()` | 低频（世界生成后不变） |
| `time.playerTimeStep` / `simulationTick` | 高频（已有时钟） |
| `entitiesById.get(shipEntityId)` | API 直接查（见下文） |

### 1.3 线程安全缺口

`ShipCommandApi` (Undertow 工作线程) 直接读 `worldState.entitiesById` (普通 `HashMap`)，gameTicker 可能同时做 `registerEntity` 导致 resize。

## 2. 新架构：按频率划分

```text
game tick 循环:
  │
  ├─ 每 tick (50ms) ──────────────  HighFrequencySnapshot
  │   ├─ 时间轴元信息（tick/year/month/day...）
  │   ├─ 动态实体（SHIP/STATION/舰队）
  │   ├─ 战斗状态变化
  │   └─ 在途实体位置插值
  │
  └─ 每 20 tick ──────────────  DailySettlementState（低频基线快照）
      ├─ 恒星/行星/卫星/重心 基线快照（静态天体）
      ├─ 国家资产表（nationId → ownedEntities）
      ├─ 行星地表数据
      ├─ 玩家→国家映射（playerId → nationId）
      ├─ 各国家可见星系列表（预计算 visibilitySystem 结果）
      └─ 各星系情报等级（预计算 intelSystem 结果）

### 访问控制

```text
                       ┌─ game 模拟层（唯一读写）
         WorldState ───┤
                       └─ 每 tick → RealTimeWorldState（只读快照）
                                      └─ 客户端/渲染器/网络直读
                              每 20 tick → DailySettlementState（只读低频快照）
                                            └─ 客户端/渲染器/网络直读

    禁止：客户端、webnet、渲染器等外部模块以任何形式直接访问 WorldState
```

### 新旧对照

| | 旧 `DailySettlementState` | 新 `DailySettlementState`（低频基线快照） |
|---|---|---|
| 更新时机 | 每 60 游戏秒 + 脏标记 | 每 20 tick（现实 1 秒） |
| 驱动方式 | `lastBaselinePublishGameSeconds >= 60` | `simulationTick % LOW_FREQ_INTERVAL == 0` |
| 承载数据 | 行星地表 + 国家资产 + 公开基线 | 行星地表 + 国家资产 + 公开基线 + **玩家→国家映射 + 预计算可见星系 + 预计算情报等级** |
| 双缓冲 | 单缓冲 (synchronized 替换) | 提升为双缓冲（与高频一致） |

| | 旧 `RealTimeWorldState` | 新 `HighFrequencySnapshot` |
|---|---|---|
| 更新时机 | 每个模拟 tick | 每个模拟 tick（不变） |
| 承载数据 | 全部 Entity + 全部 EntitySnapshot | **只含动态实体**（去掉恒星/行星等静态基线） |
| 重复构造 | 与每日快照重复构造 STAR/PLANET | **不再构造静态实体快照** |

## 3. LowFrequencySnapshot 数据结构

### 3.1 名称方案

选项 A：原地改造 `DailySettlementState` → 保留类名但语义改为低频快照
选项 B：新建类 `LowFrequencySnapshot`，`DailySettlementState` 逐步淘汰

**推荐 A**，因为已经有两端（webnet 消费侧）引用，留名可以减少改造成本。仅调整注释和字段语义。

### 3.2 新增字段

```java
public class DailySettlementState {   // ← 语义改为低频快照

    // 已有字段
    public int settledDay;                     // 保留，语义降级为"快照版本号"
    public long settledAtGameSeconds;          // 保留
    public Map<Long, PlanetSurfaceDailySnapshot> planetSurfacesByPlanetId;  // 保留
    public Map<String, Map<EntityType, List<Long>>> nationAssetsByNationId; // 保留
    public Map<String, List<EntitySnapshot>> publicEntityBaselinesBySectorKey; // 保留

    // === 新增字段 ===

    /** 该快照对应的 simulationTick（主要版本号）。 */
    public long baselineTick;

    /** 玩家→国家映射（playerId → nationId）。
     *  供 webnet 快速查找玩家所属国家，无需读 WorldState。 */
    public Map<String, String> playerToNationMap;

    /** 国家→玩家列表映射（nationId → playerId 列表）。 */
    public Map<String, List<String>> nationToPlayerIdsMap;

    /** 各国家的可见星系 ID 列表（预计算）。
     *  替代 runtime.getWorldStateForSimOnly().visibilitySystem.computeIntelVisibleSystems3D()。 */
    public Map<String, Set<Long>> visibleSystemIdsByNationId;

    /** 各星系对各国家的探测等级（预计算）。
     *  替代 runtime.getWorldStateForSimOnly().intelSystem.getEffectiveDetectorLevel3D()。
     *  结构: nationId → (systemId → detectorLevel) */
    public Map<String, Map<Long, Integer>> detectorLevelByNationAndSystem;
}
```

### 3.3 LowFrequencySnapshotBuffer

当前 `DailySettlementStateBuffer` 是单缓冲 + `synchronized`，需要升级为双缓冲：

```java
public class LowFrequencySnapshotBuffer {
    private DailySettlementState a = new DailySettlementState();
    private DailySettlementState b = new DailySettlementState();
    private DailySettlementState active = a;
    private DailySettlementState inactive = b;

    public DailySettlementState beginFillInactive() { inactive.resetForFill(); return inactive; }
    public void swapPublish() { /* 交换 active/inactive */ }
    public DailySettlementState getActive() { return active; }
}
```

设计选择：低频快照体量较大（包含所有恒星/行星基线 + 可见性预计算），不适合每 tick swap。使用双缓冲 + volatile swap 即可——低频侧 tick 写入 inactive，完成后原子交换，高频侧无锁读取。

## 4. HighFrequencySnapshot 裁剪

### 4.1 去重方案

`publishRealTimeSnapshot()` 当前全量填充所有实体快照（恒星到舰船）。改造后：

```text
// 当前: 每个实体都构造 EntitySnapshot
putEntitySnapshot(new EntitySnapshot(star...));
putEntitySnapshot(new EntitySnapshot(planet...));
putEntitySnapshot(new EntitySnapshot(ship...));

// 改造后: 只构造动态实体
// 跳过 staticBaselineEntityTypes = {STAR, PLANET, SYSTEM_BARYCENTER, MOON, ASTEROID}
// 因为这些已由 LowFrequencySnapshot 承载
putEntitySnapshot(new EntitySnapshot(ship...));   // 保留
putEntitySnapshot(new EntitySnapshot(station...)); // 保留
// star/planet/moon/asteroid 不再出现
```

这样 `RealTimeWorldState.entitySnapshots` 变轻了——不再包含所有天体的基线快照，只含 tick 间变化的动态实体。

### 4.2 对渲染器的影响

桌面模式下 `StarBatchRenderer.rebuild(state)` 和 `StarHaloRenderer.rebuild(state)` 当前读 `RealTimeWorldState.getEntitySnapshotsView()` 取恒星数据。

渲染器重建时机：`!batchRenderer.isBuilt()` 在每个渲染帧检查，首次为 true 时执行一次 `rebuild()`。游戏启动/加载过程至少耗时数秒，`rebuild()` 被调用前低频快照已发布多次，数据就绪。

改造后渲染器需要改为同时读两份快照：
```java
// 渲染器读取恒星基线数据
var lowFreq = runtime.getDailySettlementStateBufferForReadonly().getActive();
var baselines = lowFreq.publicEntityBaselinesBySectorKey;

// 渲染器读取动态实体数据
var highFreq = runtime.getRealTimeWorldStateReadonly();
var ships = highFreq.getEntitySnapshotsView();  // 只有 SHIP/STATION
```

### 4.3 对 webnet DTO 转换的影响

`SnapshotMessageFactory.buildSnapshotMessageWithNation()` 当前从 `RealTimeWorldState` 拿 public/private 实体快照。改造后需要合并两份数据：

```java
// 低频基线（恒星/行星等公开实体）
var lowFreq = runtime.getDailySettlementStateBufferForReadonly().getActive();
var publicBaselines = lowFreq.publicEntityBaselinesBySectorKey;

// 高频动态（舰船等私有实体）
var highFreq = runtime.getRealTimeWorldStateReadonly();
var dynamicSnapshots = highFreq.getEntitySnapshotsView();

// 合并：公开基线 + 动态实体 + 情报过滤
```

## 5. 更新时机与间隔

### 5.1 基准设计

```java
// 在 StarAxisGameRuntime.update() 中
private static final int LOW_FREQ_INTERVAL_TICKS = 20;

void update(float dt) {
    // ... 现有模拟逻辑 ...

    if (worldState.time.simulationTick % LOW_FREQ_INTERVAL_TICKS == 0) {
        publishLowFrequencySnapshot();
    }

    publishHighFrequencySnapshot();
}
```

直接用 `simulationTick % 20` 判断，不需要额外计数器。存档恢复后 tick 连续递增，天然对齐。

每 20 tick（现实 1 秒）发布一次低频快照。可见星系的粗粒度变化（国家扩张/舰队移动）在秒级时间尺度上才有意义，20 tick 间隔足够满足需求。

### 5.2 可见性预计算开销

`VisibilitySystem.computeIntelVisibleSystems3D(nationId)` 做八叉树范围查询。每秒（20 tick）对所有国家执行一次，NationState 通常在 2~20 个，计算量可控。

权衡方案：如果未来国家数量增至数百，可将可见性预计算改为**增量脏标记驱动**（仅标记位置/探测范围变化的实体，只重新计算受影响的国家）。

### 5.3 向下兼容

`settledDay` 字段保留但不作为主要驱动，`settledAtGameSeconds` 改为 `baselineTick` 的快照时间戳。旧存档加载时自动适配。

## 6. 访问控制规则

### 6.0 核心硬约束

> **WorldState 只能由 game 模拟层读写。客户端、webnet、渲染器等外部模块不得以任何形式直接访问 WorldState。**

所有外部读取必须通过两份只读快照：
- `RealTimeWorldState` — 每 tick 更新，含时间元信息 + 动态实体（SHIP/STATION）
- `DailySettlementState` — 每 20 tick 更新，含恒星基线 + 国家资产 + 玩家映射 + 可见性 + 情报

两份快照都是双缓冲 + volatile swap，gameTicker 线程写 inactive 后原子交换为 active，外部读 active 无需同步。

### 6.1 出站广播 (SnapshotBroadcaster + SnapshotMessageFactory)

改造前读 `WorldState`，改造后必须全部改为读快照：

| 当前（违规，需改造） | 改为读 |
|---|---|
| `nationManager.getNationIdByPlayer(pid)` | `dailySettlement.playerToNationMap.get(pid)` |
| `visibilitySystem.computeIntelVisibleSystems3D(nationId)` | `dailySettlement.visibleSystemIdsByNationId.get(nationId)` |
| `intelSystem.getEffectiveDetectorLevel3D(nationId, pos)` | `dailySettlement.detectorLevelByNationAndSystem.get(nationId).get(systemId)` |
| `astro.getSystemsView()` | `dailySettlement.publicEntityBaselinesBySectorKey` |

### 6.2 入站 API (ShipCommandApi / WebPlayerWebSocketHandler)

这些 API 运行在 Undertow 工作线程，与 gameTicker 线程不同。当前直接读 `WorldState` 是**违规的**（线程不安全 + 违反访问控制），必须改为读双缓冲：

**ShipCommandApi：**
- `worldState.entitiesById.get(shipEntityId)` → `RealTimeWorldState.getEntitiesByIdView().get(shipEntityId)`（双缓冲只读视图）
- `worldState.time.simulationTick` → `RealTimeWorldState.simulationTick`

**WebPlayerWebSocketHandler：**
- `worldState.nationManager.getNationIdByPlayer(pid)` → `dailySettlement.playerToNationMap.get(pid)`，未命中时等下一帧刷新
- `worldState.intelSystem` → `dailySettlement.detectorLevelByNationAndSystem`
- `worldState.visibilitySystem.computeIntelVisibleSystems3D(nationId)` → `dailySettlement.visibleSystemIdsByNationId`

## 7. 实施步骤

### Phase 1: 数据结构改造

1. `DailySettlementState` 新增字段（playerToNationMap, visibleSystemIdsByNationId, detectorLevelByNationAndSystem, baselineTick）
2. `DailySettlementStateBuffer` 升级为双缓冲（beginFillInactive/swapPublish）

### Phase 2: game 发布逻辑改造

3. `publishBaselineSnapshot()` 填充新增字段（预计算可见性/情报/映射）
4. 触发条件从 `>= 60 游戏秒` 改为每 20 tick（按 simulationTick 计数）
5. `publishRealTimeSnapshot()` 跳过 EntityType 为 STAR/PLANET/SYSTEM_BARYCENTER/MOON/ASTEROID 的实体快照构造

### Phase 3: webnet 消费端改造

6. `SnapshotMessageFactory` 从读 `RealTimeWorldState` + `WorldState` 改为只读两份快照
7. `SnapshotBroadcaster` 可见性/情报查询从读 `WorldState` 改为读 `DailySettlementState` 预计算字段
8. `ShipCommandApi.entitiesById` 读 `RealTimeWorldState` 双缓冲替代直接读 `WorldState`
9. `WebPlayerWebSocketHandler` nationManager/intelSystem/visibilitySystem 从读 `WorldState` 改为读 `DailySettlementState`

### Phase 4: 客户端渲染器改造

10. `StarBatchRenderer`/`StarHaloRenderer` 改为读低频快照的 `publicEntityBaselinesBySectorKey`（或附加读高频快照的动态实体）

### Phase 5: 客户端初始连接推送

11. `WebPlayerWebSocketHandler.sendSnapshotToChannel()` 在客户端首次连接 `subscribeSnapshot` 时，推送两份数据：低频基线（恒星/行星骨架）+ 当前高频动态实体。确保新客户端拿到完整的场景和数据。

### Phase 6: 清理

12. 删除 `publishRealTimeSnapshot()` 中已迁移到低频的快照构造代码
13. 全局 grep `getWorldStateForSimOnly()`，确认 webnet 所有外部读已被消除

## 8. 未解决的问题

### 8.1 线程安全原子性

`ShipCommandApi` 从 `RealTimeWorldState` 双缓冲读 entitiesById 是安全的（gameTicker 写 inactive，swap 后才读取）。`SnapshotMessageFactory` 和 `SnapshotBroadcaster` 也运行在 gameTicker 线程，读 active 缓冲无竞态。

Undertow 工作线程读两个双缓冲时，`active` 字段用 `volatile` 修饰确保可见性。

### 8.2 可见性预计算的"过时"问题

低频快照每秒更新一次，可见性/情报数据最多有 1 秒的延迟。星系可见范围的粗粒度变化（国家扩张/舰队移动）在秒级尺度上不会被玩家感知。不设实时回退路径。

### 8.3 Entity 对象引用共享的可见性风险

`RealTimeWorldState.entitiesById` 中存的是 Entity 对象的原始引用。Undertow 工作线程通过双缓冲读到这些 Entity 对象时，它们的字段可能被 gameTicker 线程同时修改。

**缓解：**
- `ShipCommandApi` 读取的字段主要是 `entityId`（不可变）+ `ownerNationId`（几乎不变）
- x86 强内存模型下实际中不会出错
- 标记为已知风险，不阻塞本次重构。未来可考虑在双缓冲层做 Entity 字段的浅拷贝。
