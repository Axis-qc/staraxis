# Module Division Plan — game + webnet 模块分工计划

> 更新时间：2026-07-06
> 目标：明确 game 模块与 webnet 模块的职责边界、数据流向和分工原则，消除架构模糊地带。

---

## 1. 关键前提

**webnet 与 game 在同一个 JVM 进程内**（都是 Gradle 子模块，共享堆内存）。所有通信都是同进程 Java 方法调用，不存在进程间通信或 RPC。

运行模式对比：

| 模式 | game 位置 | webnet | 快照链路 |
|------|-----------|--------|----------|
| 桌面单机 (`lwjgl3`) | `ClientGame` 持有 | 不启动 | 渲染器直接读 `RealTimeWorldState` 双缓冲 |
| 独立 webnet 服务 (`WebNetLauncher`) | `GameSessions` 持有 | 运行中 | webnet 读双缓冲 → 转 DTO → WebSocket 发出 |

---

## 2. 模块职责边界

### 2.1 `game` — 权威模拟引擎

```
写 ─────────────────────────────────── 读
   WorldState (权威)                    RealTimeWorldState (双缓冲)
   ├─ astro (恒星系数据)                     ├─ entitiesById (实体引用)
   ├─ entitiesById (实体总表)                ├─ entitySnapshots (预打包快照)
   ├─ time (模拟时间)                        ├─ 时间/世界元信息
   ├─ nationManager                        └─ 按 systemId 索引
   ├─ intelSystem
   └─ 各模拟系统

   输入: CommandBus.submit(cmd)
   输出: RealTimeWorldStateBuffer.swapPublish()
```

**game 拥有：**
- `WorldState` 的**唯一写入权**
- `RealTimeWorldState` 双缓冲的**填充与发布权**（`publishRealTimeSnapshot()`）
- 所有命令的最终执行权（`CommandBus`）
- 模拟时间推进（`TickDispatcher` 5 阶段流水线）

**game 不关心：**
- 数据通过什么协议、格式发给谁
- 谁在读 `RealTimeWorldState`
- 命令从哪来（本地输入 / WebSocket / AI 都行）

### 2.2 `webnet` — 同进程协议转换器

```
game 进程内 ─────────────────────────────────── 外部
                      │
  RealTimeWorldState  │  SnapshotMessageFactory
  双缓冲 (只读) ──────┤──→ 转 DTO ─→ WebSocket ─→ 客户端
                      │
  CommandBus          │  WebCommandHandler
  submit(cmd) ────────┤←─ 解 JSON ←─ WebSocket ←─ 客户端
                      │
  WorldState (只读)   │  HTTP API (查询/管理)
                      │
```

**webnet 的两种角色：**

1. **出站（game → 客户端）**：读 `RealTimeWorldState` 双缓冲 → 转 DTO `SnapshotMessageDto` → WebSocket 广播
   - 当前实现在 `SnapshotMessageFactory`（转 DTO）+ `SnapshotBroadcaster`（调度发送）
   - webnet **不构造** `EntitySnapshot`，这是 game 的责任
   - webnet **不遍历** `WorldState` 自己拼数据，只读双缓冲

2. **入站（客户端 → game）**：收 WebSocket/HTTP → 解 JSON → 调 `runtime.getCommandBusForSimOnly().submit(cmd)` 或 `runtime` 的只读查询方法
   - 当前实现在 `WebCommandHandler` 实现类 + `ShipCommandApi`
   - webnet 负责**参数校验、权限校验、token 鉴权**，然后转成 game 能理解的 `Command`

**webnet 拥有：**
- `GameSessions`（管理 `worldId` → `StarAxisGameRuntime` 的映射）
- `WsConnectionManager`（WebSocket 连接生命周期）
- `AuthStore`（账号/token/权限）
- HTTP API 路由（管理接口、Mods、AI 网关）

**webnet 绝对不能做：**
- 直接写 `WorldState` 或调用非公开 API 改变游戏结果
- 绕过 `CommandBus` 执行游戏逻辑
- 自己持有第二套游戏规则实现

## 3. 数据流全图

```
桌面单机模式:
  Input ─→ Command ─→ game ─→ RealTimeWorldState ─→ Renderer
                              (双缓冲, 同进程, 零拷贝)

webnet 服务模式:
                           ┌─→ RealTimeWorldState ─→ SnapshotBroadcaster ─→ WS 客户端
  客户端 WS ─→ webnet ─→ game ─→ CommandBus
              (鉴权/解包)    (执行)   (双缓冲同上)
```

## 4. 当前架构中的模糊地带与处理决策

### 4.1 `EntitySnapshot` 的归属

`EntitySnapshot` 定义在 `game` 模块（`staraxis.game.state.snapshot`），**这是正确的**，因为：
- 桌面模式下渲染器（`StarBatchRenderer`/`StarHaloRenderer`）直接读 `RealTimeWorldState` 中的 `EntitySnapshot`
- 它同时是 webnet DTO 转换的输入
- 一份数据结构服务于两种消费方式

### 4.2 game 构造 `EntitySnapshot` 的合理性

`publishRealTimeSnapshot()` 在 game 中遍历 `WorldState` 构造 `EntitySnapshot`，这个开销**合理**：
- 唯一替代方案是 webnet 遍历 `WorldState` 自己构造，但这等于重复工作 + 让 webnet 耦合天体结构（`StarBody`/`PlanetBody`）
- 桌面模式下这个遍历也省不掉——渲染器需要 `EntitySnapshot` 来渲染
- **结论：保持现状，构造逻辑留在 game 中。**

### 4.3 webnet 不能直接读 `WorldState`

webnet 只能通过 `RealTimeWorldState` 双缓冲读快照数据，不能直接读 `WorldState.entitiesById` 等正在被模拟线程修改的数据。双缓冲提供了天然的"tick 完成瞬间的冻结帧"隔离。

---

## 5. 后续演进要点

1. **game 侧无改动必要**：当前的 game + 双缓冲 + `EntitySnapshot` 已经是合理的分层。所有"为网络打包"的工作都在 `SnapshotMessageFactory` 中，game 只提供了原材料（`EntitySnapshot`）。

2. **webnet 入站链路规范化**：`WebCommandHandler` 接口已定义，确保所有外部命令都经此路径。新增命令类型时实现 `WebCommandHandler` 接口即可。

3. **单机模式不依赖 webnet**：桌面模式读 `RealTimeWorldState` 渲染，走 `CommandBus` 输入，完全不经过 webnet。webnet 是可选组件。

4. **`CLAUDE.md` 以及 `docs/当前进行中.md` 中的"快照是 DTO 不是缓存"这条笔记**需要调整——`EntitySnapshot` 在桌面模式下确实被渲染器直接读取，不是跨进程 DTO，它是双缓冲的共享数据单元。
