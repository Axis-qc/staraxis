# StarAxis 项目规范\n\n## 1. 基本原则\n\n- 使用中文进行项目沟通、文档编写与必要注释。\n- 修改前先理解现有结构，优先复用已有方法、字段、类型和工具。\n- 禁止为了单个需求随意改动无关模块。\n- 禁止未经确认的大范围重构或跨模块迁移。\n- 先制定修改计划，再按步骤实施。\n- 新增概念先更新术语，再进入代码、配置和 UI 文案。\n\n## 2. 当前主架构规范\n\n- 当前主线是原生 LibGDX 客户端。\n- `lwjgl3` 负责桌面平台启动和窗口配置。\n- `client` 负责原生客户端生命周期、主循环、输入、渲染组织、UI 初始化和游戏运行时连接。\n- `ui` 负责 Scene2D UI、菜单、设置、HUD、控件、Skin、字体、i18n 和 JSON UI。\n- `game` 负责纯 Java 游戏模拟、世界状态、命令、时间、生成、存档和规则。\n- `web` / `webnet` 是历史或辅助链路，不作为当前主客户端架构依据。\n\n## 3. 分层边界规范\n\n### `game`\n\n- 不依赖 LibGDX。\n- 不依赖 UI。\n- 不依赖 Web/WebNet。\n- 不创建渲染对象、窗口、Stage、Actor、Texture 或 Camera。\n- 只处理游戏规则、状态、命令和模拟。\n\n### `client`\n\n- 可以依赖 `game` 和 `ui`。\n- 负责连接游戏核心与 UI/渲染。\n- 负责把 UI action 转换为 game command。\n- 负责把 game state 转换为可显示的视图数据。\n\n### `ui`\n\n- 只表达界面、控件和用户意图。\n- 通过 action 上抛交互，不直接修改 `WorldState`。\n- 不推进模拟时间，不执行游戏规则。\n\n### `lwjgl3`\n\n- 只负责平台启动、窗口配置和发行打包。\n- 不写游戏逻辑。\n- 不持有游戏状态。\n\n## 4. 代码设计规范\n\n- 模块化设计，按职责拆分系统。\n- 禁止硬编码、硬枚举；可扩展内容应走配置、资源文件或数据表。\n- 新增功能前必须搜索是否已有相似实现。\n- 公共逻辑应抽取为可复用方法或服务。\n- 命名应清晰表达用途，配置 ID 应稳定且语义明确。\n- 新增文件应有明确职责，不创建临时杂物文件。\n\n## 5. 数据与资源规范\n\n- `assets` 存放只读本体资源和默认配置。\n- `gamedata` 存放用户数据、设置、日志、存档、账号、国家和 Mod。\n- 运行期数据不得写入 `assets`。\n- 构建产物不得长期堆放在根目录。\n- Mod 和配置应尽量数据驱动，避免把内容规则写死在代码中。\n\n## 6. 游戏时间与循环规范\n\n- 游戏推进必须基于模拟时间，而不是现实帧率。\n- 非必要少用每帧更新。\n- 行星公转、舰船移动、经济结算等系统应跟随模拟时间推进。\n- 正常情况下禁止出现“时间暂停但系统仍在运动”的逻辑，特殊机制除外。\n- 当前经济系统按游戏日结算；设计口径为游戏内 24 小时一日。\n\n## 7. 坐标与尺度规范\n\n- 世界坐标系以 `(0, 0)` 为中心。\n- X 轴向右为正，Y 轴向上为正。\n- 世界角度约定：\n  - `0°`：向右\n  - `90°`：向上\n  - `180° / -180°`：向左\n  - `-90°`：向下\n- 恒星系应使用本地坐标系，星区中心为本地原点。\n- 大尺度与局部尺度之间需要明确转换关系，避免浮点精度抖动。\n- 标准星系视图比例：`100px = 1 AU`。\n\n## 8. 注释与文档规范\n\n- 注释用于解释职责、约束和复杂逻辑，不重复描述显而易见的代码。\n- 重要文件应说明文件作用、主要依赖和对外能力。\n- 新增或变更核心概念时，应同步更新 `docs/术语对齐.md`。\n- 设计草案、实施计划和长期说明统一放入 `docs/` 或其子目录。\n- 历史 Web 架构计划不得覆盖当前原生客户端主架构。\n\n## 9. 工作流规范\n\n- 开始任务前先明确目标、影响范围和验证方式。\n- 修改前先查找相关实现和相邻代码风格。\n- 每次修改应尽量小步进行，避免一次性混入多个无关目标。\n- 测试或验证以项目已有命令为准，不臆造不存在的脚本。\n- 除测试、构建、验证外，避免频繁使用终端命令。\n- 不主动提交 Git，除非明确要求。\n\n## 10. 验证规范\n\n- 原生客户端相关修改优先运行 Gradle Wrapper。\n- 涉及启动链路时优先验证 `gradlew.bat
