## 活跃任务

> **当前主线**：将玩法核心从"殖民舰殖民"重构为"扫描 → 建设 → 自动发展"闭环：舰船到达行星轨道后扫描解锁，玩家在行星上下达建设指令，运输船全自动调度材料，行星形成前沿阵地并随规模、人口、产出、资金自动升级为城市。渲染增强、骨骼动画和大规模 UI 计划不得阻塞玩法。

### G0 — 扫描、建设与自动发展重构（最高优先级）

> **设计变更**（2026-08-09 确认）：废弃殖民舰概念。不再有"殖民"命令，改由"扫描 + 建设"驱动行星发展。玩家先派遣舰船扫描行星解锁信息，然后下达建设指令；运输船全自动拉材料；首个设施建成形成前沿阵地，随发展自动升级为定居点 → 城镇 → 城市。

- [ ] **G0.5 城市自动升级**：新增城市发展结算逻辑，行星发展度随设施数量、人口、产出、资金自动计算，达到阈值后自动升级城市阶段（`OUTPOST` → `SETTLEMENT` → `TOWN` → `CITY`），复用 `city-stages.json` 的成本与人口阈值配置；消耗对应材料。

> **验收**：玩家用探索船飞到宜居行星轨道附近 → 下达扫描指令解锁 → 在行星上建设水采集器 → 运输船自动拉材料 → 设施建成形成前沿阵地 → 继续建设后行星自动升级为定居点，全程 UI 可见且有反馈。

### G2 — 元素化资源与化学生产线（高优先级）

> **设计方向**：资源不直接做成“燃料/钢材/电子元件”等终产物，而是由原始物质、基础元素和加工产物组成的生产网络。采用真实化学启发的配方，不实现完整化学模拟。
> **库存模型**：每个行星拥有一个 `LocalInventory`（本地库存），地表和轨道上的采集、加工、消费设施都访问同一个库存；运输船只负责不同库存节点之间的货物转移。

- [x] **G2.1 定义 `LocalInventory`**：每个行星、空间站和深空资源站拥有独立本地库存，记录物质数量、容量、预留数量和库存变化；地表与轨道设施不拆分成两个库存。
- [x] **G2.2 定义采集设施**：采集设施从资源点向本地库存写入原材料；第一版已支持水采集，地表、轨道、小行星和深空资源站的差异留待后续扩展。
- [x] **G2.3 定义加工设施与配方**：加工设施只从本地库存读取输入并写回产物和副产物；JSON 配方包含 `inputs`（消耗物）、`outputs`（产物）、`byproducts`（副产物）、`energyCost`（能源消耗）、`processTime`（加工时间）、`facilityType`（设施类型）和 `technologyId`（科技条件）。
- [x] **G2.4 定义最小物质集合**：第一版控制在 8～12 种，包含水、金属矿、硅酸盐、碳质矿、氢气、氧气、碳、铁、硅、铝、铜等；原始资源以矿物或化合物形式采集，不直接假设所有元素都能单独开采。
- [x] **G2.5 实现第一条化学生产线**：殖民地水资源通过电解槽从本地库存取料，按 `2H2O + 电力 -> 2H2 + O2` 写回氢气和氧气；必须消耗能源并支持副产物。
- [x] **G2.6 定义 `CargoTransfer`**：运输船从源 `LocalInventory` 扣除货物并创建运输中记录，抵达后将货物加入目标 `LocalInventory`；运输中的货物不能被两端重复使用。
- [x] **G2.7 接入 `DailySettlementState`**：`PlanetSurfaceDailySnapshot` 增加工业只读快照（本地库存 / 采集与加工设施统一字段 / 相关在途运输 / 最近结算结果）；`StarAxisGameRuntime` 保存 `lastSettlementReport` 并在基线发布时按行星拆分写入，快照全部深拷贝为不可变数据；同步支持 webnet 转发。
- [x] **G2.8 增加资源可见性与反馈**：行星工业页显示本地库存、日产出、能源消耗、设施进度和失败原因；物流页显示在途货物；工业状态已接入存档/加载，滚动内容不被窗口截断。

> **范围约束**：第一版不实现完整元素周期表、不做通用化学求解器、不追求严格质量守恒；设施之间不直接互相连接，统一通过本地库存交互；运输船只连接不同库存节点。

> **当前阶段验收**：首个设施建成后，行星会创建共享的 `LocalInventory`、水采集设施和电解槽（G0.3 建设流程触发，取代原殖民触发）；game 日结算可验证水采集、水电解和 `CargoTransfer` 的原子转移；`DailySettlementState`、webnet 和四分页行星 UI 均能按 `planetEntityId` 展示对应工业与物流数据。

#### T2 -- glTF 模型加载管线改造

> **目标**：将模型加载从 OBJ + libGDX 直接加载，改为 glTF + 中性数据结构 + 转换器架构，支持骨骼动画/PBR 材质，并为未来 Vulkan 迁移铺路。
> **背景**（2026-08-08 讨论确认）：
> - OBJ 不支持骨骼动画/形变动画，无法满足未来模型效果需求
> - glTF 是 Khronos 标准，原生支持骨骼动画/PBR/形变动画，数据布局 GPU 友好，未来 Vulkan 迁移零成本
> - 当前模型加载（ObjLoader + ModelBuilder）与 libGDX 深度耦合，换渲染后端需全部重写
> - 新建 `game_asset` 模块隔离"文件解析/网格生成"与"渲染后端"，解析层零渲染依赖，跨后端复用
>
> **架构设计**：
> ```
> assets/ (磁盘文件)          game_asset 模块 (解析)           client 模块 (转换+渲染)
>
> star_eater.gltf  ---->  GltfLoader 解析            ---->  MeshDataToModel 转换
> star_eater.bin         |                               |
> star_eater.png     MeshData (中性中间态)          libGDX Model (可渲染)
>                     + MaterialData
>                     + SkinData (骨骼)
>                     + AnimationData (动画)
>
> (程序化生成)        SphereGenerator/BoxGenerator
>                         |
>                     MeshData ----> MeshDataToModel ----> libGDX Model
> ```
>
> **未来 Vulkan 迁移**：`game_asset` 模块原封不动，client 换 `MeshDataToVkBuffer` 转换器即可。

> **状态（2026-08-08）**：T2.1～T2.9、T2.11 已完成并归档至 [`2026-08-08.md`](日志/2026-08/2026-08-08.md)。已完成资源加载、shader 初始化和舰船恒星光照方向修复；完整游戏内视觉确认仍待执行。

#### P2 -- 游戏主界面 HUD 与交互系统

> **目标**：建立完整的游戏主界面 HUD 体系，覆盖悬停提示、固定 HUD、可开关信息窗口三类 UI，形成「扫一眼标注 → 悬停看摘要 → 点开看全部 → 钉住做对比」的信息密度递进。
> **背景**：UI 控件层已完备（Vector 控件体系 + JSON 声明式 UI + 主题系统），但缺少统一窗口管理与通用悬停机制，当前 HUD 仅有时间/视图标签。原 Phase 1~8 计划已跟不上实际情况，全部作废，本方案为 2026-07-23 讨论定稿。玩家开局流程记录见 `docs/日志/2026-07/2026-07-20.md`。
>
> **核心设计决策（2026-07-23 确认）**：
> - **三层 UI 模型**：
>   - 第 1 层 HUD 固定层：始终可见、不可关闭（顶栏、命令栏、视图标签）
>   - 第 2 层悬停层：跟随鼠标的 tooltip，悬停 300ms 自动出现
>   - 第 3 层窗口层：可拖动/关闭的信息窗口，由 tooltip 钉住或点击选中打开
> - **实体详情面板**：单例跟随选中；钉住后脱离选中变独立窗口，允许多开对比（上限 3 个，超出替换最旧）
> - **钉住触发**：tooltip 显示满 3 秒自动钉住（2026-07-23 修正：原为"鼠标移入 tooltip 内 3 秒"，但鼠标移开实体 tooltip 即消失、tooltip 锚定在实体旁，鼠标来不及移入，故改为显示即计时）；钉住期间 tooltip 右下角显示圆圈进度环
> - **窗口位置**：不做位置记忆，统一在屏幕中央出现；多开时级联偏移 30px；玩家自行拖动
> - **命令栏**：纯文字按钮，图标留待 Phase 10 润色
> - **不做迷你地图**：Stellaris 模式——银河主视图即地图、缩放即导航；以场景内实体标注（Phase 6）替代迷你地图的方位表达
> - **ESC 栈**：ESC 先关闭最上层窗口，无打开窗口时才弹暂停菜单

## 工作笔记

### 迁移策略
- **不做旧代码兼容过渡**：新版确认无依赖后直接删除旧文件，不在新旧之间做兼容层
- **单向兼容**：支持读旧版数据，但写入必须用新版本格式；禁止产生旧版本数据

### 模块职责
- **权威状态仅在 game**：所有改变游戏结果的逻辑只允许在 game 模块执行
- **WorldState 仅限 game 模块访问**：WorldState 只能由 game 模拟层读写。客户端、webnet、渲染器等外部模块不得以任何形式直接访问 WorldState。
- **外部只能读两份快照**：`RealTimeWorldState`（每 tick 更新，动态实体 + 时间元信息）+ `DailySettlementState`（每 20 tick 更新，恒星基线 + 国家资产 + 玩家映射 + 可见性 + 情报等级）
- **纯渲染数据不塞进 game 状态**：轨道环顶点、光晕参数等 100% 视觉辅助数据由 client 自行维护
- **webnet 是同进程协议转换器**：webnet 与 game 在同一 JVM 内，出站读 `RealTimeWorldState` + `DailySettlementState` 双缓冲转 DTO 发 WebSocket，入站收 WebSocket 解包后调 `CommandBus.submit(cmd)`。不跨进程、不 RPC、不碰 WorldState。
- **`EntitySnapshot` 是双缓冲共享数据单元**：桌面模式下渲染器直接读双缓冲中的 `EntitySnapshot` 做渲染，不是单纯的跨进程传输 DTO。一份数据同时服务桌面渲染和网络传输。

### 代码规范
- **数据驱动优先于硬编码**：权重表、配置参数等优先用 JSON 数据文件，避免代码里写死
- **纹理注册器与业务系统分离**：`SpriteRegistry` 是底层基础设施，只做 key → 纹理映射，不感知舰船/恒星/行星等业务语义。业务系统通过 key 引用纹理，不接触文件路径。
- **舰船类型系统延后**：`ShipSizeDef` / `ship-sizes.json` 在 P0 阶段不做，待 Phase 5 造船系统上线时再定义，届时舰船按 `shipSizeId` 传入不同 spriteKey。P0 阶段所有舰船统一用默认 key。
- **布局不同则不强行抽象**：数据布局不同（如 6 float vs 7 float）的重复代码收益有限，标记 TODO 即可
- **现取现算优先**：不提前算好存快照，除非有明确的性能瓶颈证据。调 `public` 方法共享算法比塞数据进状态更干净
