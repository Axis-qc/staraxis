### 3. 行星轨道环渲染优化
- **问题描述**：Profiling 结果显示 `celestial/planet` 占 13.32ms（74%），是唯一瓶颈
- **原因分析**：
  1. 轨道环每帧对每个行星重算 512 点椭圆（sin/cos + toRenderPos），约 13ms
  2. 遍历所有实体做轨道可见性判断，无视口剔除
  3. 三次遍历实体表（可见性检查、行星球体、轨道环）
- **解决方案**：
  1. **轨道世界坐标缓存**：`ensureOrbitCache()` 按轨道参数哈希缓存，只在参数或星位变化时重算 sin/cos
  2. **轻量更新**：`updateOrbitRingLightweight()` 仅做 `toRenderPos` 平移（相机移动时）+ 透明度更新
  3. **星区剔除**：直接用 `entity.sectorCoord` 与 `sectorCenters` 的 q,r 匹配，不建空间索引
  4. **单次遍历**：合并行星可见性检查和轨道环渲染为一次遍历
- **优化结果**：`celestial/planet` 从 13.32ms → 2.68ms，总帧时从 18ms → 8.73ms（约 115fps 理论值）
- **相关文件**：
  - `web/src/rendering/layers/celestial/renderers/planetRenderer.ts`

### 4. 前端插值周期时长错配修复
- **问题描述**：舰船移动渲染卡顿，debug 数据显示 `blend` 从 0 直接跳到 1，没有平滑过渡
- **原因分析**：
  1. `calculateCycleDurationMs` 用游戏时间差（`gameDeltaSeconds × 1000`）算插值周期
  2. 后端 tick 到达节奏不均匀（正常 40-60ms，突发时 1ms 内到两个 tick，空窗期 100ms+）
  3. 游戏时间和真实时间不同步：游戏时间 50ms 对应的真实到达间隔可能只有 1ms
  4. 周期提前结束 → 进入 freeze/extrapolate → 下一个 tick 到达时位置跳变
- **解决方案**：用真实收包时间 `receivedAtClientMs` 替代游戏时间驱动插值周期
  - `cycleDurationMs = next.receivedAtClientMs - current.receivedAtClientMs`
  - `cycleStartClientMs = currentSnapshot.receivedAtClientMs`（不再用 `nowMs`）
  - 渲染进度 = `(now - current.receivedAt) / (next.receivedAt - current.receivedAt)`
- **相关文件**：
  - `web/src/game/world/interpolation/snapshotInterpolationBuffer.ts`

### 5. 后端低频快照阻塞高频快照分析与修复
- **问题描述**：前端插值修复后仍有 ~100ms 周期性卡顿，与后端低频快照（每秒一次）周期一致
- **原因分析**：
  1. 通过 tick 到达数据分析发现：每约 20 个 tick 出现一次 100ms 空窗 + 突发
  2. 后端 `tickAndBroadcast()` 每 tick 构建全量 DTO（1936 实体），低频时额外提取低频 DTO
  3. 低频快照（含恒星/行星/星区中心）JSON 体量大，虽在 `lowFreqExecutor` 异步序列化+发送
  4. 但 Undertow 的 XNIO IO 线程对同一 channel 写入串行，低频大数据 flush 时高频小消息排队
- **解决方案**：`shouldSendLowFreq` 判断提到循环外，低频 DTO 在主线程从已构建的全量 DTO 提取（引用拷贝，微秒级），异步线程只做 JSON 序列化 + WebSocket 发送，不碰 `runtime` 双缓冲
- **技术决策**：异步线程不调用 `buildSnapshotMessageWithNation`（内部有 `publishRealtimeSnapshotIfNeeded` 副作用），避免与主线程的双缓冲 swap 竞态
- **相关文件**：
  - `webnet/src/main/java/staraxis/webnet/websocket/SnapshotBroadcaster.java`
