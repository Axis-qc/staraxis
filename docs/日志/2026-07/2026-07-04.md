## 工作摘要
轨道缩放实现。发现 AstroGenerator 以 starRadius*6 作为轨道基准导致巨星系统轨道越界（超出 System View 3M 远平面），引入 systemRadiusGURange 替代恒星物理半径作为轨道基数，确保所有类型行星轨道适配世界空间。

## 已完成的任务

### 1. 轨道缩放方案设计与审查
- **问题描述**：巨星（RED_GIANT/BLUE_GIANT）恒星的轨道以 starRadius*6 为基准，第7颗行星轨道 ~3,528,000 GU 超出 System View 远平面 3,000,000 GU。根因是用恒星物理半径而非系统范围做轨道基数。
- **解决方案**：为 star-types.json 中7个恒星类型新增 systemRadiusGURange 字段，轨道第一圈改用 systemRadius * random(0.03, 0.08)，上限 systemRadius*0.9 截断，下限 starRadius*2.0 保护。
- **审查修复**：初版 0.85 上限 + 2.5 下限导致巨星系统极端情况仅 2 颗行星，审查后调整为 0.9 上限 + 2.0 下限，行星数提升至 4~6 颗。

## 问题与解决方案

### 问题1：极端 RNG 下行星数偏少
- **现象描述**：B 型/巨星在 systemRadius 取最小值 + starRadius 取最大值 + 连续出现 2.0 分离因子时，行星数可能低至 2-3 颗。
- **原因分析**：下限保护 starRadius*2.0 对巨星（35k~40k）强制抬高了第一轨道，消耗了大量 systemRadius 空间。
- **解决方案**：调整上限 0.85->0.9 释放空间；同时降低下限 2.5->2.0 减少消耗。典型行星数提至 4~6 颗，极端 <3 概率降至 <5%。

### 问题2：初版配置下巨星系统行星数不足
- **现象描述**：v1 计划中 RED_GIANT 的 systemRadius 下限 300k，但 starRadius*2.0=70k 为首轨，第二轨 ~105k，第三轨 ~180k...第四轨已近上限。
- **原因分析**：未充分联合分析下限保护和上限的交互。
- **解决方案**：依据玩家"重力井最大 900k 直径"放宽至 systemRadius 上限 300k，且下限从 2.5 降至 2.0，保证所有类型最坏情况 ≥3 颗。

## 技术要点
1. **行星系统尺度 ≠ 恒星物理尺度**：恒星膨胀到巨星时，其原行星盘范围不会同比放大。因此 systemRadius 不取恒星物理半径，而是按恒星类型单独配置的系统范围。
2. **下限保护的必要性**：starRadius*2.0 确保行星不会被渲染到恒星内部（视觉上行星与恒星可区分）。
3. **重力井独立于轨道**：gravityWellRadiusGU = systemRadius * 1.5，不再依赖最远行星位置，避免小样本波动。
4. **所有类型重力井 ≤ 450k GU**：满足玩家指定 900k 直径上限，且最大轨道远小于 System View 3M 远平面。
