### 2. T2 -- glTF 模型加载管线改造方案设计

> **目标**：将模型加载从 OBJ + libGDX 直接加载，改为 glTF + 中性数据结构 + 转换器架构，支持骨骼动画/PBR 材质，并为未来 Vulkan 迁移铺路。

**讨论确认的关键决策**：

- **格式选择**：glTF -- Khronos 标准，原生支持骨骼动画/PBR/形变动画，数据布局 GPU 友好，未来 Vulkan 迁移零成本
- **模块隔离**：新建 `game_asset` 模块（零渲染依赖），隔离"文件解析/网格生成"与"渲染后端"
- **架构设计**：
  ```
  assets/ (磁盘文件)          game_asset 模块 (解析)           client 模块 (转换+渲染)

  star_eater.gltf  ---->  GltfLoader 解析            ---->  MeshDataToModel 转换
  star_eater.bin         |                               |
  star_eater.png     MeshData (中性中间态)          libGDX Model (可渲染)
                       + MaterialData
                       + SkinData (骨骼)
                       + AnimationData (动画)

  (程序化生成)        SphereGenerator/BoxGenerator
                          |
                      MeshData ----> MeshDataToModel ----> libGDX Model
  ```
- **未来 Vulkan 迁移**：`game_asset` 模块原封不动，client 换 `MeshDataToVkBuffer` 转换器即可
- **模块架构验证**：`game` 模块零 libGDX 渲染依赖，换 Vulkan 时 game/webnet 不动，只重写 client + ui
- **发布格式**：.gltf 明文发布，方便玩家写 mod，引擎加资源校验容错

## 问题与解决方案

### 问题1：OBJ 格式不支持骨骼动画
- **现象描述**：OBJ 仅支持静态几何 + 材质，无骨骼动画/形变动画/PBR 材质
- **原因分析**：OBJ 是 1990s 的几何交换格式，设计之初就不考虑动画
- **解决方案**：改用 glTF（Khronos 标准，原生支持骨骼动画/PBR/形变动画）
- **验证结果**：方案已确认，T2 任务已分解

### 问题2：模型加载与 libGDX 深度耦合
- **现象描述**：ObjLoader 和 ModelBuilder 直接产出 libGDX Model，换渲染后端需全部重写
- **原因分析**：当前没有隔离"文件解析"与"渲染后端"的中间层
- **解决方案**：新建 `game_asset` 模块，解析层输出中性 `MeshData`，client 层写转换器转成 libGDX Model
- **验证结果**：方案已确认，`game` 模块已验证零 libGDX 渲染依赖，换 Vulkan 时 game/webnet 不动

## 技术要点

- **glTF vs OBJ**：glTF 原生支持骨骼动画/PBR/形变动画，数据布局 GPU 友好；OBJ 仅支持静态几何
- **.gltf vs .glb**：.gltf 是多文件（JSON + .bin + 贴图），.glb 是单文件二进制；开发期用 .gltf 方便调试，发布时用 .gltf 明文方便 mod
- **模型加载流程**：磁盘文件 -> game_asset 解析 -> MeshData 中性中间态 -> client 转换 -> libGDX Model
- **Vulkan 迁移路径**：game_asset 模块零修改，client 换 MeshDataToVkBuffer 转换器
- **实例化渲染**：几百个模型实例只需几十种唯一网格 + transform 矩阵，启动加载 < 1 秒
- **game 模块纯净性**：game 模块零 libGDX 渲染依赖，换 Vulkan 时 game/webnet 完全不动
