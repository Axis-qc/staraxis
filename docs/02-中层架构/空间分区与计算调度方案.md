> **版本**：1.0（草案）
> **日期**：2026-07-01

> **关联文档**：`docs/02-中层架构/3D宇宙架构方案.md`

## 0. 核心结论

- **计算分区**：按恒星系（`starSystemId`）分组，采用**加权贪心分配**（LPT 算法）分发到线程
- **空间索引**：Octree 只做空间查询，不参与计算调度
- **两者解耦**：计算分区解决"谁算"，空间索引解决"在哪查"

## 1. 问题陈述

### 1.1 旧 hex 系统的混淆

旧 hex 网格把两件事混在一起：

| 概念 | 旧 hex 方案 | 问题 |
|-----|-----------|------|
| 空间索引 | 星区网格（`SectorCoord`） | 按六边形划分空间 |
| 计算分区 | 隐含按星区 | 实际每 tick 全表扫描 `entitiesById.values()` |

结果是：hex 网格既没有真正用作分区，用在索引上也只是 O(1) 查坐标 → 星区的映射，并未利用网格的邻域特性。

### 1.2 3D 宇宙的新需求

3D 宇宙没有规则网格可用，需要重新设计：

```
需要明确回答两个问题:
  1. 空间查询:           "实体A附近有什么？"     → Octree
  2. 计算负载分配:         "这个实体的移动/战斗谁算？" → 本方案
```

### 1.3 当前计算模式分析

每 tick 的执行链路：

```
StarAxisGameRuntime.update():
  1. commandBus.executeCommands()        → 按 entityId 查找单个实体
  2. shipMovementSystem.update()         → entitiesById.values() 全扫 → filter ShipBody
  3. visibilitySystem.updateAll()        → 全扫找本国实体 → hex 星区扩展
  4. intelSystem.rebuildIfDirty()        → 全扫找探测源 → hex 星区扩展
```

- 目前**所有计算都是全表扫描**，没有空间分区参与调度
- 唯一的空间索引是 `entitySectorById: Map<Long, SectorCoord>` ＋ `WorldSector.entityIds` 列表

## 2. 设计目标

```
1. 负载均衡:      各线程计算量接近，避免"一个线程满载、其他空闲"
2. 空间局部性:    同一恒星系内的实体尽量在同一线程处理
3. 通信最小化:    跨线程交互控制在消息级别，不共享可变状态
4. 重平衡可控:    战斗热点变化时能调整分配，但不频繁抖动
5. 渐进可实施:    先单线程，后多线程，架构不改
```

## 3. 计算分区方案：按 starSystemId 加权分配

### 3.1 为什么选恒星系

恒星系是游戏世界天然的"计算边界"：

```
一个恒星系包含:
  ─ 恒星:         1~6 颗     (静态)
  ─ 行星:         0~15 颗    (静态)
  ─ 空间站:       0~5 个     (低频变动)
  ─ 己方舰船:     0~50 艘    (动态)
  ─ 敌方舰船:     0~200 艘   (战斗峰值)

特点:
  ─ 复杂度有上限（不会出现一个星系 10 万艘船）
  ─ 星系内交互密集（战斗/移动/经济），跨星系交互低频（FTL/远程传感器）
  ─ systemId 是现有数据模型的一级字段（Entity.systemId），零成本
```

相比按空间区域（Octree 分块）的致命问题：

| 方案 | 问题 |
|-----|------|
| 按空间区域分 | 螺旋臂稠密区 vs 臂间空洞 → 负载极度不均 |
| 按 entityId 区间分 | 同星系实体分到不同线程 → 战斗需要跨线程同步 |

### 3.2 负载度量

每个星系的"重量" = 该星系内需要每 tick 处理的实体数量：

```java
// 轻量级计数器，每 tick 由 worker 线程更新
class SystemLoad {
    long systemId;
    int entityCount;       // 当前星系实体总数
    int dynamicCount;      // 动态实体数（舰船等），变动时触发重平衡
    long lastActiveTick;   // 最后活跃 tick，用于判断冷/热
}
```

不同实体类型的计算权重（可配置调整）：

| 实体类型 | 权重 | 说明 |
|---------|------|------|
| 恒星 | 0 | 完全静态，不参与计算 |
| 行星 | 0 | 完全静态，不参与计算 |
| 空间站 | 0.5 | 极少变动 |
| 静止舰船 | 0.3 | 停泊/待机 |
| 移动舰船 | 1.0 | 每 tick 物理推进 |
| 战斗中舰船 | 2.0~5.0 | 武器/护盾/命中结算 |

### 3.3 初始分配算法（LPT 贪心）

世界生成完成后执行一次，生成 `systemId → threadId` 映射表。

```java
/**
 * LPT（Longest Processing Time）加权贪心分配。
 *
 * 按实体数降序排列星系，每次把当前最重的星系分配给
 * 当前总负载最轻的线程。
 *
 * 保证: 最忙线程的负载 ≤ 最优值 + 单个最大星系负载
 * 定理: 这是多项式时间内最小化最大完成时间的最优贪心策略
 */
Map<Integer, List<Long>> assignSystems(
        List<SystemLoad> systems,    // 所有星系负载（按 entityCount 降序）
        int threadCount) {

    // 初始化 N 个线程的负载桶
    long[] loads = new long[threadCount];
    Map<Integer, List<Long>> assignment = new HashMap<>();

    // 按实体数降序排列
    systems.sort((a, b) -> b.entityCount - a.entityCount);

    for (SystemLoad sys : systems) {
        // 找到当前总负载最小的线程
        int bestThread = argMin(loads);
        assignment.computeIfAbsent(bestThread, k -> new ArrayList<>())
                  .add(sys.systemId);
        loads[bestThread] += sys.entityCount;
    }

    return assignment;
}
```

#### 示例

3 线程，6 个星系：

```
星系负载:
  A(180), B(120), C(10), D(10), E(8), F(8)

排序后: A(180), B(120), C(10), D(10), E(8), F(8)

分配步骤:
  线程0: A(180)                              → 负载 180
  线程1: B(120)                              → 负载 120
  线程2: C(10) → D(10) → E(8) → F(8)        → 负载 36

结果: [180, 120, 36]  ← 重负载分散，轻负载聚合
```

对比 `systemId % N` 均匀模分：

```
最坏情况: A(180) + B(120) 分到同一线程
结果: [300, 10, 8]  ← 一个线程撑死，两个线程空转
```

### 3.4 动态重平衡

#### 触发条件

```java
// 每 60 tick 或战斗开始/结束时检查
boolean needsRebalance(SystemLoad sys, SystemLoad previous) {
    // 方案1: 绝对阈值
    return Math.abs(sys.entityCount - previous.entityCount) > THRESHOLD;
    // 或 方案2: 相对阈值
    // return (sys.entityCount * 1.0 / previous.entityCount) > 1.5;
}
```

#### 执行策略

```
只移动"热星系"（entityCount > HOT_THRESHOLD），冷星系不动

迁移代价:
  ─ 将该星系的所有实体从一个线程迁移到另一个
  ─ 迁移期间该星系的计算暂停一 tick（实体被双缓冲保护）
  ─ 迁移完成后恢复，不影响其他星系

防抖:
  ─ 每个星系两次迁移之间至少间隔 300 tick（~5 秒）
  ─ entityCount 使用滑动平均值，不裸用瞬时值
```

### 3.5 跨线程通信

不同线程负责的星系之间需要协作的场景有限：

| 场景 | 方案 |
|-----|------|
| 星系内舰船移动 | 同一线程内，直接操作 |
| 舰船 FTL 跳跃到另一个星系 | 从源线程移除 → 发送消息到目标线程 → 目标线程下 tick 注册 |
| 远程传感器（跨星系探测） | Octree 只读查询 + 消息传递 |
| IntelSystem 汇总 | 每个线程输出本地情报 → 主线程合并 |
| 存档/快照 | 暂停所有线程 → 主线程全量收集 |

```java
// 跨线程消息结构
class InterThreadMessage {
    enum Type {
        ENTITY_ARRIVAL,    // 舰船到达目标星系
        SENSOR_DETECTION, // 远程传感器探测结果
        COMBAT_EFFECT,     // 跨星系武器效果（极少）
    }
    Type type;
    long targetSystemId;
    EntitySnapshot payload;
}
```

## 5. Octree 的角色

### 5.1 职责明确

```
Octree (空间索引)                 SystemAssignment (计算分区)
─────────────────                ────────────────────────
"离这个点 1000GU 内有啥？"         "System A 的移动让线程2算"
"这个 Frustum 里有哪些恒星？"      "System B 的战斗让线程1算"
"捡取射线命中了什么？"             "System C 空闲，线程0顺便处理"

  只读共享（每 tick 重建）          只有 systemId→threadId 映射
  可被任意线程安全查询              worker 线程只处理自己的星系
```

### 5.2 并发策略

```java
// Octree 的 epoch 管理
class GalaxyOctree {
    volatile int epoch;          // 当前版本号
    OctreeNode root;

    // 每 tick 由主线程重建（或在 worker 完成后合并）
    void rebuild(WorldState ws) { ... }
    
    // 任意线程只读查询
    List<Long> querySphere(Vector3 center, double radius) { ... }
}
```

Octree 本身不需要锁——它是**写一次、读多次**（per-tick 重建）。worker 线程在计算期间只读查询。

## 8. 重要设计决策

### 决策 1：不按空间区域分区

```
原因:
  ─ 恒星分布极不均匀（螺旋臂稠密 vs 臂间空洞）
  ─ 玩家活跃区域集中在 1~3 个星系，其他星系几乎空闲
  ─ 按空间分区要么负载不均，要么过度分片
  
结论: 按实体 ID 分（逻辑分区）优于按坐标分（空间分区）
```

### 决策 2：用 starSystemId 而非 entityId

```
原因:
  ─ systemId 天然对应游戏逻辑边界
  ─ 星系内实体交互密集（战斗、传感器）
  ─ 跨星系交互有明确事件边界（FTL 跳跃）
  ─ 星系数量已知（~5000），entityId 范围未知
  
结论: systemId 分区比 entityId 区间分区更合理
```

### 决策 3：动态重平衡只移动热星系

```
原因:
  ─ 冷星系（< 10 实体）几乎不产生计算负载
  ─ 迁移一个冷星系的收益远小于迁移开销
  ─ 只有战斗中星系（100+ 实体）才值得迁移
  
规则:
  ─ 只迁移 entityCount > HOT_THRESHOLD（建议 50）的星系
  ─ 两次迁移间隔 ≥ 300 tick
```

### 决策 4：Octree 不做并发写

```
原因:
  ─ Octree 每 tick 全量重建（或批量增量更新）
  ─ worker 线程只读查询，不修改
  ─ 避免了锁竞争和树平衡问题
  
结论: 写一次读多次，epoch 版本控制即可
```

## 附录：负载估算

### 典型世界规模

| 参数 | 值 |
|-----|-----|
| 恒星系总数 | 5000 |
| 平均每个星系实体数 | 8~15（恒星+行星） |
| 活跃星系（有舰船） | 50~200 |
| 战斗中星系（峰值） | 1~5 |
| 战斗星系实体数 | 100~500 |

### 线程分配示例

假设 4 核 CPU，5000 星系，其中有 3 个热星系各 200 实体，其他为空星系（~10）：

```
LPT 分配后:
  线程0: 热星系A(200) + 150个空星系(1500)   = 1700
  线程1: 热星系B(200) + 150个空星系(1500)   = 1700
  线程2: 热星系C(200) + 150个空星系(1500)   = 1700
  线程3: 0个热星系   + 1850个空星系(18500)  = 18500

问题: 空星系太多，全部分到一个线程了。
修正: 空星系也做加权，不能按"10个实体"计算，
      因为"空星系"的维护开销比"战斗星系"小很多。
      
      引入 "冷星系打包"：
      ─ 实体数 < 5 的星系按一个固定小权重（如 0.1）计入
      ─ 避免几千个冷星系全堆到最后一个线程
```

### 权重校准

```
初始权重:
  天文实体（恒星/行星）: 0      → 完全不产生计算
  空间站:               0.5    → 经济结算
  静止舰船:             0.3    → 燃料/维护
  移动舰船:             1.0    → 物理推进
  战斗中舰船:           3.0    → 武器/护盾/伤害结算

实际权重需通过 profile 校准:
  在 WorldState 中添加 Measurement 计数器
  运行 1000 tick → 统计每个实体类型的平均耗时
  调整权重公式使总耗时与权重成正比
```
