# AI 插件化架构设计

> 创建时间：2026-06-13  
> 状态：规划中  
> 最新口径：`web` 后续定位为 AI 控制台 / 管理控制台；`webnet` 后续定位为联机网络管理与控制网关；主游戏画面由原生客户端 `client`/`lwjgl3` 渲染。完整职责边界见 `0-docs/01-底层架构/运行时模块职责与联机AI架构.md`。

## 一、背景与动机

### 当前架构的问题

1. **耦合度高**：`ai_system` 作为独立 Python 进程，需要单独维护和启动。
2. **灵活性差**：AI 模型配置硬编码在 `config.yaml`，玩家无法自定义。
3. **扩展性弱**：新增 AI 功能需要修改 `ai_system` 代码。
4. **浏览器渲染方向偏离目标**：`web` 不再作为主游戏画面客户端继续扩展，浏览器侧应转向 AI 控制台与管理界面。

### 目标架构

将 AI 功能从“内置独立进程”转变为“受权限保护的 AI 控制台 / 工具网关”，让玩家可以：

- 自行配置 LLM Provider（本地模型或云端 API）。
- 通过 `web` AI 控制台与 AI 对话或下达自然语言意图。
- 通过 `webnet` 暴露的受控 API / tool 调用获取游戏数据和执行操作。
- 在不让浏览器承担主游戏画面渲染的前提下，让 AI 控制玩家可控单位。
- 让所有写操作统一进入 `game` 的 `CommandBus` / 运行时命令入口，避免形成第二套规则实现。

## 二、架构设计

### 2.1 整体架构

```text
┌─────────────────────────────────────────────────────────────┐
│                        玩家设备                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌─────────────┐    WebSocket/HTTP    ┌──────────────────┐ │
│  │ web AI控制台 │ ◄────────────────► │ webnet (Java)    │ │
│  │  (Vue 3)    │                     │ 联机管理/API网关 │ │
│  └──────┬──────┘                     │                  │ │
│         │                            │ ┌──────────────┐ │ │
│         │ AI/API                     │ │ REST API     │ │ │
│         ▼                            │ │ /api/v1/*    │ │ │
│  ┌─────────────┐                     │ └──────────────┘ │ │
│  │  AI 插件    │ ───── REST/WS ─────►│ ┌──────────────┐ │ │
│  │ /外部工具   │                     │ │ WebSocket    │ │ │
│  └──────┬──────┘                     │ │ /ws/ai       │ │ │
│         │                            │ │ /ws/native   │ │ │
│         ▼                            │ └──────────────┘ │ │
│  ┌─────────────┐                     └────────┬─────────┘ │
│  │ LLM Provider│                              │           │
│  │ (玩家自配)   │                              │ Command   │
│  └─────────────┘                              ▼           │
│                                      ┌──────────────────┐ │
│                                      │ game runtime     │ │
│                                      │ WorldState       │ │
│                                      │ CommandBus       │ │
│                                      └──────────────────┘ │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 模块职责

- `game`
  - 负责权威世界状态、模拟推进、命令执行和只读快照发布。
  - AI/API 写操作必须转换为 `Command` 后提交给 `game`。
- `webnet`
  - 负责账号、token、权限、世界/房间/会话管理。
  - 负责 AI tool/API 网关。
  - 负责后续原生联机同步入口。
- `web`
  - 负责 AI 控制台、管理控制台、摘要展示、日志和命令结果展示。
  - 不再负责 Three.js 高频世界画面渲染。
- `client`/`lwjgl3`
  - 负责原生客户端和主游戏画面渲染。

### 2.3 API 设计原则

1. **只读优先**：默认暴露只读 API，写操作需要显式授权。
2. **权限隔离**：AI 使用玩家 token 认证，只能访问该玩家有权限的数据。
3. **命令入口统一**：AI/API 写操作必须转换为 `game` 模块中的 `Command`，通过运行时命令入口提交，禁止直接写 `WorldState`。
4. **视野与归属约束**：AI 只能读取玩家可见范围内的数据，只能控制玩家拥有或被授权的单位。
5. **向后兼容**：保留 `/ws/ai` 端点，但标记为“遗留接口”或过渡接口。
6. **文档优先**：所有 API 必须有 OpenAPI/Swagger 文档。

## 三、API 清单

### 3.1 只读数据 API（可安全暴露）

| 端点 | 方法 | 说明 | 权限 |
|------|------|------|------|
| `/api/v1/world/summary` | GET | 获取世界概览 | 玩家可见范围 |
| `/api/v1/entities/{type}` | GET | 获取实体列表 | 玩家视野内 |
| `/api/v1/entities/{type}/{id}` | GET | 获取单个实体详情 | 玩家视野内 |
| `/api/v1/sectors` | GET | 获取星区列表 | 已探索星区 |
| `/api/v1/sectors/{id}/systems` | GET | 获取星区内的恒星系 | 已探索星区 |
| `/api/v1/countries` | GET | 获取国家列表 | 已知国家 |
| `/api/v1/countries/{id}` | GET | 获取国家详情 | 已知国家 |
| `/api/v1/fleets` | GET | 获取舰队列表 | 玩家舰队 |
| `/api/v1/fleets/{id}` | GET | 获取舰队详情 | 玩家舰队 |
| `/api/v1/research` | GET | 获取科技树状态 | 玩家科技 |
| `/api/v1/economy` | GET | 获取经济数据 | 玩家经济 |

### 3.2 操作 API（需要玩家授权）

| 端点 | 方法 | 说明 | 权限 |
|------|------|------|------|
| `/api/v1/fleets/{id}/move` | POST | 移动舰队 | 玩家舰队 |
| `/api/v1/fleets/{id}/attack` | POST | 攻击目标 | 玩家舰队 |
| `/api/v1/research/{id}/start` | POST | 开始研究 | 玩家科技 |
| `/api/v1/buildings/{id}/construct` | POST | 建造建筑 | 玩家建筑 |

所有操作 API 的处理流程必须是：

```text
token/session 校验
  -> playerId/nationId 绑定校验
  -> 视野/归属/授权校验
  -> 转换为 game Command
  -> runtime.submitCommand(...)
```

### 3.3 WebSocket 数据

| 端点 | 说明 | 消息类型 |
|------|------|----------|
| `/ws/ai` | AI 控制台/AI 插件过渡通信通道 | `ai.chat`, `tool.call`, `tool.result` |
| `/ws/game` | 游戏状态摘要或过渡期实时推送 | `snapshot.update` |
| `/ws/native` | 后续原生联机同步入口（命名可调整） | `native.frame`, `command.ack` |

> 注意：`/ws/game` 不再作为浏览器主画面渲染链路继续扩展；高频世界画面应由原生客户端渲染。

## 四、实现计划

### Phase 1：API 暴露（短期）

1. 在 `webnet` 中创建 `api/v1/` 包，作为 AI 控制台与外部工具的受控 API 网关。
2. 实现只读 API 端点，数据来源优先为 `game` 发布的只读快照/ViewModel。
3. 添加 OpenAPI 文档。
4. 禁用 `ai_system` 自动启动。
5. 将 `web` 首页方向调整为 AI 控制台 / 管理控制台，不再扩展浏览器世界渲染链路。

### Phase 2：AI 控制台 MVP（短中期）

1. 在 `web` 中实现登录、世界选择、AI 聊天、工具调用日志、命令结果展示。
2. 在 `webnet` 中实现 AI tool gateway。
3. 将 AI tool 写操作转换为 `game` Command。
4. 将查询结果按玩家权限过滤后返回给 AI 控制台。

### Phase 3：WebSocket 与联机增强（中期）

1. 实现 `/ws/ai` 的 AI 对话与工具调用流式返回。
2. 实现面向原生客户端的联机同步 endpoint，例如 `/ws/native`。
3. 支持面向 AI 控制台的低频摘要订阅。
4. 添加操作 API 端点，所有写操作转换为 `game` Command。

### Phase 4：插件生态（长期）

1. 发布 AI 插件 SDK（JavaScript/TypeScript）。
2. 提供示例浏览器扩展或外部工具。
3. 建立插件市场机制。

## 五、迁移策略

### 5.1 ai_system 处理

- **保留代码**：`ai_system/` 目录保留不删除。
- **禁用启动**：修改 `WebAiAutoStarter.java`，默认不自动启动。
- **标记遗留**：在 `/ws/ai` 端点添加 `deprecated` 或 `legacy` 标记。
- **控制台转向**：`web` 迁移为 AI 控制台 / 管理控制台，停止把 Three.js 世界画面作为主方向继续扩展。
- **文档说明**：在 README 中说明新旧架构的过渡期。

### 5.2 向后兼容

- 保留 `/ws/ai` 端点，现有 AI 工具仍可使用。
- 新 API 与旧接口并行运行一段时间。
- 提供迁移指南给已使用 `ai_system` 的玩家。
- 浏览器世界渲染相关代码可作为调试/参考保留，但不作为主客户端目标。

## 六、安全考虑

### 6.1 认证与授权

- 所有 API 必须使用玩家 token 认证。
- AI 操作权限与玩家账户绑定。
- 敏感操作（如删除、攻击）需要二次确认。
- AI 工具调用必须携带可审计的 `requestId` / `toolCallId`。

### 6.2 速率限制

- 对 API 调用添加速率限制。
- 防止 AI 过度消耗服务器资源。
- 记录 API 使用日志用于审计。

### 6.3 数据隔离

- AI 只能访问玩家视野内的数据。
- AI 不能获取其他玩家的私有信息。
- AI 不能绕过游戏规则（如战争迷雾）。
- AI 不能直接写 `WorldState`。
