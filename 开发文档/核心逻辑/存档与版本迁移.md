# 存档与版本迁移（核心口径）

> 目标：定义存档的**权威结构**、**写入与读取流程**、**版本校验规则**与**失败处理口径**。
> 
> 本项目口径：游戏可重复游玩、每局可重新生成；**不承诺旧版本读取新版本存档（不向后兼容）**。但考虑到小补丁/小版本升级通常不影响存档，本文支持“新版本读取老版本存档（有限向前兼容）”：加载时允许版本不一致并提示玩家，但必须满足兼容规则（见下文）。
> 
> 因此本文不设计跨版本迁移链（不维护逐版本迁移脚本），仅要求存档记录 `gameVersion` 并在加载时执行兼容性判定与提示。

---

## 1. 核心结论（先读这一段即可落地）

- 存档必须记录 `gameVersion`（存档生成时的游戏版本：用于加载兼容性判定与提示）。
- 读取存档时（核心规则）：
  - 若 `save.gameVersion == currentGameVersion`（版本一致）：直接加载。
  - 若 `save.gameVersion < currentGameVersion`（存档版本更旧）：
    - **允许加载**（用于小补丁/小版本升级场景）。
    - 必须在 UI 明确提示“版本不一致”（提示当前版本与存档版本）。
  - 若 `save.gameVersion > currentGameVersion`（存档版本更新）：
    - **拒绝加载**（旧版本不能加载新存档）。
    - 提示玩家“请升级到对应版本或更新版本后再加载”。
- 不做自动迁移：
  - 不维护逐版本迁移脚本链（不做 schemaVersion 迁移）。
  - 允许加载旧存档的前提是：本次更新不属于“大型更新/破坏性更新”。
- 存档内容分层：
  - **权威状态（必须保存）**：会影响游戏结果、联机权威推进需要的状态。
  - **可再生状态（不必保存）**：可由权威状态/配置/种子重建的缓存。
  - **客户端表现缓存（不保存或可选保存）**：UI 展开状态、镜头位置等，不影响规则。

---

## 2. 存档版本策略（有限向前兼容口径）

### 2.1 `gameVersion`（版本判定口径）

- `gameVersion`（存档版本：推荐采用 **语义化版本 SemVer**，例如 `1.2.0`）：
  - 写入：每次保存时写入当前运行版本（`currentGameVersion`）。
  - 读取：加载时用于判定“是否允许加载”与“是否需要提示版本不一致”。

#### 2.1.1 推荐格式：语义化版本（SemVer）

- **格式**：`MAJOR.MINOR.PATCH`（主版本号.次版本号.修订号），例如 `1.2.3`。
- **优点**：
  - **语义明确**：`MAJOR` 版本更新通常意味着破坏性变更；`MINOR` 版本新增功能但保持兼容；`PATCH` 版本修复问题。
  - **可靠比较**：可直接通过库函数或自定义逻辑比较版本大小，实现 `save.gameVersion < currentGameVersion` 的判定。
- **替代方案**：如果开发流程强依赖构建号，也可使用单调递增的整数 `buildNumber`，比较更简单，但语义不如 SemVer 清晰。

#### 2.1.2 兼容性规则（强制口径）

- `save.gameVersion == currentGameVersion`（版本一致）：允许加载。
- `save.gameVersion < currentGameVersion`（存档更旧）：允许加载，但必须提示“版本不一致”。
- `save.gameVersion > currentGameVersion`（存档更新）：拒绝加载。

> 注：本规则默认适用于“小补丁/小版本”（`PATCH` 或 `MINOR`）升级。若某次更新为破坏性更新（大型更新，例如 `MAJOR` 版本号变更），应在发布说明中明确该版本将拒绝加载更旧存档，或要求玩家开新档。

### 2.2 不支持的能力（必须明确写在文档里）

- 不支持：
  - 旧版本加载新版本存档（不向后兼容）
  - 自动迁移与兼容层（不维护 schemaVersion 迁移脚本链）

## 3. 存档整体结构（建议口径）

> 存档结构的目标是：能完整恢复服务端权威状态，并支持联机房间在暂停/断线后继续。

### 3.1 顶层结构

```ts
// 概念性结构（口径），字段名仅示例；具体实现可用 JSON/二进制。
interface SaveFile {
  meta: SaveMeta;       // 元信息：版本、时间、展示摘要
  world: WorldState;    // 世界权威状态
  players: PlayerState[]; // 玩家/派系权威状态（含资产、科技、外交等）

  // 可选：用于快速加载的索引/摘要（不影响规则，可丢弃重建）
  indices?: SaveIndices;
}

interface SaveMeta {
  gameVersion: string;     // 游戏版本：加载时必须与当前运行版本一致
  createdAtUnixMs: number; // 创建时间：用于 UI 展示
  updatedAtUnixMs: number; // 最近保存时间：用于 UI 展示
  saveName: string;        // 存档名：用于 UI 展示

  // 可选摘要：用于存档列表展示（不影响规则）
  summary?: {
    simulationDay: number; // 当前模拟日：用于展示进度
    serverTick?: number;   // 可选：当前权威 tick：用于联机恢复
    seed?: string;         // 可选：世界种子：用于展示
  };
}
```

### 3.2 权威状态分层口径

- `WorldState`（世界权威状态：必须足以恢复模拟推进）建议包含：
  - 世界生成的关键参数与种子（用于复现）
  - 世界结构（星区/恒星系/行星等）的权威数据（如果不是完全可再生）
  - 当前推进进度（例如 `simulationDay`、必要时 `serverTick`）
  - 全局事件队列/冷却/计时器（如果影响规则结果）

- `PlayerState`（玩家/派系权威状态）建议包含：
  - 资产/库存/资源、生产队列、科研状态
  - 外交关系与条约
  - 控制的实体集合（舰队、城市、空间建筑等）

## 4. 写入流程（保存口径）

### 4.1 保存触发点（建议）

- 手动保存（玩家主动触发）
- 自动保存（定时/关键事件点）
- 联机暂停点保存（例如掉线暂停、主机/服务端主动落盘）

### 4.2 保存过程（建议口径）

1. 停止接收新指令（或进入保存锁：避免边写边改）
2. 从服务端权威状态生成 `SaveFile`
3. 写入 `meta.gameVersion = currentGameVersion`
4. 序列化并写盘（必要时写临时文件再原子替换）
5. 写入完成后恢复接收指令

---

## 5. 读取流程（加载口径）

### 5.1 加载前置校验（强制）

- 校验文件可读、结构完整、必要字段存在
- 校验 `meta.gameVersion` 存在

### 5.2 版本判定与提示（强制）

- 若 `save.meta.gameVersion == currentGameVersion`（版本一致）：允许加载。
- 若 `save.meta.gameVersion < currentGameVersion`（存档更旧）：
  - 允许加载。
  - 必须提示“版本不一致”（显示当前版本与存档版本）。
- 若 `save.meta.gameVersion > currentGameVersion`（存档更新）：
  - **拒绝加载**（旧版本不能加载新存档）。
  - 必须提示玩家升级游戏版本后再加载。

### 5.3 提示文案口径（建议）

- 版本一致：可不提示，或仅在调试模式显示。
- 存档更旧（允许加载）：
  - “存档版本（`save.meta.gameVersion`）与当前版本（`currentGameVersion`）不一致，已尝试加载。若出现异常建议开新档。”
- 存档更新（拒绝加载）：
  - “该存档版本（`save.meta.gameVersion`）高于当前版本（`currentGameVersion`），当前版本无法加载新存档。请升级游戏后再尝试。”

---

## 6. 与联机的关系（口径）

- 以服务端为准保存权威状态。
- 若联机存在“暂停点/时间膨胀/掉线处理”等机制：
  - 存档应记录足以恢复推进的时间轴字段（例如 `simulationDay`，必要时 `serverTick`）。
- 客户端本地缓存（UI、镜头）不应污染权威存档；如需保存，建议独立为客户端偏好文件。

---

## 7. 验收标准（最小闭环）

- 能保存并成功加载同版本存档。
- 版本不一致时必定拒绝加载，且错误提示信息完整。
- 存档结构明确区分“必须保存的权威状态”和“可再生/缓存状态”。
