# 回放与确定性（联机分歧定位口径）

> 目标：定义**服务器自动回放**与**确定性校验**机制，解决“联机不同步/分歧”问题。
> 
> 核心要求（本轮约束）：
> - 服务器自动滚动保存 **30 分钟** 的回放数据。
> - 回放内容包含：指令流、事件流、随机源、版本号、时间戳、必要状态摘要（hash）。
> - 回放文件采用环形缓冲方式，新数据自动覆盖旧数据，不无限增长。
> - 出现分歧时可通过日志 + 回放文件快速复现并定位。

---

## 1. 回放整体设计

| 组件 | 作用 | 关键要点 |
|------|------|-----------|
| 指令流（`Commands`，指令记录集合） | 记录客户端→服务端所有指令（含重发同 `cmdId`（指令全局唯一 ID，用于幂等追踪）） | 按接收顺序记录，包含完整 `CommandHeader`（指令头：通用追踪/排序/鉴权信息）与 `payload`（指令体：具体业务字段） |
| 事件流（`Events`，事件记录集合） | 记录服务端→客户端的增量事件 | 按发送顺序记录，包含 `EventHeader`（事件头：事件类型/时间/追踪字段） + `payload`（事件体：具体变化字段） |
| 状态摘要（`StateHash`，状态哈希摘要） | 每 N tick（tick：服务端权威推进步）生成哈希，快速对比状态一致性 | 建议 `N=10`（每 10 tick 生成一次），字段选择见 2.3 |
| 随机源（`RandomSeeds`，随机源记录） | 记录服务端所有随机数种子或序列 | 保证重放确定性（确定性：相同输入得到相同输出） |
| 版本信息（`VersionInfo`，版本信息） | 记录 `gameVersion`（游戏版本，SemVer）、`protocolVersion`（协议版本）、`schemaVersion`（结构版本，可选） | 回放加载前置校验（校验：防止跨版本回放无意义） |

---

## 2. 回放文件结构（建议示例）

```
replay.pkg (binary 或 JSONL)
├── header {
│    versionInfo: { gameVersion, protocolVersion },
│    beginServerTick: number,         // 回放开始 tick
│    endServerTick: number,           // 回放结束 tick
│    createdAtUnixMs: number
│ }
├── records[ ]  // 按时间顺序连续追加
│    ├── type: 'Command' | 'Event' | 'StateHash' | 'Seed'
│    ├── serverTick: number
│    ├── payload: any
└── ...
```

### 2.1 写入策略

- **环形缓冲**：服务器内存中维护 `records[]` 的环形队列，长度覆盖 30 分钟。
- **落盘节奏**：
  - 每分钟 flush 一次追加文件。
  - 若文件超过 30 分钟窗口，则截断/覆盖最旧部分（可通过维护多个 segment 文件或对同一文件循环写）。

### 2.2 读取/重放流程

1. 读取 `header`，校验 `versionInfo` 与当前运行版本一致。
2. 按 `records[]` 时间顺序回放到模拟引擎：
   - 重现指令流 → 驱动服务器逻辑。
   - 对比事件流与重算结果，若不一致触发定位流程。

### 2.3 状态摘要 (StateHash)

- 建议字段：
  - `serverTick`
  - `simulationDay`
  - `globalResourceHash`（全局资源、经济关键数值 hash）
  - `fleetPosHash`（舰队位置 hash）
  - `rngStateHash`（随机源状态）
- 生成算法：MurmurHash / xxHash 等快速 hash。
- 用途：
  - 快速检测“客户端汇报 hash 与服务器 hash 是否一致”。
  - 回放定位：二分查找分歧 tick。

---

## 3. 日志集成（Log + Replay）

- 关键链路日志：
  - 指令接收、Ack、执行耗时
  - 事件生成、广播耗时
  - StateHash 生成 & 对比结果
- 日志字段需包含：`serverTick`, `cmdId`, `playerId`, `latencyMs`, `category`, `replayFileOffset`（便于跳转）。

---

## 4. 分歧定位流程（最小闭环）

1. **检测分歧**：客户端上报 `StateHash` 与服务器不一致；或服务器自检 hash 不一致。
2. **锁定回放窗口**：根据分歧 tick，截取前后若干 tick 的回放子段。
3. **离线重放**：
   - 在同版本服务器 build 上离线重放。
   - 若复现分歧 → 进入二分定位。
4. **二分定位**：
   - 逐步缩小 `startTick ~ endTick` 区间，直到定位到第一个分歧 tick。
5. **代码/数据检查**：
   - 查看同 tick 指令处理、事件生成、随机数消耗、并行写冲突点。

---

## 5. 约束与注意事项

- **性能开销**：30 分钟窗口 + 二进制序列化，预估磁盘吞吐 `≈ 指令/事件速率 * recordSize`，需要在性能预算中评估。
- **安全**：回放文件仅保留在服务器，不下发给客户端（避免泄漏内部状态实现细节）。
- **版本升级**：若 `MAJOR` 版本升级导致协议/存档不兼容，旧回放文件可弃用。

---

## 6. 验收标准

- 服务器可在后台持续生成 30 分钟滚动回放文件。
- 出现 hash 分歧时，能利用回放 + 日志在离线环境复现并定位到具体 tick。
- 回放文件不会无限增长，新数据会覆盖最旧数据。
