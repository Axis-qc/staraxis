# 游戏循环与模拟推进（核心逻辑）

> 目标：定义游戏的核心循环、模拟推进方式与“按日结算/时间停止”的统一口径。

## 1. 核心循环（宏观）

1. 玩家在星区/恒星系/行星等层级做决策（建造、移动、贸易、外交等）
2. 客户端将决策以 **指令（Command）** 形式提交给服务端
3. 服务端在模拟时间推进中执行规则计算并更新世界状态
4. 服务端向客户端发送事件/快照，客户端刷新 UI 与呈现

## 2. 模拟推进原则

- 核心逻辑必须由模拟时间驱动（禁止用帧率驱动核心状态）
- 尽量减少每帧更新：
  - 可按“事件触发 + 固定结算点”的方式推进（例如日结算）

## 3. 时间单位口径（与《时间推进规则》一致）

- 24 游戏小时 = 1 游戏日
- 默认：1 游戏小时 = 1 现实秒
- 经济系统按日结算

## 4. 结算节奏（建议口径）

- 高频：移动、战斗态势等可按较小步长推进（例如每若干模拟秒）
- 低频：经济、人口、维护、市场按日结算

> 注：具体步长值属于实现参数，但“哪些系统属于日结算账本”必须在经济系统文档中明确。

## 5. 计算压力下的时间膨胀（整体减速推进）

> 目标：游戏后期实体数量/交互量激增（例如大规模舰队战斗）时，**宁可整体变慢，也不允许跳过结算/丢失步骤**，以保证权威状态不会因为“算不完”而出现不一致。

### 5.1 核心口径

- **整体减速，而不是降低精度**：
  - 模拟仍按既定规则逐步推进（tick/步长不变，结算步骤不变）。
  - 当服务端计算压力上升时，降低“现实时间 -> 模拟时间”的推进速度，让 CPU/线程池有更多时间把当前步长内的计算做完。
- **服务端权威决定推进速度**：
  - 客户端不自行决定推进速度，只做显示与预测适配。

### 5.2 触发条件（建议口径）

- 以“每个推进步/每个 tick 的计算耗时”作为压力指标：
  - 当连续 N 次推进步耗时超过预算（例如预算 50ms，但实际 120ms），触发时间膨胀。
  - 当连续 M 次推进步耗时恢复到预算以内，逐步恢复到正常速度。

### 5.3 时间膨胀系数（建议口径）

- 定义 `timeScale`（时间膨胀系数）：
  - `timeScale = 1.0`：正常速度
  - `0 < timeScale < 1.0`：整体变慢
- 建议计算方式（示例口径）：
  - `timeScale = clamp(budgetMs / avgComputeMs, minScale, 1.0)`
  - 其中 `avgComputeMs` 为最近一段窗口的平均计算耗时；`minScale` 为最低速度下限（防止慢到不可玩）。
- 恢复策略：
  - `timeScale` 必须平滑变化（避免忽快忽慢），例如每秒最多变化 ±0.05。

### 5.4 客户端表现口径

- 当 `timeScale` 降低时：
  - 客户端展示“时间膨胀/减速推进”状态（例如 UI 显示 x0.6）。
  - 对弱一致内容（移动/轨迹表现）允许加大插值缓冲，避免画面抖动。

## 6. 掉线/超时处理与暂停决策（联机口径）

> 目标：当玩家掉线或网络超时导致无法继续稳定同步时，避免“强行推进 + 缺席玩家状态不确定”引发不一致。

### 6.1 基础规则（权威口径）

- 服务端监测到玩家连接掉线或超时：
  - 将该玩家标记为“掉线/超时”。
  - **踢出该玩家的实时联机会话**（会话踢出：断开当前连接，保留其账号身份可重连）。
- 服务端进入“联机暂停点”（暂停点：停止模拟推进，仅保留 UI/输入）：
  - 触发一个全局暂停事件/提示（提示：告诉剩余玩家发生了掉线）。

### 6.2 由在场玩家选择后续（权威口径）

- 在场玩家可选择：
  - **等待掉线玩家重新进入**：保持暂停，直到其重连成功。
  - **继续推进游戏**：服务端解除暂停，继续模拟推进。

### 6.3 继续推进时的缺席玩家口径

- 当选择“继续推进”时，必须在规则层明确缺席玩家的处理方式（建议二选一，项目需定稿）：
  - **托管/冻结**：缺席玩家不再接收输入，其可控实体进入托管策略（例如停止主动行为/仅防御）。
  - **AI 接管**：缺席玩家由 AI/脚本接管（需在 AI 文档中定义口径）。

> 注：无论采用哪种方式，都必须保证服务端权威推进与事件顺序确定，避免并发写状态导致的不一致。

---

## 7. 时间停止（分域冻结）
- 舰船或特殊技能，停止时间推进，但自身可正常交互，移动，攻击等行为
- 时间停止冻结：模拟推进
- 允许继续：UI、输入、镜头、视觉表现
- 例外清单必须在对应系统文档中显式列出
