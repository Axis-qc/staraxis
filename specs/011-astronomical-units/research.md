## 1. 定点数（Fixed-point）实现方案

### Research Question
如何实现定点数表示天文单位，确保确定性和高性能？

### Decision: 使用 long（64 位整数）+ 缩放因子

**Rationale**:
- **确定性**：整数运算保证跨平台一致性，避免浮点数精度问题
- **性能**：整数运算比 BigDecimal 快，比浮点数更可控
- **范围**：long 类型可表示 -2^63 到 2^63-1，配合缩放因子可覆盖所需范围

### Implementation Details

**缩放因子选择**：
- **基础缩放因子**：`SCALE_FACTOR = 10^12`（1 万亿）
- **内部单位**：1 AU = 10^12 内部单位
- **表示范围**：
  - 最小值：0.000000000001 AU（1 内部单位）
  - 最大值：约 9,223,372,036 AU（约 145,000 光年）

**计算公式**：
```java
// AU 转换为内部单位
long internalUnits = (long)(auValue * SCALE_FACTOR);

// 内部单位转换为 AU
double auValue = (double)internalUnits / SCALE_FACTOR;
```

**精度考虑**：
- 对于小于 0.000000000001 AU 的值，使用单位转换（例如使用更小的单位或科学计数法）
- 对于大于约 145,000 光年的值，使用光年或秒差距作为单位

### Alternatives Considered

1. **使用 float（32 位浮点数）**
   - 优点：内存占用小，性能好
   - 缺点：精度有限，跨平台可能不一致，不符合确定性要求
   - **拒绝原因**：精度不足，无法保证确定性

2. **使用 double（64 位浮点数）**
   - 优点：精度较高，性能好
   - 缺点：跨平台可能不一致，浮点运算误差累积
   - **拒绝原因**：无法保证完全确定性，浮点误差可能累积

3. **使用 BigDecimal**
   - 优点：无限精度，完全确定性
   - 缺点：性能开销大，内存占用大
   - **拒绝原因**：性能不符合游戏实时计算要求

## 2. 单位转换精度和舍入策略

### Research Question
如何实现 AU、光年、秒差距之间的转换，确保精度达到 99.9% 以上？

### Decision: 使用精确的转换常数 + 定点数计算

**Rationale**:
- 使用标准天文定义确保准确性
- 定点数计算避免浮点误差累积
- 转换常数预先计算，避免运行时误差

### Implementation Details

**转换常数**（基于标准定义）：
- `1 AU = 1.496 × 10^8 公里`（精确值）
- `1 光年 = 63,241.077 AU`（精确值，基于光速和地球轨道）
- `1 秒差距 = 206,265 AU`（精确值）

**转换实现**：
```java
// AU 转光年
long lightYears = (auInternalUnits * 1000) / 63241077;  // 使用定点数避免浮点误差

// 光年转 AU
long auInternalUnits = (lightYearsInternalUnits * 63241077) / 1000;
```

**舍入策略**：
- 使用定点数时，舍入到最接近的内部单位
- 对于显示，保留足够的小数位（例如光年显示到小数点后 3 位）
- 转换精度验证：通过单元测试验证转换精度达到 99.9% 以上

### Alternatives Considered

1. **直接使用浮点数转换**
   - 优点：实现简单
   - 缺点：精度可能不足，误差累积
   - **拒绝原因**：不符合精度要求

2. **使用科学计数法存储**
   - 优点：可表示极大和极小值
   - 缺点：实现复杂，性能开销
   - **拒绝原因**：对于游戏场景过于复杂，定点数已足够

## 3. 数据迁移工具设计

### Research Question
如何设计迁移工具，确保现有游戏数据能够正确转换到新单位系统？

### Decision: 版本化迁移 + 批量转换 + 验证机制

**Rationale**:
- 版本化迁移确保可追溯性和可回滚
- 批量转换提高效率
- 验证机制确保数据完整性

### Implementation Details

**迁移流程**：
1. **检测数据版本**：读取现有数据，识别版本号
2. **转换映射**：根据旧单位系统到新单位系统的映射进行转换
3. **批量处理**：支持目录批量转换
4. **验证**：转换后验证数据完整性和合理性
5. **备份**：转换前自动备份原始数据

**转换映射表**：
- 旧单位系统（游戏单位）→ 新单位系统（AU）
- 需要根据当前系统确定转换比例（例如：1 游戏单位 = X AU）

**验证机制**：
- 范围检查：转换后的值在合理范围内
- 一致性检查：相关数据之间的比例关系保持一致
- 完整性检查：所有必需字段都已转换

### Alternatives Considered

1. **兼容层（运行时转换）**
   - 优点：不需要迁移，向后兼容
   - 缺点：性能开销，代码复杂度高
   - **拒绝原因**：不符合规范要求（已选择完全迁移）

2. **手动迁移**
   - 优点：用户可控
   - 缺点：易出错，效率低
   - **拒绝原因**：不符合用户体验要求

## 4. 可视化缩放机制实现

### Research Question
如何实现自动缩放 + 手动调整的可视化缩放机制？

### Decision: 分层缩放系统 + UI 控件覆盖

**Rationale**:
- 自动缩放解决大部分观察困难
- 手动调整提供灵活性
- 分层设计保持代码清晰

### Implementation Details

**自动缩放逻辑**：
1. **视图级别缩放**：根据摄像机缩放级别自动调整
2. **天体类型缩放**：不同天体类型使用不同的基础缩放比例
   - 恒星：基础缩放 × 视图缩放
   - 行星：基础缩放 × 视图缩放 × 0.5（更小）
   - 轨道：基础缩放 × 视图缩放
3. **阈值控制**：当视图缩放超过阈值时，自动调整显示细节

**手动调整机制**：
- UI 控件：滑块或按钮，允许用户调整缩放倍数
- 覆盖自动缩放：用户调整后，手动设置覆盖自动计算
- 重置功能：提供重置到自动缩放的功能

**实现位置**：
- 逻辑层：`VisualScaleConfig` 类存储缩放配置
- UI 层：`AstronomicalScaleRenderer` 类实现渲染转换
- 配置层：`visual-scale-config.properties` 定义默认缩放参数

### Alternatives Considered

1. **完全自动缩放**
   - 优点：用户无需操作
   - 缺点：无法满足所有用户需求
   - **拒绝原因**：不符合规范要求（需要手动调整选项）

2. **完全手动缩放**
   - 优点：用户完全控制
   - 缺点：用户体验差，需要频繁调整
   - **拒绝原因**：不符合规范要求（需要自动缩放）

## 5. 配置系统设计

### Research Question
如何设计配置系统，支持星区大小、单位转换比例和可视化缩放参数的可配置？

### Decision: Properties 文件 + 配置加载器 + 预设系统

**Rationale**:
- Properties 文件简单易用，符合项目现有模式
- 配置加载器提供统一接口
- 预设系统提供快捷选项

### Implementation Details

**配置文件结构**：
```
assets/i18n/
├── astronomical-units-config.properties    # 基础单位定义
├── sector-size-config.properties           # 星区大小配置（默认值 + 可配置）
├── orbit-size-config.properties            # 轨道大小配置
├── star-size-config.properties             # 恒星大小配置（按类型）
├── planet-size-config.properties           # 行星大小配置（按类型）
└── visual-scale-config.properties          # 可视化缩放配置
```

**配置加载器设计**：
- `AstronomicalUnitSystem`：加载基础单位配置
- `SizePresetLoader`：加载大小预设配置
- `VisualScaleConfigLoader`：加载可视化缩放配置
- 所有加载器支持缓存，避免重复 I/O

**预设系统**：
- 提供预设档位（small/medium/large）作为快捷选项
- 支持自定义配置覆盖预设
- 配置验证：加载时验证配置合理性

### Alternatives Considered

1. **JSON 配置文件**
   - 优点：结构化，易于解析
   - 缺点：需要额外依赖，不符合项目现有模式
   - **拒绝原因**：项目已使用 properties 文件，保持一致性

2. **硬编码配置**
   - 优点：性能好，实现简单
   - 缺点：不符合数据驱动原则，难以修改
   - **拒绝原因**：违反宪法要求（禁止硬编码）

## 6. 逻辑单位到渲染单位的转换比例

### Research Question
如何确定默认的逻辑单位（AU）到渲染单位（像素）的转换比例？

### Research Finding: 基于当前系统分析

**当前系统状态**（根据 `游戏比例与单位距离.md`）：
- 星区渲染大小：`hexRadius = 50.0` 像素
- 星区逻辑大小：`blockSize = 1.0` 游戏单位
- 转换关系：**未明确定义**

**新系统设计**：
- 星区逻辑大小：1 星区 = 1 光年 = 63,241 AU
- 星区渲染大小：保持 `hexRadius = 50.0` 像素（向后兼容）

**转换比例计算**：
- 1 星区 = 63,241 AU = 50 像素
- 因此：1 AU ≈ 0.00079 像素（对于星区级别）
- 但实际渲染时，不同尺度的天体需要不同的转换比例

**Decision: 分层转换比例**

**Rationale**:
- 不同尺度的天体需要不同的转换比例才能正确显示
- 星区级别、轨道级别、恒星/行星级别分别定义转换比例

**Implementation**:
- 星区级别：1 光年 = 50 像素（保持现有）
- 轨道级别：1 AU = X 像素（可配置，默认基于视图缩放）
- 恒星/行星级别：使用可视化缩放机制动态调整

### Alternatives Considered

1. **统一转换比例**
   - 优点：实现简单
   - 缺点：无法同时正确显示不同尺度的天体
   - **拒绝原因**：不符合真实比例显示需求
