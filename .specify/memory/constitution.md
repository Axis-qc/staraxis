# StarAxis Constitution

## Core Principles

### I. 模块化、可维护性与数据驱动 (Modularization, Maintainability & Data-Driven)
所有功能必须以模块化方式设计。在创建新方法或字段前，必须先检索现有代码库以避免重复。

- **禁止硬编码**：禁止硬编码 (Hardcoding) 与硬枚举 (Hard Enums)。
- **数据驱动优先**：游戏行为与内容应由外部数据（如 JSON/表）定义，而不是硬编码在代码中。
- **配置加载口径**：所有可配置项（如数值、ID、路径）必须通过配置系统加载，禁止散落的魔法数字
  (Magic Numbers) 与硬编码字符串。
- **可演进性**：配置与数据结构需要允许未来迭代与 Mod 扩展。

### II. 架构分层与层间边界（单机） (Layered Architecture & Layer Boundaries)
系统架构必须严格遵循分层原则，即使在单机模式下也必须保持清晰的层间边界，以保证可维护性与长期演进。

- **项目定位**：本项目为 2D 俯视角太空 4X 大战略；不考虑 3D 渲染。
- **单机分层口径**：
  - **核心模拟层（Sim/Core）**：负责推进 `WorldState`（规则、随机判定、落账点）。
  - **平台与表现层（Platform/Presentation）**：负责窗口/输入/2D 渲染/音频/UI（含 JCEF Web UI，如使用）与资源加载等平台 glue，不得包含会改变游戏结果的规则计算。
- **UI 只读与解耦**：UI 层必须作为独立层级存在，通过特定的 UI 模型（UI Model）/ViewModel 或数据绑定与游戏逻辑解耦。
- **禁止项**：
  - 严禁在 UI/表现层直接修改权威世界数据（`WorldState`）。
  - 严禁在核心模拟层直接构建 UI 相关条件或状态。
  - UI 逻辑不得包含任何会改变游戏结果的规则计算，仅负责响应数据变化并更新视图。
- **对外暴露**：核心模拟层应当通过接口/事件/快照向外暴露状态，由 UI 层监听并决定如何显示。
- **可复用与本地化**：UI 组件应具备可复用性，并支持本地化文本系统。

### III. 单机权威与本地世界状态 (Offline Authoritative)
- **核心**：本项目采用单机模式，游戏世界状态的唯一权威为本地进程内的 `WorldState`
  （或同等命名的世界状态容器）。
- **边界**：任何会改变游戏结果的逻辑、计算与随机判定，必须在核心模拟模块中执行，并以对
  `WorldState` 的写入作为最终落账点。
- **禁止**：
  - 模块绕过统一入口直接“偷写”其他模块维护的实体数据。
- **说明**：联机与服务端系统当前不在范围内，相关文档与实现应以单机模式为准。

### IV. 确定性模拟 (Deterministic Simulation)
- **核心**：游戏的核心模拟逻辑必须是确定性的。在给定相同输入序列和初始状态下，模拟结果必须
  完全一致。
- **应用**：这是存档/读档一致性的基础。
- **禁止**：在核心逻辑中引入不确定性来源，如未固化种子的随机数、浮点数精度敏感计算、依赖
  系统时间或哈希顺序等。

### V. 实体-ID 索引模型 (Entity-by-ID)
- **核心**：所有游戏数据必须以 ID 作为唯一索引与引用方式。任何系统模块不得持有跨帧/跨模块的
  “裸对象引用”作为权威引用。
- **适用实体示例**（不限于）：
  - 国家 `countryId`
  - 星区 `sectorId`
  - 恒星系 `starSystemId`
  - 星球 `planetId`
  - 舰队 `fleetId`（多个舰船的集合体）
  - 舰船 `shipId`（单个舰船）
  - 领袖 `leaderId`
  - 人口 `populationId`
- **ID 生成方式（原则）**：
  - ID 的生成方式以“实体类型”为边界进行组织（例如按类型分配 ID 空间或由类型 + 序列构成）。
  - ID 生成与索引模型的具体设计单独沉淀到《ID 索引模型》文档中，以便迭代。
- **对象引用生命周期**：
  - 允许在 **单个模拟 tick** 内持有实体对象引用（例如局部变量/临时计算对象）。
  - **跨 tick** 必须仅持有 ID（或同等的可失效引用结构），禁止跨 tick 持有权威实体对象引用。
- **系统写入规则**：
  - 经济/战斗/外交/AI 等系统模块必须通过 `id` 获取实体数据，并仅修改其负责字段，最终写回
    `WorldState`。
  - 任意“修改实体”的操作必须是可追踪的：输入（哪些 id）→ 变更（哪些字段）→ 落账（写入点）。
- **禁止**：
  - 以对象实例地址/哈希作为跨系统引用。
  - 通过 UI 层直接改写实体集合。

### VI. 内存常驻与实体文件存档 (In-Memory + Save Files)
- **核心**：游戏运行时，世界数据应常驻内存；并且必须支持保存为实体文件（存档）与从实体文件
  加载恢复。
- **存档要求（原则）**：
  - **完整性**：存档必须包含恢复游戏所需的最小完整世界状态（含所有被引用的实体）。
  - **引用完整性**：任何 ID 引用在存档中必须可解析（禁止悬挂引用）。
  - **一致性**：读档后应能继续确定性推进，且存档/读档不应引入额外随机性。
  - **版本迁移**：存档格式必须具备版本号；当数据结构演进时需提供迁移策略。
- **设计拆分**：
  - 存档系统的具体设计（文件格式、原子性、校验、压缩、错误处理、版本迁移细则等）单独沉淀到
    《存档系统》文档中，以便迭代。
- **禁止**：
  - 运行时依赖外部服务（如服务端）才能恢复存档。
  - 仅保存“差量且无法恢复”的状态（除非同时能保证可完整重建）。

### VII. 规范化命名与注释 (Standardized Naming & Documentation)
代码可读性优于简洁性，规则统一且可执行：
- **语言约定**：所有回复、说明、文档、技术交流与代码注释必须使用简体中文。
- **标识符约定**：代码中的标识符保持英文；禁止使用拼音命名；错误信息、日志内容允许为英文。
- **命名约定**：变量/函数使用 camelCase；类/接口/组件使用 PascalCase；常量使用
  UPPER_SNAKE_CASE；文件/文件夹使用 kebab-case；命名需语义清晰，禁止随意缩写。
  - **示例**：变量 `playerId`；函数 `loadSaveGame()`；类 `FleetController`；接口
    `ShipRepository`；组件 `MainMenuPanel`；常量 `MAX_SHIP_COUNT`；文件夹
    `combat-simulator/`；文件 `fleet-controller.java`。
- **注释约定**：注释用于解释“为什么这样设计”，而不是代码字面含义；复杂逻辑、业务判断、边界
  条件必须写注释；禁止无意义注释；统一使用 `TODO` / `FIXME` / `NOTE` / `HACK` 标记。
  注释以中文为主，必要术语可附英文。

#### 文档字段注释规范
- **目标**：让任意单篇文档即可自洽，读者无需跳转即可理解字段 / 结构 / 缩写含义。
- **适用范围**：所有开发文档（总览、系统设计、协议、示例、缺口清单等）。
- **正文写法（行内字段必须注释）**：
  - `fieldName`（一句话解释它是什么或做什么用）
- **代码块写法（每个字段行内注释）**：

```ts
interface SaveHeader {
  saveId: string;          // 存档唯一 ID
  saveVersion: number;     // 存档版本号
  simulationTick: number;  // 当前模拟 tick
}
```

- **枚举/状态码写法**：枚举值必须附带中文解释，例如 `Timeout`（请求超时）。
- **例外情况**：CPU、GPU、JSON 等通用缩写可不解释。

### VIII. 扩展性与 Mod 支持 (Extensibility & Mod Support)
架构设计必须预留扩展接口。无需向后兼容，直接进行覆盖迭代开发，但必须在底层设计中考虑 Mod
加载机制和 API 暴露，确保游戏生态的长期生命力。

### IX. 游戏模拟驱动 (Simulation-Driven Logic)
游戏逻辑必须严格遵循游戏模拟时间，而非依赖帧率 (FPS)。尽量减少在 `update` (每帧更新)
方法中编写非必要逻辑，以优化性能并确保多端同步的一致性。

### X. 多核性能优化 (Multi-Core Performance Optimization)
- **并行优先**：所有性能关键的系统必须优先考虑多线程/多任务并行实现，显式利用 CPU 多核能力。
- **无锁或低锁**：在高并发路径中应采用无锁或极低锁粒度的算法与数据结构，避免全局锁成为瓶颈。
- **任务调度**：引擎层必须提供统一的 Job System 或任务队列，将可并行的工作拆分为细粒度任务，
  由调度器在不同核心上动态分配。
- **线程安全**：所有跨线程共享的数据结构必须通过不可变数据、消息传递或锁分段策略保证线程安全；
  严禁出现竞态条件。
- **性能度量（指定需要再进行测试）**：新增或修改的并行代码必须附带基准测试，证明相较单线程实现
  存在显著性能提升或在相同性能下降低能耗。

## 技术标准与约定 (Technical Standards & Conventions)

### 坐标系与轴向
- **方向**：0 向右，90 向上，180/-180 向左，270 向下。
- **轴向**：X 轴向右为正，Y 轴向上为正。

### 人口与资源单位
- **存储单位**：人口相关字段统一以百万人为单位（1 个体 = 0.000001 百万人）。
- **显示规范**：UI 层面需通过辅助函数动态转换为 K/M/G 格式，保持视觉上的直觉性。

### 性能与资源管理（游戏开发）
- **避免帧内分配**：在高频 `update` / 渲染路径中避免创建临时对象与隐式装箱；必要时使用对象池或
  复用容器。
- **资源加载可控**：资源加载必须可追踪、可释放、可复现；避免散落式的直接 IO/硬路径读取，优先
  通过统一的资源/资产管理入口（例如 AssetManager 或等价封装）。
- **数据驱动优先**：数值、平衡、文本、本地化与可配置内容应数据化（文件/表/配置）而非硬编码，
  便于调参与 Mod 扩展。

## 开发工作流 (Development Workflow)

### 修改原则与质量门禁
- **计划先行**：所有修改必须先制定详细的修改计划，严禁在未经允许的情况下进行大范围或跨模块修改。
- **命令限制**：严禁在非测试场景以及未指定使用终端下使用终端命令。所有非测试性的环境变更、构建
  触发或资源处理必须优先通过 Gradle 任务或专门的自动化脚本完成，确保操作的可审计性和幂等性。
- **职责隔离**：禁止对当前分配任务外的其他模块进行随意变动，确保变更的可追溯性和局部性。
- **质量门禁**：项目的核心质量门禁是确保游戏能够正常编译和启动。**不强制要求编写单元测试**。
  开发者应优先保证代码的稳定性和可集成性，而非追求测试覆盖率。

### 版本控制与合并纪律 (Version Control & Merge Discipline)
- **顶层架构入库**：顶层架构/整体设计文档必须纳入 Git 并随架构变更同步更新（避免只存在于个人笔记
  或聊天记录）。
- **上传时机**：默认在当前任务/用户故事全部完成（实现 + 文档对齐）后再统一上传（push），避免在未
  完成阶段频繁推送造成主干噪音。
- **合并时机**：合并分支必须发生在工作完成之后（任务清单完成、必要的手工验证完成）。禁止在未达成
  质量门禁时合并到主分支。
- **例外流程**：若确需中途上传用于协作/备份，必须显式标注 WIP（例如 commit message/PR 标题包含
  WIP），且不得合并。

## Governance

本宪章是 StarAxis 项目的最高开发准则，所有代码提交、方案评审及任务拆解均须遵循上述原则。

- **修订流程**：对本宪章的任何修订，都必须经过技术评审并由架构负责人确认，以确保项目技术方向的一致性。
- **版本策略**：宪章版本遵循语义化版本（SemVer）。
  - MAJOR：对治理/原则作出不兼容的重定义或移除核心约束。
  - MINOR：新增原则或对原则作出实质性扩展。
  - PATCH：措辞澄清、拼写修正、非语义变更。
